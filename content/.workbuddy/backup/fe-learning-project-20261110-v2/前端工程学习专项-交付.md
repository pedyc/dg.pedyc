## 目标

不学会怎样：回滚只能重跑流水线，而流水线构建的是主干最新提交——于是「回滚」实际是又发了一版新代码；线上出事后只有压缩后的文件名与行列号，一条报错等于一个坐标；而流水线是绿的，于是所有人都以为上线成功了。

两条判据各一句话：**这一版能不能回去**（产物按版本存放，回滚 = 切指针）、**出事后能不能定位到源码行**（sourcemap 传到该传的地方）。本段装 ⑤（上线）与 ⑥（判定）两环。

读物清单在 [[前端工程学习专项#读什么]]，本页不重复。

## 自测

答不出就是没学：

1. 回滚为什么不能重建？
2. 没传 sourcemap 时，一条报错你拿得到什么、拿不到什么？
3. 灰度扩到 10% 时，你用哪个数说「停」？这个数多久能看到？
4. 流水线全绿，能不能说这次上线成功？如果不能，缺的是哪一层信号？
5. 服务端日志干净，但用户说白屏——错在哪一侧，为什么日志里没有？

## 决定项

| 决定项 | 取值 | 为什么这个不能换 |
|:--|:--|:--|
| 部署目标 | 静态托管，**必须支持多个版本目录共存** | 只支持单目录覆盖的托管做不到「回滚 = 切指针」，这一档就没有判据 |
| 监控 | Sentry 免费额度，或任一支持 sourcemap 上传的方案 | 选哪家不重要，验收是堆栈能还原到源码行 |
| 灰度形态 | **待定**：静态托管本身不做按比例放量，只有版本目录 + 指针切换 | 要真灰度就得换到支持流量切分的平台，或接受「全量切换 + 退得快」 |

**三项都还是待确认状态，第三项是新提出的。** 前两项不定，「用得上」那一档连「做没做对」都判断不了。第三项要接受一个诚实的结论：**在纯静态托管上，⑤ 环的「影响面收得住」只能退化成「退得快」**——这不是配置问题，是部署形态的问题。若这个降级不可接受，就得在 12-12 前改部署目标，而不是到那时才发现做不到。

## 要留下的东西

- [ ] 产物按版本目录 + 内容哈希存放，回滚 = 切指针，现场切一次
- [ ] 按 [[如何选择前端监控方案]] 选定一个方案，把 sourcemap 传到该传的地方，然后从一条真实报错还原到源码行
- [ ] 在监控里为四个层级各指出一条信号（进程 / 200、关键路径成功、错误率、客户端资源加载失败），说明白屏时哪一个先红
- [ ] 在链路图上标出「回滚完成 ≠ 用户拿到旧版本」，指向 [[缓存机制学习专项]] 的事故类型学（发版后旧副本的四类成因——由那边写，本页不重复一份）
