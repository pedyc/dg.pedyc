## 目标

不学会怎样：链路只能靠读配置「证明做对了」，真出一次故障说不清断在哪一段，也拿不出证据。

**判定链**：一次改动走到线上的六道关口。真正会出事的不是单篇笔记里写错的那一行，是接缝——而接缝的特点是**每处配置单独看都对**，所以链按「一次改动走完六道」切，不按工具切。

| 环节 | 判什么 | 判错的代价 |
|:--|:--|:--|
| ① 切改动 | 这次改动能不能单独上线、单独撤回 | 撤回撤不干净，只能连别人的一起退；范围在发布记录里露出来 |
| ② 提交 | 重建出来的这一份，还是不是我在本地验证过的那一份 | CI 全绿、线上却不是同一个东西，「我这边是好的」无从追责 |
| ③ 过门 | 这个改动该不该进主干 | 检查跑了但没设成必过，红了也能合——只跑不设，等于没门 |
| ④ 出产物 | 产物里的每个资源，引用它的页面找不找得到；出事能不能回到源码行 | 白屏、子路径 404、老页面拉旧 chunk 失败，且只落在部分用户身上 |
| ⑤ 上线 | 坏了影响面收得住吗、能不能退回去 | 回滚只能重建，而重建的是最新主干——「回滚」是又发了一版；退回还撞上已写入的缓存 |
| ⑥ 判定 | 用哪个信号说「这次成了」 | 缓存没生效当成功，正常波动当故障，直到用户反馈才发现 |

**链外不学**：

- **清单之外的词不补**。下面 41 条已经按判断缺口列到这个领域的边上，再往外加就是往回走回「把名词铺满」。
- **不往实现里钻**。打包器说到「依赖图怎么来、dev 为什么不打包」为止，不进 AST、插件生命周期、loader 内部。
- **流水线语法不复述第三遍**。[[CI-CD流程]] 与 [[使用Claude-Code自动化CI-CD流水线]] 已有两份实现，[[GitHub Actions]] 只讲平台模型；平台语法的易错点合并成一条。
- **不碰并行架构**。SSR、微前端、Monorepo 都破「单仓、单应用、一个产物」，链在第一环就不成立；它们的位置在 [[前端工程化工具]] 的架构方案节。
- **不做性能优化**。[[前端性能优化]] 负责那一段，[[缓存机制学习专项]] 是它下面另一条专项；本页只到「产物体积能被定位」。

> 与领域页的分工：[[前端工程]] 的里程碑按同一套三段切（构建链路 / 质量闸门 / 交付与观测），本页是它的执行分解——六个环节两两落进三段。**勾选以子专项为准**，领域页按阶段整体打勾——否则同一件事要在两个地方各勾一半，两处必然互相过期。

## 成功标准

> **三档深度，不是三段内容。** 链管「学哪些」，KR 管「学到哪一档」——两条轴正交，所以 KR 不重抄链的每一行。结果填过 / 未过。

| 关键结果 | 判据 | 怎么验 | 结果 |
|:--|:--|:--|:--|
| **讲得出** | 抽到任何一问都能答，且能说出「不这样做会怎样」；只复述配置项算未过 | 三个子专项的自测题各抽 1 道，口述 5 分钟，中途打断追问一次 | |
| **做得出** | 三件东西能在屏幕上打开：一次被拒的提交、一份带两个数字的构建报告、一次切指针的回滚 | 打开终端与面板逐个指，不许口述代替 | |
| **用得上** | 走完六道，且出过一次事故能定位到源码行；说不清断在哪一段算未过 | 复盘一次真实发版，按六道关口倒推 | |

> 未过时「缺的那一块」落成什么：讲不出 → 补一条 atomic，标题即那句「为什么」；做不出 → 缺哪件补哪件，写成 sop 或 atomic；用不上 → 断在哪一环，就是链上缺的那块。

## 读什么

**依据**：
- webpack Concepts（Entry / Modules / Loaders / Mode / Caching）
- Vite Guide（Why Vite / Build / Static Deploy）
- GitHub Actions（workflow syntax / deployment environments / OIDC）
- MDN Server-side 目录，外加一条招聘 JD 的能力项。

**形状**：42 条判断缺口（全部无笔记），20 条已有笔记挂在一旁当入口——链接总数 62，**灰 42（68%）**。这个领域对我是冷的，大部分读物本来就该是灰的；灰链即待写清单，不标「待写」。

### ① 切改动（3 条）

- [[一次 revert 能撤掉什么，取决于那次合并不是一个提交]]——合并提交会把一串别人的改动打包成一次撤销
- [[feature flag 的粒度决定改动能不能单独下线]]——没有开关时，唯一的止血手段就是回滚整个版本
- [[发布记录要能追到哪一层：提交、版本、产物还是时间窗]]——追不到产物这一层，「线上跑的是哪份代码」就永远是个推断

### ② 提交与可复现（7 条）

- [[产物由源码、lockfile、构建配置三者共同决定]]——缺任一项，产物就不可复现，「验证过」也就无法指认
- [[没有 lockfile 时 minor 会自己往上飘]]——代码一行没改产物却变了，答案通常在这里
- [[dist 入不入库，决定线上跑的是谁在哪台机器上构建的]]——两种取舍各有一个说不清的后果
- [[环境变量在构建期被静态替换，不是运行时读取]] → [[环境变量（Vite）]]、[[如何在Vite中配置环境变量？]]
- [[mode 决定的是优化集合，不是正确性]]——「优化没生效」先查 mode，别先改配置
- [[打包器从 entry 出发静态构建依赖图]] → [[Webpack 模块打包的本质是什么？依赖图是如何构建的？]]
- [[dev 期按原生 ESM 直出，build 期才打包]] → [[Vite 是如何实现原生 ESM 加载的？开发时不打包是怎么做到的？]]

### ③ 过门（5 条）

- [[检查存在与检查被强制是两件事]] → [[前端质量闸门]]（按「错误在哪一刻被拦下」分三道，正是这一环）
- [[钩子挂 pre-commit 还是 pre-push，代价不对称]] → [[pre-commit Hook工作流]]、[[Git Hooks]]、[[Husky]]（term）；装法见 [[通过husky+lint-staged进行代码质量防护]]
- [[ESLint 与 tsc 查的东西有交集，为什么两个都要]]——[[ESLint]] 只给了它查什么，没给交集
- [[提交门为什么不跑 E2E]]——慢的那道门没人愿意等，于是被绕过，而绕过没有记录
- [[规范随时写得出来，链路却跑不通]]——先写规范的代价是，规范描述的是想象

### ④ 出产物（12 条）

- [[内容哈希让「名字变了」代替「通知缓存过期」]] → [[Content-Hash]]（term）
- [[入口 chunk 里塞了运行时和清单，业务没改整站缓存也会失效]]——hash 与内容脱钩的典型现场
- [[moduleIds 的确定性决定第三方 chunk 的 hash 能否跨构建复用]]——vendor 缓存白丢的原因
- [[分割边界就是请求边界]] → [[Webpack 的 Code Splitting 和懒加载是如何实现的？]]、[[如何在Vite中进行手动拆包？]]
- [[base 决定的是产物内所有资源 URL 的前缀]]——部署到子路径整站 404 的单一成因
- [[静态服务器怎么处理未知路径，决定了子路由刷新会不会白屏]]——SPA 回退与前端路由是两个约定，得对上
- [[部署后旧页面向旧文件名发起的动态加载会失败]]——新旧产物共存，是「回滚能不能切指针」的前置
- [[缓存头必须与文件名指纹配套]] → [[前端静态资源多级缓存配置规范]]：入口 HTML 协商、带 hash 的强缓存
- [[MIME 由响应头声明，浏览器据此决定要不要执行这份资源]]——脚本被当纯文本返回，现象是白屏而控制台无错
- [[语法降级不等于 API 补齐]]——只改 target 补不了 polyfill，老浏览器该白还是白
- [[loader 只对 test 命中的文件生效]]——新引入的 .scss 能不能直接 import，取决于这里
- [[静态可分析性决定摇树能不能作用到这个模块]] → [[Tree Shaking]]（term）、[[什么是 Tree-shaking？它的前提条件是什么？在哪些情况下会失效？]]

### ⑤ 上线（12 条）

- [[触发事件的语义差异决定这次跑的是哪份代码、能拿到什么凭据]]——push、PR、pull_request_target 是三个权限世界；分支到环境的映射也在这里
- [[job 之间不共享文件系统，产物必须显式传]] → [[GitHub Actions]]（平台模型）
- [[cache 可丢，artifact 是本次交付物]]——混用这两个词，deploy 拿到的是上一次的 dist
- [[needs 决定单测挂了部署会不会照样跑]]——失败不向下传播，门就是画出来的
- [[托管 runner 是预置镜像，运行时通常要自己装]]——「本地能跑 CI 报 command not found」的第一成因
- [[依赖缓存的 key 语义：精确命中与前缀回退是两种结果]]——「这次是命中还是没命中」判不出来，后面全在猜
- [[部署凭据的作用域：secrets 可见性、environment 保护、OIDC 换取]]——取到空 token 时，分不清是权限、作用域还是时机
- [[流水线的三处平台语义：并发组、矩阵与 fail-fast、条件求值时机]]——连推两次线上最终是哪一次的结果，答案在这里
- [[部署原子性：资源与入口 HTML 谁先替换]]——顺序错了，用户拿到半新半旧的页面
- [[preview 命令不是生产服务器]]——「preview 通过了」不是上线判据
- [[灰度扩量按什么判据扩]]——[[灰度]] 只给了定义，没给扩量的门槛与回退线
- [[回滚不只是退代码，还会撞上已写入的数据与缓存]]——第二次故障往往发生在回滚之后

### ⑥ 判定（3 条）

- [[「可用」是分层判据：进程活着、200、关键路径成功、错误率，四者不等价]]——流水线绿了不等于上线成功；口径见 [[前端监控指标采集]]，采集面见 [[前端监控]]
- [[客户端错误不进服务器日志]]——白屏与资源加载失败发生在浏览器侧，服务端日志干净是正常的
- [[回滚要落到一个可执行动作上]]——「回滚」不是名词，是某一条命令或某一次指针切换

### 该读但不读

- **打包器源码与插件生命周期**：能讲清「dev 为什么不打包」就够，再往下是写给写插件的人看的。
- **K8s / 容器编排**：静态站不经过它；等真要自建部署再开另一条链。
- **业务监控与埋点体系**：[[埋点]] 归产品分析，本页只到「错误能定位到源码行」。
- **微前端与 Monorepo 的工程实践**：库里已有四五篇，但都破「单仓单应用一个产物」，读了也用不上。
