## 重写 Husky.md（concept，保持类型）

**原状**：只有四节（核心定义 / 核心价值 / 拦截场景表 / 协同生态 / 关联与延伸），没有 `## 概念：` 二级结构、没有知识图谱五桶、没有适用范围与失效边界；带 `status: active`、`created:`（未登记字段）、uid 缺失、description 61 字（wiki-index 的 `DESC_MAX=30` 会被标点截断）。

**类型判定：仍 concept**。库内同类已分裂：ESLint / Playwright 是 term，Vite / Webpack / pnpm 是 concept。判据用规范那句「术语/定义 → term；概念整合 → concept」——本页的价值在「core.hooksPath 为什么能取代 .git/hooks」这条机制整合，不是定义，所以留 concept，与 Git Hooks 把它列为下位一致。

**主轴**：Husky 是 Git Hooks 的**分发器**，不是钩子框架。它加的不是能力，是一条分发通道。

**事实核查（6 处）**：
- 原文「利用 core.hooksPath 直接绑定项目中的 `.husky` 目录」→ **不准**。v9 指向的是 `.husky/_`（执行器与存根目录），`.husky/` 只是给人写钩子的地方。原文把两层混成一层
- 原文「基于现代 Shell 脚本机制，摒弃繁重配置逻辑」→ 只对一半。v9 删的是 `source .husky/_/husky.sh` 与抽象层，**没删**脆弱点：分发仍绑在 `prepare` 上，失败静默
- 原文缺 `prepare` 这一环——而它才是 Husky 存在的理由（`.git` 不进版本库 → 只能靠 install 后置脚本分发）
- 原文缺「退出码是唯一接口」：husky 不读输出、不判对错，「跑过但什么都没查」与「通过」等价
- 原文缺绕过面：`--no-verify` / `-n`、`HUSKY=0`、`--ignore-scripts`、走 libgit2 的 GUI（最后一条标注需实测）
- 原文缺 `core.hooksPath` 的**独占性**：设上之后 `.git/hooks` 下一切失效（队友自写、别的工具写的），且无提示。这是它与 simple-git-hooks/lefthook 共存不了的根因

**新增**：双泳道 mermaid（装一次 / 每次提交）、三条推论、`关键区别` 只跟「手写 core.hooksPath」比四行（分发 / 依赖 / 入口 / 换方案成本）、失效边界四条、批判三条（统一的是配置不是环境；门槛与绕过的博弈；为一条通道付一份工具链）。

**未写核心命题节**：全库 0 篇钩子相关 atomic（搜过 50-ZETTELCASTEN 标题与正文），硬凑等于造假，与 DevOps 页同一处置。

**待探索用纯文本**（不用 `[[ ]]`）：lint-staged / commitlint / `Q-如何确保代码在本地提交前通过规范校验` 均未立，加链接就是三条新死链。

## 顺手改 SOP 的 v8 时代排查条款

`通过husky+lint-staged进行代码质量防护.md` 的排查清单原第 2 条「是否执行过 `npm run prepare`（`.husky/pre-commit` 必须具备可执行权限）」——**可执行位在 v9 已不是必要条件**（`.husky/_/h` 按文件名转调），照这条排查会把人的时间浪费在 chmod 上。

改法：拆成四条，并把最常见且**静默**的失败提到前面——
1. 有没有 `.git`；2. `git config core.hooksPath` 是否输出 `.husky/_`（为空 = prepare 没跑 = 钩子不存在）；3. 钩子文件是否提交、文件名是否拼对（明确写「可执行位与 shebang 不再是必要条件」）；4. 是否被 `-n` / `HUSKY=0` / GUI 跳过。

并给整条排查加了前置判断：前两条失败时表现为「提交顺利通过」，看起来像没问题——这是与 [[Husky]] 页「分发只发生一次、失败静默」那句对齐。

另把步骤 2 的说明从「生成 `.husky` 目录」改为「生成 `.husky/_` 执行器、一个示例 `.husky/pre-commit`」，与 Husky 页的两层区分保持一致。

**未动**：该 SOP 的 `status: active`、12 位 uid（属存量批次）；「知识图谱」里的「问题来源」桶是旧写法，未改。

## 判定 wiki-log 的读者变迁，AGENTS.md 收口

**起因**：用户问 wiki-log 为何少用。实测不是「用少了」，而是**写端在 10-27 断了**：10-28 至 11-05 有 14 次提交（11-04 单次改 43 个 md，+775/−577），wiki-log 零条目。`.workbuddy/memory/` 从 10-20 起存在——10-20～10-27 是双写期，10-28 起单写。`wiki-sync-state.json` 最后更新停在 10-23。所以三项内部同步里只有 wiki-index 还活着。

**读端本来就没有入口**：全库 31 个 md 提到 wiki-log，其中操作入口类 8 个（schema / ingest / lint / sync / 两个 skill / _skills-overview / AGENTS）**全部是「追加、记录、检查遗漏」，无一处要求先读**。schema 里它只出现在「记录规范」一节，是输出契约而非输入依赖。

**git 替代不了它，但 memory 可以**：commit message 全是 `vault backup`，git 只能答「改了哪些文件」，答不了「为什么」。决策记录的价值是真的，只是载体换了地方——而新载体在 `.workbuddy/`（Obsidian 默认不显示点目录），所以它消失得无声无息。

**决策**（用户选）：承认 `.workbuddy/memory/` 为继任者，只改入口，不恢复双写。理由：双写等于同一事记两处（违反 AGENTS 第 8 条），且靠纪律维持、已经断过一次。

**改动**（`AGENTS.md` 两处）：入口表新增「查某处改动、设计取舍的历史理由」行（memory 10-28 起；wiki-log 冻结于 10-27，grep 关键词或只看最近 20 条，勿通读）；「创建或重写笔记」行去掉已失效的 `同步 wiki-index / wiki-log / sync-state` 列举，改为指向 `build_wiki_index.py`。

**未动**：`01-META/Log/wiki-log.md` 本体（只读区；「冻结」定性目前只在 AGENTS，文件头未标，要标需单独授权）；两个 skill（`obsidian-note-local` 步骤 4、`wiki-sync-local` 全篇）仍声称写 wiki-log——入口已改、执行者未改，是下一步要定的事。
