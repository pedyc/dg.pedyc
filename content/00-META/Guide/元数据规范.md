## 元数据规范

### 通用字段

| 字段 | 用途 | 可选值 | 备注 |
|------|------|--------|------|
| uid | 唯一标识 | 时间戳 | 自动生成 |
| title | 笔记标题 | - | - |
| aliases | 别名 | - | 方便搜索 |
| description | 描述 | - | - |
| tags | 标签 | `#父/子` 格式 | 横向分类 |
| status | 笔记状态 | 见下方 | 生命周期 |
| content-type | 内容分类 | 见下方 | 决定使用模板 |
| category | 横向分类 | learning / work / life / hobby / blog | - |
| published | 发布状态 | true / false | 博客文章专用 |
| up | 父级链接 | [[MOC/概念]] | 知识网络 |
| date-created | 创建时间 | 日期 | 工具自动 |
| date-modified | 修改时间 | 日期 | 工具自动 |

### status：笔记状态

> 流转方向：**单项不可逆**（atomic 例外：永不复用）

#### 基础定义

| 状态 | 含义 | 典型触发条件 |
|:---|:---|:---|
| fleeting | 闪念/草稿 | 刚捕获的原始想法 |
| cultivating | 培育中 | 持续补充内容/链接 |
| active | 活跃 | 作为主力引用，被持续维护 |
| completed | 已完成 | 内容成熟但不再主动维护（仍有效） |
| archived | 已归档 | 终态，不再维护 |

#### 按 content-type 的归档语义

| content-type | completed 语义 | 归档触发条件 |
|:---|:---|:---|
| **atomic** | 洞察完成 | ⚠️ **几乎不归档**——洞察是资产，永不过期 |
| **concept** | 概念理解完成 | 版本过时（ES2026 → ES2027）但笔记未更新 |
| **term** | 定义完成 | 定义被证伪 或 被新版本替代 |
| **roadmap** | 版本覆盖完成 | 新版本已发布但笔记未更新 |
| **sop** | 流程验证完成 | 技术栈变更导致流程失效 |
| **area** | 领域探索完成 | 放弃该领域的学习/关注 |
| **moc** | 索引整理完成 | 主题已放弃，无导航价值 |

#### 归档的两层机制

| 机制 | 适用场景 | 操作 |
|:---|:---|:---|
| `status: archived` | 笔记完成/成熟但仍有效，不想维护 | 原目录不动，仅改 status |
| **移入 50-ARCHIVE/** | 明确过时、错误、或长期孤立（入链=0）且无保留价值 | 物理移动到归档目录 |

#### 归档判断决策树

```bash
笔记不更新了？
├── 内容完善 + 仍被引用 + 版本未过时
│   └── → status: completed（原目录不动）
├── 版本已更新但笔记未更新
│   └── → status: archived 或 移入 50-ARCHIVE/
├── 入链=0 + 从未被引用 + 无孤立价值
│   └── → 移入 50-ARCHIVE/
└── atomic 类型
    └── → 永不归档（洞察是资产）
```

> [!warning]
> **Zettelkasten 不删除原则**：atomic 笔记永不被删除；其他类型笔记过时/孤立时归档而非删除。

### content-type：内容分类

> **特定笔记类型（重要）**

| 分类 | 类型 | 目录 | 定义 | 示例 |
|------|------|------|------|------|
| 面向 **PARA** | `project` | 10-PROJECTS | 项目，有明确目标和截止日期 | P- 求职前端岗位 |
| 面向 **PARA** | `area` | 20-AREAS | 领域，需持续关注的范围 | A- 人工智能 |
| 面向 **主题** | `article` | 60-BLOGS | 长篇博客/主题文章 | 博客文章 |
| 面向 **时间** | `diary` | 90-DIARY | 时间序列记录 | 日记、周报 |
| 面向 **知识管理** | `atomic` | 30-ZETTELKASTEN | 永久笔记，单一洞察/观点 | " 闭包的本质是…" |
| 面向 **知识管理** | `concept` | 40-RESOURCES | 概念集合，解释 " 为什么 " 或 " 如何运作 " | 闭包（概念总览） |
| 面向 **知识管理** | `moc` | 40-RESOURCES | 内容地图，索引多个相关笔记 | 导航页、知识地图 |
| 面向 **知识管理** | `sop` | 40-RESOURCES | 标准流程，明确步骤的操作指南 | 部署流程 |
| 面向 **知识管理** | `question` | 40-RESOURCES | 开放性问题，探索性思考 | Q- 如何学习编程 |
| 面向 **知识管理** | `term` | 40-RESOURCES | 术语解释（来自文献/外部） | HTTP 协议 |
| 面向 **知识管理** | `comparison` | 40-RESOURCES | 对比分析，跨越多个概念 | A vs B |
| 面向 **知识管理** | `record` | 40-RESOURCES | 事件记录，时间线 + 背景 + 影响 + 引申 | 俄乌冲突 |
| 面向 **知识管理** | `roadmap` | 40-RESOURCES | 版本演进、时间线、发展历程 | React 版本演进 |

> [!tip]
> - **特定型**（由物理位置决定）：`project` → 10-PROJECTS，`area` → 20-AREAS，`diary` → 90-DIARY，`article` → 60-BLOGS
> - **通用型**（由 content-type 决定）：atomic → 30-ZETTELKASTEN，其他 → 40-RESOURCES

### atomic vs concept

| 维度 | atomic（原子笔记） | concept（概念笔记） |
|------|-------------------|-------------------|
| **定位** | 单一洞察/观点（陈述句） | 概念总览与整合 |
| **content-type** | `atomic` | `concept` |
| **目录** | 30-ZETTELKASTEN | 40-RESOURCES |
| **文件名** | 陈述句（如 " 闭包的本质是…"） | 纯标题（如 " 闭包 "） |
| **aliases 前缀** | 无特定规则 | `C-` 前缀 |
| **结构** | 一句话观点 + 论据 + 简单关联 | 核心定义 + 命题 + 机制 + 图谱 |
| **写作负担** | 轻，随时可写 | 重，需要系统整理 |
| **升级路径** | atomic → concept | - |
| **引用方式** | 引用 atomic 或 concept 都可以 | - |

**使用建议：**
- 先写 atomic，记录单一洞察
- 随着相关 atomic 增多，创建 concept 作为索引入口
- 其他笔记引用时，无需区分 atomic/concept，均可直接引用

### area vs concept vs moc

| 维度 | area（领域） | concept（概念） | moc（地图） |
|:--- |:--- |:--- |:--- |
| **定位** | 责任范围，需持续关注 | 知识性，理解即可 | 内容索引，导航入口 |
| **content-type** | `area` | `concept` | `moc` |
| **目录** | 20-AREAS/ | 40-RESOURCES/ | 40-RESOURCES/ |
| **核心特征** | 长期目标 + 关键领域 | 核心命题 + 知识图谱 | 链接集合 |
| **维护** | 需要持续更新目标/领域 | 知识成熟后整理 | 动态维护链接 |
| **判断标准** | 需要设定学习目标？ | 纯知识性理解？ | 需要索引导航？ |

**区分原则：**

- **area**：PARA 的 "A"——需要设定长期目标、持续关注的**责任范围**
	- 核心必须有 " 长期目标 "（愿景 + 里程碑）
	- 例：前端开发、人工智能、健康管理、个人成长
- **concept**：纯知识性概念，理解后即可——**不设目标**
	- 例：闭包、HTTP、浏览器渲染流程
- **moc**：作为导航入口，索引多个相关笔记——**不设目标**
	- 例：前端知识地图、方法论汇总、Web 安全策略索引

**进阶判断：**
- 如果只是 " 了解某技术 " → concept 或 moc
- 如果需要 " 深入学习并应用到项目 " → area

**Area vs Topic（子主题）的区分：**

子目录下的笔记可能是 Area 或 Topic：
- **Area**（需设定目标）：`A-人工智能`、`A-健康管理`
- **Topic**（仅做笔记索引）：`A-前端/Angular.md`、`A-前端/React.md`

Topic 笔记特点：有大量子链接但没有 " 长期目标 " 章节。

**目录结构示例：**

```bash
20-AREAS/
├── A-人工智能/           ← Area（独立责任领域）
│   ├── A-人工智能.md    ← Area 主体，有长期目标
│   └── MOC-xxx.md       ← 该领域的 MOC
├── A-前端/              ← Area（责任领域）
│   ├── 前端工程.md     ← Topic（框架聚合，无目标）
│   ├── Angular.md       ← Topic
│   ├── React.md         ← Topic
│   └── Vue.md           ← Topic
└── A-Web安全/           ← Area（独立责任领域）
    ├── A-Web安全.md     ← Area 主体，有长期目标
    ├── Web安全策略.md   ← MOC
    └── Web安全问题.md   ← MOC
```
