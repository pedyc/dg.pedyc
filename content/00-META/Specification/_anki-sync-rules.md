## Anki 集成工作流

本规则定义 Obsidian 知识库与 Anki 的打通方式：哪些笔记生成卡片、卡片如何格式、如何同步。**核心判断：Anki 只奖励「有稳定正确答案」的知识**，卡片必须遵循 [[知识卡片制作原则]]（最小信息、主动回忆、具体化）。

### 核心原则

- **Anki 测试「有稳定正确答案的事实」，不测试「未收敛的探索」**
- **卡片挂在收敛产物上，不挂在发散容器上**
- **卡片随源笔记同步，不手动维护第二份内容**

### 卡片来源规则

| content-type | 是否生成卡片 | 理由 | 卡片形态 |
|:--- |:--- |:--- |:--- |
| `atomic` | ✅ 主候选 | 单一洞察、永不修改/归档，卡片不会漂移 | 陈述句 → recall 卡（"X 的本质是什么？"） |
| `term` | ✅ 生成 | 术语定义是经典闪卡素材，客观稳定 | 定义卡 / cloze 填空 |
| `question` | ⛔ 不直接生成 | 未收敛，无稳定答案可测 | 仅在收敛后生成（见下） |
| `concept` | ⛔ 不直接生成 | 聚合型，一张卡装不下 | 核心命题可拆成 atomic 后生成 |
| `sop` | ⛔ 不直接生成 | 流程型，多步骤 | 关键步骤/边界可拆成卡 |
| `moc` / `area` / `project` / `article` / `diary` / `comparison` | ⛔ 不生成 | 索引/导航/时序类，非记忆单元 | — |

### question 收敛规则

question 不直接同步，收敛后才进 Anki：

- question 验证出明确答案 → 把「答案」做成卡，不同步整个 question 笔记
- question 收敛为 SOP → SOP 的关键步骤/边界条件拆成卡
- 关联规范见 [[_笔记类型规范]] 的 `SOP ↔ Question 关联规则`

### 卡片格式约定

使用 obsidian-to-anki-plugin 的 `#card` 语法，在笔记正文内联标记：

```markdown
<!-- 基础卡：问题换行 #card 答案 -->
Vue 3 的响应式基于什么 API 实现？ #card
Proxy（替代 Vue 2 的 defineProperty）

<!-- 内联卡：用分隔符 -->
`Proxy #card :: 响应式系统的核心实现`

<!-- cloze 填空：适合 term -->
Vue 3 的响应式基于 {{c1::Proxy}} 实现。
```

**格式约束**：
- 一张笔记 ≤ 3 张卡（避免一卡多知识点，遵循「最小信息原则」）
- 卡面引用具体概念，不用"列出所有…"这类宽泛问题
- 卡与卡之间不靠 `<!-- SR:… -->` 注释区分，所有卡均由 `#card` 标记生成（`#card` 出现一次生成一张卡，同笔记多卡用多个标记）
- 卡片内容优先引用源笔记已存在的概念链接，不额外复制大段上下文

### Deck 分类原则

**Anki deck 是调度容器（决定卡片何时复习），不是知识索引**。知识库的领域/主题分类（PARA、MOC、content-type）已由 Obsidian 承担，不要复制进 Anki。

- ✅ **按「复习用途」分**：少量 deck + 主题子 deck（用 `::` 分层），如 `前端面试::JS基础`
- ⛔ **不要按「知识目录」映射**：`10-PROJECTS/P-求职/…`、`MOC-前端面试真题库/…` 这类目录结构对「何时复习某张卡」没有调度价值
- **deck 数量原则**：主 deck 尽量少（控制间隔重复调度节奏），主题细分交给子 deck

### 同步工作流

1. **标记**：LLM 在生成/更新笔记时，对符合卡片来源规则的笔记添加 `#card` 标记
2. **同步**：用户或 LLM 在 Obsidian 中运行 obsidian-to-anki-plugin，将标记的卡片推送到 Anki
3. **维护**：源笔记变更 → 重新同步覆盖卡片；源笔记归档 → 卡片随笔记移除或保留在 Anki 原 deck
4. **wiki-log**：不单独记录卡片同步（属于系统维护，不记录）；若新创建了 atomic/term 源笔记，按常规 ingest 记录

### 与现有子系统关系

- **卡片来源依赖** [[_笔记类型规范]] — content-type 决定能否生成卡片
- **卡片质量依赖** [[知识卡片制作原则]] — 卡片格式黄金原则
- **源笔记维护依赖** `obsidian-note-local` — 创建/更新笔记时顺带处理卡片标记

### 实践示例：前端面试复习

**场景**：针对求职面试的复习卡。面试题本质是 question 的收敛态（有标准答案），恰好符合「question 收敛后生成」规则。

**Deck 结构**：

```text
前端面试                    ← 一个大 deck（掌握复习节奏）
├── 前端面试::JS基础
├── 前端面试::框架
├── 前端面试::网络与浏览器
└── 前端面试::手写代码       ← 单独子 deck（见下）
```

**卡片优先级**（参考 [[前端面试知识清单]] 的 70/20/10 精力分配）：

| 卡片类型 | 对应知识 | 示例 | 优先级 |
|:--- |:--- |:--- |:--- |
| 概念定义卡（term 类） | 高频名词 | 闭包、事件循环、this 绑定、HTTP 缓存、跨域、XSS/CSRF | ⭐⭐⭐⭐⭐ 先做 |
| 原理 recall 卡（atomic 类） | "为什么" | 为什么 Vue 用 Proxy？列表为什么需要 key？ | ⭐⭐⭐⭐⭐ |
| 对比卡 | 易混淆区分 | Vue vs React、HTTP/1 vs HTTP/2、let vs const | ⭐⭐⭐⭐ |
| 手写代码卡 | 高频手写 | 防抖/节流、深拷贝、Promise、数组去重、call/apply/bind | ⭐⭐⭐⭐ 单独子 deck |
| 安全/网络题 | 面试占比 20% | 浏览器渲染过程、事件循环、CSP | ⭐⭐⭐ |

**不做的**：
- 长题单/面经记录（未收敛的 question）——Anki 测单点事实，整篇面经测不了
- 项目 STAR 案例——叙事能力 Anki 练不了，用模拟面试练
- 加分项（Three.js、Node、可视化）——按知识清单建议先砍掉

### 边界

- **不做**：不自动同步卡片到 Anki（需用户在 Obsidian 手动触发插件），不做双向回写
- **例外**：用户明确要求某笔记生成卡片，即使类型不在上表，按用户要求执行
