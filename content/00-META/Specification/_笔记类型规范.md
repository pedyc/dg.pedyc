## 笔记类型规范

本文件是本库所有 content-type 的**唯一可信源**，定义每种笔记类型的定位、目录、命名规则、使用场景和 Wiki 层内联规则。

---

### 一、content-type 总览

| 类型 | content-type | 目录 | aliases 前缀 | 文件名示例 | 定义 |
|------|-------------|------|-------------|-----------|------|
| 原子笔记 | `atomic` | `30-ZETTELKASTEN/` | 无 | `闭包的本质是…md` | 一句话洞察，陈述句观点 |
| 概念笔记 | `concept` | `40-RESOURCES/` | `C-` | `闭包.md` | 概念整合与系统理解 |
| 术语笔记 | `term` | `40-RESOURCES/` | `T-` | `TCP.md` | 术语客观定义 |
| 标准流程 | `sop` | `40-RESOURCES/` | `SOP-` | `周回顾.md` | 标准化操作流程 |
| 问题笔记 | `question` | `40-RESOURCES/` | `Q-` | `如何学习编程.md` | 开放性问题探索 |
| 比较笔记 | `comparison` | `40-RESOURCES/` | `VS-` | `React vs Vue.md` | 对比分析 |
| 事件记录 | `record` | `40-RESOURCES/` | `R-` | `俄乌冲突.md` | 事件时间线记录 |
| 演进路线 | `roadmap` | `40-RESOURCES/` | `R-` | `Angular版本演进.md` | 版本演进时间线 |
| 人物笔记 | `person` | `40-RESOURCES/` | `R-` | `爱因斯坦.md` | 人物生平与思想记录 |
| 索引地图 | `moc` | `40-RESOURCES/` | `MOC-` | `前端知识地图.md` | 领域入口与索引 |
| 领域笔记 | `area` | `20-AREAS/` | `A-` | `人工智能.md` | 责任范围与长期目标 |
| 项目笔记 | `project` | `10-PROJECTS/` | `P-` | `求职.md` | 有明确截止日期的任务 |
| 博客文章 | `article` | `60-BLOGS/` | 无 | `如何学习React.md` | 长篇主题文章 |
| 日记 | `diary` | `90-DIARY/` | 无 | `2026-07-17.md` | 时间序列记录 |

### 二、各类型详解

#### atomic（原子笔记）

| 字段 | 值 |
|------|-----|
| content-type | `atomic` |
| 目录 | `30-ZETTELKASTEN/` |
| aliases 前缀 | 无 |
| 文件名 | **陈述句**，如"闭包的本质是函数保存了其定义时的作用域链" |
| 模板 | `template_atomic.md` |

**定位**：source of truth，单一洞察/观点。是你对某个问题的独立理解。

**核心特征**：
- 文件名必须是陈述句——表达一个明确观点
- content-type 不写 aliases 前缀
- 写作负担轻，随时可写
- **永不归档，永不删除**——洞察是资产

**升级路径**：多个相关 atomic → 创建 concept 作为索引入口

#### concept（概念笔记）

| 字段 | 值 |
|------|-----|
| content-type | `concept` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `C-` |
| 文件名 | 纯标题，如"闭包" |
| 模板 | `template_concept.md` |

**定位**：概念总览与整合串联，天然成为索引入口。解释"为什么"或"如何运作"。

**核心特征**：
- 核心是"核心命题"——用陈述句表达对概念的洞见
- 核心命题应引用 atomic 笔记（陈述句观点），而非 term（术语定义）
- 包含运行机制可视化（Mermaid）
- 提供 FAQ 链接 Question 笔记
- 提供 SOP 链接建立"理解→实践"的桥梁

#### term（术语笔记）

| 字段 | 值 |
|------|-----|
| content-type | `term` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `T-` |
| 文件名 | 术语名，如"TCP" |
| 模板 | `template_term.md` |

**定位**：术语客观定义（来自文献/外部），被 concept 引用。

**核心特征**：
- 客观中立，不包含个人观点
- 包含来源出处和相关术语
- 随所属 concept 更新，不需要独立维护
- aliases 用 `T-` 前缀

#### sop（标准流程）

| 字段 | 值 |
|------|-----|
| content-type | `sop` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `SOP-` |
| 文件名 | 动宾结构，如"使用Claude Code自动化CI/CD流水线" |
| 模板 | `template_sop.md` |

**定位**：已验证的标准操作流程，明确步骤、边界条件、常见坑点。

**核心特征**：
- 核心是标准化——目标 + 实现步骤 + 实践示例
- 包含边界条件——适用场景 + 常见坑点
- 使用 Mermaid 流程图可视化流程

**内联规则**：
- SOP 创建后，在 `wiki-index.md` 的 SOPs 章节添加条目
- 如 SOP 属于某 area，在该 area 页面的 SOPs 小节添加链接
- 如 SOP 与某 concept 相关，在该 concept 的知识图谱中添加引用

**与 Question 的关系**：SOP 是 Question 的"收敛态"。Question 提出问题和多种方案，经过实践验证后集成为 SOP（详见第五节类型对比）。

#### question（问题笔记）

| 字段 | 值 |
|------|-----|
| content-type | `question` |
| 目录 | 混合（30/40-RESOURCES） |
| aliases 前缀 | `Q-` |
| 文件名 | 问题描述，如"如何高效使用 Claude Code" |
| 模板 | `template_question.md` |

**定位**：开放性问题探索，与 SOP 互补——SOP 是已验证的标准流程，Q 是待探索的问题。

**核心特征**：
- 包含问题背景、现有答案、探索路径、待验证点
- 不需要有最终答案，保持"待探索"状态
- 被 area/moc 的 FAQ 引用

**内联规则**：
- Question 创建后，在父 area 或 moc 的 FAQ 节添加引用
- Question 验证后可收敛为 SOP（更新 Question 的知识图谱标注 `→ 已验证方案：[[SOP-XXX]]`）

#### comparison（比较笔记）

| 字段 | 值 |
|------|-----|
| content-type | `comparison` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `VS-` |
| 文件名 | "A vs B"格式 |
| 模板 | `template_comp.md` |

**定位**：对比分析，跨越多个概念。

**核心特征**：
- 包含对比维度、双方特性、适用场景
- 引用相关概念或 term

**内联规则**：
- 如比较"A vs B"，在 A 和 B 的 concept 页面的"并列概念"或"关键区别"中添加引用

#### record（事件记录）

| 字段 | 值 |
|------|-----|
| content-type | `record` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `R-` |
| 文件名 | 事件名 |
| 模板 | `template_record.md` |

**定位**：客观记录事件，附带观点。

**核心特征**：
- 特有字段：`date`（事件日期）、`location`（地点）、`participants`（参与者）
- 包含时间线、背景、影响、引申

#### roadmap（演进路线）

| 字段 | 值 |
|------|-----|
| content-type | `roadmap` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `R-`（与 record 共享，语义不冲突） |
| 文件名 | "xxx版本演进" |
| 模板 | `template_roadmap.md` |

**定位**：线性演进路线图，记录版本迭代或技术发展时间线。

#### person（人物笔记）

| 字段 | 值 |
|------|-----|
| content-type | `person` |
| 目录 | `40-RESOURCES/` |
| aliases 前缀 | `R-`（与 record/roadmap 共享） |
| 文件名 | 纯人名，如"爱因斯坦" |
| 模板 | `template_person.md` |

**定位**：客观记录人物生平，附带思想观点提炼。与 record 的区别：record 记录事件，person 记录人物。

**核心特征**：
- 特有字段：`birth`、`death`、`nationality`、`occupation`
- 包含人物卡片、人生时间线、主要成就、思想与观点、代表作品、关系网络
- 思想观点应链接 atomic/concept 笔记，作为 wiki 层入口

**内联规则**：
- Person 默认挂载到主题 MOC（列表末尾），仅当无对应 MOC 且属于 area 责任核心时挂 area"人物"小节
- 如人物思想与某 concept 相关，在该 concept 的知识图谱中添加引用

#### moc（索引地图）

| 字段 | 值 |
|------|-----|
| content-type | `moc` |
| 目录 | `40-RESOURCES/`（也可在 `20-AREAS/` 下） |
| aliases 前缀 | `MOC-` |
| 文件名 | 纯标题，如"前端知识地图" |
| 模板 | `template_moc.md` |

**定位**：area 的子级索引，串联同领域多个 concept/sop/term。

**核心特征**：
- 不设长期目标（与 area 的本质区别）
- 只做索引，不做消化
- 包含链接集合、核心原则、待补充清单

#### area（领域笔记）

| 字段 | 值 |
|------|-----|
| content-type | `area` |
| 目录 | `20-AREAS/` |
| aliases 前缀 | `A-` |
| 文件名 | 纯标题，如"人工智能" |
| 模板 | `template_area.md` |

**定位**：PARA 的"A"——责任范围，需持续关注。核心必须有"长期目标"（愿景 + 里程碑）。

**核心特征**：
- 包含长期目标、核心心智模型、执行系统、知识网络、领域健康度
- 需要设定学习目标和持续关注
- 与 moc 区别：area 有目标，moc 无目标

#### project（项目笔记）

| 字段 | 值 |
|------|-----|
| content-type | `project` |
| 目录 | `10-PROJECTS/` |
| aliases 前缀 | `P-` |
| 文件名 | 纯标题 |
| 模板 | `template_project.md` |

**定位**：PARA 的"P"——有明确目标和截止日期的任务。

**特有字段**：`consequence`、`urgency`、`energy-type`、`quadrant`、`expire`

#### article（博客文章）

| 字段 | 值 |
|------|-----|
| content-type | `article` |
| 目录 | `60-BLOGS/` |
| aliases 前缀 | 无 |
| 文件名 | 纯标题 |
| 模板 | `template_article.md` |

**特有字段**：`published: true/false`、`category: blog`

#### diary（日记）

| 字段 | 值 |
|------|-----|
| content-type | `diary` |
| 目录 | `90-DIARY/` |
| aliases 前缀 | 无 |
| 文件名 | 日期格式 |
| 模板 | `template_diary.md` |

**定位**：时间序列记录。wiki-index 不收录，由用户自行查阅。

### 三、文件命名与 aliases 规则

#### 核心原则

**前缀仅用于 aliases 检索，WikiLink 引用使用纯标题。**

```markdown
<!-- 正确：纯标题引用 -->
[[闭包]] 而不是引 [[C-闭包]]

<!-- aliases 字段放前缀 -->
aliases: [C-闭包]
```

#### aliases 前缀速查

| 前缀 | content-type | aliases 示例 |
|------|-------------|--------------|
| `A-` | area | `A-人工智能` |
| `P-` | project | `P-求职` |
| `Q-` | question | `Q-如何学习编程` |
| `MOC-` | moc | `MOC-前端知识地图` |
| `SOP-` | sop | `SOP-周回顾` |
| `T-` | term | `T-TCP` |
| `C-` | concept | `C-闭包` |
| `VS-` | comparison | `VS-React vs Vue` |
| `R-` | record / roadmap / person | `R-俄乌冲突` / `R-Angular-版本演进` / `R-爱因斯坦` |
| （无） | atomic / article / diary | — |

#### 子主题命名规则

当一个笔记是另一个笔记的子主题时，在 aliases 中添加父级前缀，避免命名混淆：

| 场景 | aliases 示例 |
|:---|:---|
| Fiber 是 React 的子概念 | `["C-React-Fiber", "Fiber"]` |
| Fiber 是 React 的子术语 | `["T-React-Fiber", "Fiber"]` |
| 场景图结构 是 ThreeJS 的子概念 | `["C-ThreeJS-场景图结构", "场景图结构"]` |
| 虚拟头节点 是 链表 的子术语 | `["T-链表-虚拟头节点", "虚拟头节点"]` |

**命名格式**：`{类型前缀}-{父概念}-{子概念}`

**判断标准**：
- 子概念名称通用/易混淆（如 Fiber）→ 必须加父级前缀
- 子概念名称独特/仅限某领域 → 建议加父级前缀
- 子概念是 atomic（陈述句）→ 不需要加前缀

### 四、类型对比

#### atomic vs concept vs term

| 维度 | atomic | concept | term |
|------|--------|---------|------|
| **定位** | 单一洞察/观点 | 概念总览与整合 | 术语客观定义 |
| **content-type** | `atomic` | `concept` | `term` |
| **目录** | 30-ZETTELKASTEN | 40-RESOURCES | 40-RESOURCES |
| **文件名** | 陈述句 | 纯标题 | 纯标题 |
| **aliases 前缀** | 无 | `C-` | `T-` |
| **结构** | 一句话观点+论据+关联 | 定义+命题+机制+图谱 | 定义+来源+相关术语 |
| **写作负担** | 轻 | 重 | 轻 |
| **升级路径** | atomic → concept | — | term → concept 的组成部分 |
| **是否可归档** | 永不 | 版本过时可归档 | 定义被证伪可归档 |

**判断标准**：
- 想表达"洞察/观点" → atomic
- 想表达"术语/定义" → term
- 想做"概念整合和索引" → concept

#### area vs concept vs moc

| 维度 | area | concept | moc |
|:--- |:--- |:--- |:--- |
| **定位** | 责任范围，需持续关注 | 知识性，理解即可 | 内容索引，导航入口 |
| **content-type** | `area` | `concept` | `moc` |
| **目录** | 20-AREAS/ | 40-RESOURCES/ | 40-RESOURCES/ |
| **核心特征** | 长期目标 + 关键领域 | 核心命题 + 知识图谱 | 链接集合 |
| **维护频率** | 需持续更新目标/领域 | 知识成熟后整理 | 动态维护链接 |
| **是否设目标** | ✅ 必须有长期目标 | ❌ | ❌ |

**进阶判断**：
- 如果只是"了解某技术" → concept 或 moc
- 如果需要"深入学习并应用到项目" → area

#### sop vs question（SOP-Q 关联）

| 维度 | sop | question |
|:--- |:--- |:--- |
| **定位** | 已验证的标准流程 | 待探索的开放性问题 |
| **content-type** | `sop` | `question` |
| **核心产出** | 明确的步骤序列和检查清单 | 探索路径、备选方案、待验证点 |
| **状态** | 已验证、可重复 | 待探索、可变化 |
| **与对方的关系** | Question 的收敛态 | SOP 的发散前身 |

**SOP ↔ Question 关联规则**：
- Question 提出问题和多种方案 → 经实践验证后收敛为 SOP
- SOP 的 FAQ 中引用关联的 Question：`- [[Q-XXX]] — 此 SOP 解决的问题来源`
- Question 的知识图谱中标注已验证方案：`- → 已验证方案：[[SOP-XXX]]`
- 更新后的 Question 可保留"已验证"标记，亦可归档（避免已解决的 Question 仍然活跃）

**示例**：

```markdown
<!-- SOP 中的 FAQ 引用 Question -->
### FAQ
- [[Q-如何高效使用 Claude Code？]] — 此 SOP 解决的问题来源

<!-- Question 中的标注 -->
### 知识图谱
- → 已验证方案：[[SOP-使用Claude-Code自动化CI-CD流水线]]
```

### 五、状态流转

#### 状态定义

| 状态 | 含义 | 典型触发条件 |
|:---|:---|:---|
| `fleeting` | 闪念/草稿 | 刚捕获的原始想法 |
| `cultivating` | 培育中 | 持续补充内容/链接 |
| `active` | 活跃 | 作为主力引用，被持续维护 |
| `completed` | 已完成 | 内容成熟但不再主动维护（仍有效） |
| `archived` | 已归档 | 终态，不再维护 |

**流转方向**：`fleeting → cultivating → active → completed → archived`（单项不可逆）

#### 按 content-type 的归档语义

| content-type | completed 语义 | 归档触发条件 |
|:---|:---|:---|
| **atomic** | 洞察完成 | ⚠️ **几乎不归档**——洞察是资产，永不过期 |
| **concept** | 概念理解完成 | 版本过时但笔记未更新 |
| **term** | 定义完成 | 定义被证伪或被新版本替代 |
| **roadmap** | 版本覆盖完成 | 新版本已发布但笔记未更新 |
| **sop** | 流程验证完成 | 技术栈变更导致流程失效 |
| **area** | 领域探索完成 | 放弃该领域的学习/关注 |
| **moc** | 索引整理完成 | 主题已放弃，无导航价值 |

#### 归档的两层机制

| 机制 | 适用场景 | 操作 |
|:---|:---|:---|
| `status: archived` | 笔记仍有效但不想维护 | 原目录不动，仅改 status |
| **移入 50-ARCHIVE/** | 明确过时/错误/长期孤立且无保留价值 | 物理移动到归档目录 |

### 六、目录位置速查

```bash
content/
├── 00-META/           # 系统元数据（规范、架构、索引）
├── 10-PROJECTS/       # project（面向 PARA）
├── 20-AREAS/          # area（面向 PARA）+ 子目录中的 topic/MOC
├── 30-ZETTELKASTEN/   # atomic
├── 40-RESOURCES/      # concept, moc, sop, term, question, comparison, record, roadmap, person
├── 50-ARCHIVE/        # 归档内容
├── 60-BLOGS/          # article
├── 90-DIARY/          # diary
└── 99-ASSETS/         # 附件资源
```

| 目录 | 存放 content-type |
|------|-----------------|
| 10-PROJECTS | `project` |
| 20-AREAS | `area` |
| 30-ZETTELKASTEN | `atomic`（唯一） |
| 40-RESOURCES | `concept`, `moc`, `sop`, `question`, `term`, `comparison`, `record`, `roadmap`, `person` |
| 60-BLOGS | `article` |
| 90-DIARY | `diary` |

### 七、Wiki 层内联规则速查

| content-type | 父级引用 | wiki-index 位置 | ingest 需求 |
|-------------|---------|----------------|-------------|
| atomic | concept | — | ✅ atomic → concept |
| concept | area | Concepts 章节 | ❌ |
| sop | area/concept | SOPs 章节 | ❌ |
| term | concept | Terms 章节 | ❌ |
| comparison | 相关 concept | Comparisons 章节 | ❌ |
| record | 时政/政治经济 area | Records 章节 | ❌ |
| moc | area | MOCs 章节 | ❌ |
| question | area/moc | 关联 area 的 FAQ | ❌ |
| roadmap | concept/area | Concepts 章节 | ❌ |
| person | moc（默认）/area | 关联 MOC 列表末尾 / area 人物小节 | ❌ |
