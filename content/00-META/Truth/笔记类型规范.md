## 各类型定位

| content-type | 定位（一句话） |
|-------------|--------------|
| `atomic` | source of truth，单一洞察/观点，永不归档、永不删除 |
| `concept` | 概念总览与整合，解释「为什么」或「如何运作」（有「核心命题」段，是 atomic 的原料库） |
| `term` | 术语客观定义（来自文献），被 concept 引用 |
| `sop` | 已验证的标准流程，Question 的「收敛态」 |
| `question` | 开放性问题探索，SOP 的「发散前身」 |
| `comparison` | 对比分析，跨越多个概念 |
| `record` | 客观记录事件，附带观点 |
| `roadmap` | 线性演进路线图，版本迭代/技术发展时间线 |
| `person` | 客观记录人物生平，附带思想观点提炼 |
| `moc` | 领域入口与索引，只做索引不做消化（「消化禁令」见下：一旦写原理就下沉为 concept） |
| `area` | 责任范围，需持续关注，必须有长期目标 |
| `project` | 有明确目标和截止日期的任务 |
| `article` | 长篇主题文章 |
| `diary` | 时间序列记录 |

## atomic 与 Anki 记忆卡（Yanki 双用途）

> `atomic` 的核心是「标题即陈述句观点」，这一结构天然适配 Anki 的 Cloze（填空）卡片。通过 yanki-obsidian 插件，同一篇 atomic 笔记**既是 Zettelkasten 的可引用观点，又是 Anki 的复习卡片**，零额外制卡成本。

- **识别规则**：用 `~~双波浪线~~` 挖掉观点句中的**关键机制词**（1~2 个），yanki 识别为 Cloze 卡片；`~~删除线~~` 在 Obsidian 中仍渲染为删除线，不影响阅读。
- **挖空范围**：只挖「关键词」，不挖整句，聚焦主动回忆的锚点。
- **禁忌**：正文中不要出现孤立的 `---` 分隔符，否则 yanki 会误判为 Basic 卡片（正面/背面两段式）。
- **字段关系**：`tags` 会同步为 Anki 标签；`noteId` 由 yanki 自动添加，**勿手动删除**（删除会导致复习进度丢失）。
- **论据/示例与关联**：这些属于「论证与连接」，进入卡片背面或仅作上下文，**不参与挖空**；挖空只针对观点句本身。

## 断链与 atomic 提炼

> [!note] 断链 = 尚未掌握完全的知识
> 知识库中的 `[[断链]]`（被引用但对应文件不存在的标题）**不是错误**，而是一个「待办标记」——它代表「我认可了这个洞见、并在别处引用了它，但还没把它提炼成独立的 atomic 掌握」。
>
> - **断链是知识治理的信号**：看到断链，意味着这里有「悬而未决」的知识，值得提炼成 atomic 来消化。
> - **提炼断链 = 补全知识**：从断链标题创建 atomic，本质是「消化一个已被认可的洞见」，批量创建 atomic 只是副产品。
> - **优先级**：断链标题（已被 concept 认可）> 误放的 atomic（已写好但位置错）> 裸陈述句（尚未成文的洞见）。

### 断链的三类判断

| 现象 | 含义 | 处理 |
|------|------|------|
| 标题在全库搜不到同名文件，只在 concept 的 `[[...]]` 里被引用 | **断链**（洞见被认可但未成文） | 提炼成 atomic |
| 标题在 30-RESOURCES 有同名文件，但 content-type 是 atomic | **误放**（atomic 写好了但位置错） | 移到 50-ZETTELCASTEN |
| 标题在 30-RESOURCES 有同名文件，content-type 也正确 | 正常引用（非 atomic） | 无需处理 |

## 类型辨析（判断标准）

- **atomic vs concept vs term**：想表达「洞察/观点」→ atomic；想表达「术语/定义」→ term；想做「概念整合和索引」→ concept
- **area vs concept vs moc**：需要「深入学习并应用到项目」→ area（有长期目标）；只是「了解某技术」→ concept 或 moc（无目标）
- **sop vs question**：已验证可重复 → sop；待探索可变化 → question

### MOC vs concept 边界（消化禁令）

> 三层粒度模型：`area`（宏观，责任视角）→ `moc`（中观，导航视角）→ `concept`（微观，概念视角）→ `atomic`（最小洞见）。MOC 与 concept 是这条链上最易混淆的一环，边界规则如下：

| 判定维度 | `moc`（只索引不消化） | `concept`（解释与整合） |
|---------|----------------------|------------------------|
| 核心动作 | **分类**：把笔记按主题/维度归类 | **解释**：说明「为什么」「如何运作」 |
| 每条的形态 | `[[链接]] — 一句话说明`（说明只做分类标注，不展开原理） | `[[atomic]]` + `**原理**`（原理是论证，可展开） |
| 是否产出洞见 | ❌ 不产出，洞见下沉到 concept/atomic | ✅ 核心命题段产出 atomic |
| 有无「核心命题」段 | ❌ 无（若有，说明已越界为 concept） | ✅ 有（这是 atomic 的唯一合法原料段） |
| 典型章节 | 分类分组、知识网络、待探索 | 核心命题、运行机制、关键区别、适用范围、批判、FAQ、SOP |

**消化禁令**：MOC 一旦开始写「为什么/原理/机制」，就应下沉为 concept（或把该条目提炼成 atomic）。判断口诀——**「MOC 问『有哪些』，concept 答『为什么』」**。

**易踩的三种错位**（体检已实际发现）：
1. **concept 写得像 MOC**：只有子概念罗列、无「核心命题」段 → 本质是 MOC，应改 `content-type: moc` 或补核心命题段。
2. **MOC 膨胀成 concept**：开始逐条展开原理、写运行机制 → 应把消化内容下沉到 concept，MOC 只留索引。
3. **area 误标成 concept**：带「长期目标」「关键领域」等 area 专属字段，却标 `concept` → 应改回 `area`（React.md 曾是此例）。

## 目录规则

- **特定型**（由物理位置决定）：`project` → 10-PROJECTS，`area` → 20-AREAS，`article` → 60-BLOGS，`diary` → 90-DIARY
- **通用型**（由 content-type 决定）：`atomic` → 50-ZETTELCASTEN，其余 → 30-RESOURCES
