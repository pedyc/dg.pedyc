> [!important] 本文件不定义任何判据
> 判据原文一律在 `01-META/Truth/` 与 `AGENTS.md`。本文件只写三件事：它为什么存在、属于哪一类、靠什么在每次被违反时发声。下一节定义的是「判据」**这个词**，不是任何一条判据。
> 「判据」列只写名词短语，不出现「必须」「不得」「应当」。一旦在这里复述条文，它就变成第二真值源——而且是没人校的那一份。

## 〇、判据指什么

这个词在库里出现过几十次，有两种所指，此前没有定义过。

| | 用法 | 例句 | 发生时刻 |
|:--|:--|:--|:--|
| A | **判定依据** | 「sop 与 question 的判据是**有没有值得留下的岔路**」「判据是**收益能否指认**」「判据是**单篇失效**，不是容器结束」 | 正在写或选某一篇的那一刻 |
| B | **设计条文** | 「**判据只能有一份**」「判据原文一律在 `Truth/` 与 `AGENTS.md`」 | 建库、改规则的那一刻 |

A 的语法都是「判据是 X，不是 Y」——一个问句加答案键；B 是条文，可以违反，需要存档。**B 是 A 的存档形式**：每条条文在被用到时，必须能塌缩回一个「这一刻 A 还是 B」的问题。塌缩不出来的，就是不可判定的那一条。

> **判据 = 一个在具体时刻必须回答、且有答案键的问题。**

三个测试：

1. **它能被违反吗？** 不能（如「知识很重要」）→ 不是判据，是描述。
2. **它能回答「这一刻 A 还是 B」吗？** 不能 → 是理由或目标，不是判据。
3. **被违反时谁发声？** 脚本 / 评审 / 无——这是**载体**，不是判据本身。载体为「无」的判据仍是判据。

它不是四样东西：**理由**（为什么这么定，住 `Guide/Design`）、**载体**（让它发声的机制）、**步骤**（`Specification`）、**知识**（世界是怎样的，住 30）。判据只回答一件事：这一刻该怎么做。

## 一、两类判据，一条测试分开

本库的判据有两个来源，混在一起就看不出哪条该留、哪条该废。

**预设判据（P）**：本库初始化时，从一个目的演绎出来的规则。它在库里还没有任何笔记的时候就已经成立。例如「按行动组织而不是按主题」——不是因为试过主题分类失败，而是它的上位前提（痛点是唯一动力源）规定了组织方式。

**工程自增长判据（E）**：库长大以后，实践中撞出来的补丁。它在初始化时不存在，理由是某次具体事故或某项具体成本。例如「`up` 的每个链接都要双引号」——理由是实测 27 处裸写导致字段读成空。

**分开它们只需要一句测试：去掉它，目的还达成吗？**

| 结果 | 类型 | 它靠什么成立 |
|:--|:--|:--|
| 达不成 | 预设 | 目的本身 |
| 仍达成，只是更贵或更容易错 | 工程 | 一次事故或一项成本 |

三个推论，决定这张表怎么用。

**第一，两类判据的废除路径不同。** 预设只能被「目的变了」推翻——没人用它不构成废除理由，因为它是目的的要求，不是偏好的产物。工程只能被「证据过期」推翻——反例消失、成本消失、读者消失，它就该退场。

这解释了字段墓碑里为什么全是工程判据（`status`、`related`、`quadrant`、`category`）：它们的证据是「有人读它」，而读者会消失。反过来，没有一条预设判据进过墓碑。

**第二，预设判据大多没有载体，这不是缺陷。** 「为什么按行动组织」无法被脚本查——能查的只有「目录里是不是只剩 `atomic`」这种下游形态。所以把「判据必须有脚本兜底」当判据用，会逼着给预设判据编一个假脚本。准确的要求是：**每条判据都得知道自己的载体，可以是「无」。**

**第三，工程判据会反过来修正预设的落法。** 它不改变目的，但会改变目的的落地形状。「PARA 只贡献三个容器位」是预设（R 的判据不可判定），但具体是哪三个位、第 30 个目录怎么兜底，是工程判据定的。

## 二、从目的往下推

![[判据六层推导.excalidraw|560]]

图是这张表的缩略版：左边是层号与该层的判据条数，蓝卡为预设、橙卡为工程。下面逐层展开，图上每格对应下文一行。

### L0 目的

**造一个第二大脑：一个能在需要时被调用的外部记忆。**

两个词要分开。「记得住」是外部化，它只是手段；「用得上」是价值，它才是目的。库的价值不在存量——库里现有 1200 多篇笔记，如果只能读不能用，这个数量是负债不是资产。

下面每一层，要么是这一句的演绎，要么是一次落地时的撞墙。

### 第 0 层：两个前提

它们不是从「第二大脑」推出的，而是「为什么要造第二大脑」的前提。没有它们，L0 不成立。

| 编号 | 判据 | 为什么 | 载体 | 原文 |
|:--|:--|:--|:--|:--|
| P1 | 痛点是唯一动力源 | 知识管理不靠「应该」驱动，靠「要用」。没有痛点的库会退化成收藏，收藏不产生调用 | 无 | [[痛点是知识管理的唯一动力源]] |
| P2 | 知识只有被调用时才产生价值 | 它给出了「价值」的定义。后面所有判据都在服务这一个词，而不是服务「写得多」或「整理得齐」 | 无 | [[知识只有被调用时才产生价值]] |

### 第 1 层：为什么是 PARA + 卡片盒

这一层回答「用什么结构」，也是预设判据最密集的地方。

| 编号 | 判据 | 为什么 | 载体 | 原文 |
|:--|:--|:--|:--|:--|
| P3 | 按行动组织，不按主题（PARA） | 调用的触发点是手上正在做的事，不是它属于哪个学科。按主题分，分类数无限增长；按行动分，容器只有几个 | 无 | [[为什么使用PARA笔记法]] |
| P4 | 原子化 + 双链（卡片盒） | 调用的第二种形态是拿一条旧判断支撑一个新判断，这是横向的，容器给不了。选它而不是别的实现，是因为 Obsidian 的双链是原生能力，落地成本接近零 | 模板 | [[卡片盒笔记法]] |
| P5 | 树 + 网，共用同一批节点 | 缺树变孤岛（笔记在，找不到），缺网变收藏夹（读得到，用不上）。两套节点会产生两个答案，改一处不报错，而且不显形 | 无 | [[本库设计原则]] |
| P6 | 抗不整理 | 一个人维护。需要定期回看才能维持的结构，三个月不动就会烂成两套答案。它是预设判据里唯一**否决式**的：不要求做什么，只否决需要定期回看的方案 | 无 | [[本库设计原则]] |
| P7 | 单一真值，其余只引用 | 同一事实两处写，改一处不报错，是本库最不能接受的失效。它是 P5 的直接推论：共用节点要求同一件事只有一个来源 | Truth 纪律 | [[真值索引]] |

### 第 2 层：落地，先解决「放哪」

P3 与 P4 一落地就撞：PARA 要求每篇有唯一归属，卡片盒拒绝回答「它属于什么」。这一层是本库对这次相撞的裁决。

| 编号 | 判据 | 为什么 | 载体 | 原文 |
|:--|:--|:--|:--|:--|
| P8 | 归属与形态正交 | 两个维度各有唯一权威，才不会出现「选了 concept 必须放 30」。一一映射的代价是每加一个目录就要重定义一次类型，两处必然漂移 | 脚本 | [[本库目录结构]] |
| P9 | PARA 只贡献三个容器位 | P/A/Archive 有明确判断（有截止日期、长期负责、已退役）；R 的判断是「将来可能有用」，不可判定，而且正是收藏夹的定义 | 无 | [[本库目录结构]] |
| P10 | 树必须有缺省位 | 树必须覆盖所有节点，否则出现「树上没有位置」的孤岛。缺省是排除法的结果，不是设计出来的一个类别 | 无 | [[本库目录结构]] |
| P11 | 缺省目录的判据在出口 | 缺省目录不能正面定义，否则它就不是缺省。它能防的失效只有「只进不出」 | 无 | [[本库目录结构]] |
| P12 | atomic 永不归档 | 洞察是资产，不随时间过期。归档意味着它退役，而它没有退役的理由 | 无 | [[atomic 设计]] |
| E1 | 十位分组、个位排序 | 目录顺序若随新建而变，位置就不稳定。找回来靠的是结构，不是记忆 | 无 | [[本库目录结构]] |
| E2 | 两个维度分管，不设统一优先级 | 形态不影响归属，归属不影响形态。强行排先后会造出一个假的优先级，然后每次判都要多答一个没用的问题 | 无 | [[本库目录结构]] |
| E3 | `20-AREAS` 边界：负责 vs 弄懂 | 领域目录一旦收知识笔记，A 就变成第二个 R | 无 | [[本库目录结构]] |
| E4 | 三个单形态目录 | 50、60、90 是树上唯一的锚点。若 50 被工作区吞掉，树就没有锚了；其余目录形态不限，是实测 59 篇里 57 篇非 `project` 得出的 | 脚本 | [[本库目录结构]] |
| E5 | `50` 准入只看形态 | 作者判据不可判定（查不出谁写的），实测也从未执行——写笔记的人只看得见形态 | 脚本 | [[本库目录结构]] |
| E6 | `30` 的出口三条 | 排除法只能防进错，防不了出不去。一篇三年前的二手概念七步全过，之后没有任何动作会再碰到它 | 无 | [[本库目录结构]] |
| E7 | 归档只有一层，移入目录；判据是单篇失效，不是容器结束 | 软归档（只改字段）与物理移动并存，会产生两个答案。实测 88 篇归档里只有 13 篇字段同步。归档对象是单篇，整目录搬会把仍有效的资产一起退役 | 脚本 | [[元数据规范]] |
| E8 | `40-ARCHIVE` 免维护 | 已退役的东西仍被要求合规，等于给不再维护的部分继续摊维护量 | 无 | [[本库目录结构]] |

### 第 3 层：怎么写

这一层起全是工程判据。原因很直接：理论只回答「该不该拆小」，不回答「拆小后正文写几段」。

| 编号 | 判据 | 为什么 | 载体 | 原文 |
|:--|:--|:--|:--|:--|
| E9 | `content-type` 十四种枚举 | 类型自由生长，模板与视图就无法枚举。枚举是成本的边界，不是知识的分类学 | 脚本 | [[笔记类型规范]] |
| E10 | `content-type` 决定模板 | 一次判断换一次正确的正文骨架，减少重复劳动，也让几十篇笔记长成同一形状 | 模板 | [[笔记类型规范]] |
| E11 | `atomic` 标题先主语、后可判断 | 标题会离开本文单独出现（被引用、搜索结果、图谱）。主语悬空时无所谓真假，读者连它在说什么都不确定 | 模板 | [[atomic 设计]] |
| E12 | `atomic` 正文三段：观点 + 边界 + 论据 | 只写观点会坍缩成主题概括，论据放开会长成 mini concept。论据至多一条，是因为多留等于写作动作翻倍，且多出的在 concept 里已经写过 | 模板 | [[atomic 设计]] |
| E13 | 边界必填 | 没有边界的断言，读者不知道它何时失效，也就没法拿去判断 | 模板 | [[atomic 设计]] |
| E14 | 论据归谁看复用度 | 服务两个以上论点或需展开成节 → 上移 concept；只服务一个且不超一行 → 留下。判据是复用度，不是「论证归 concept」这句简化说法 | 无 | [[atomic 设计]] |
| E15 | 新笔记不挖空 | 挖空要求每次多做一个判断（哪个词是关键机制词），这个判断经常做不准。省下的成本能换成更多篇 | 模板 | [[atomic 设计]] |
| E16 | `atomic` 与 `concept` 看形式，不看主客观 | 客观机制一旦以命题陈述就是 `atomic`。按主客观分，客观命题无处安放，改写只会丢掉精确性 | 无 | [[笔记类型规范]] |
| E17 | 注记与 `atomic`：可反驳 vs 可核实 | 事实只需核实，判断需要划边界。判断混进注记，会以「已经记过了」的姿态躲掉边界 | 模板 | [[笔记类型规范]] |
| E18 | MOC 只索引不消化 | MOC 一旦写原理就变成第二个 concept，内容存两份，改一处漂一处 | 模板 | [[笔记类型规范]] |
| E19 | 规范名不越界 | 名字的外延由规范给定。正文越界不会报错，只让每条入链都得先猜它指规范还是指领域 | 无 | [[笔记类型规范]] |
| E20 | `sop` 与 `question` 看有没有岔路 | 「能不能写死步骤」随说话人的水平漂移，同一件事三个月前写不出、现在随手就写 | 无 | [[笔记类型规范]] |
| E21 | 断链 = 待提炼 | 断链不是错误，是「认可了这个洞见但还没成文」。它是待办，不是欠账 | 脚本 | [[笔记类型规范]] |

### 第 4 层：怎么连

树解决「找回来」，这一层解决「用上」。全部是工程判据，因为卡片盒只要求「连」，不规定「怎么连才不乱」。

| 编号 | 判据 | 为什么 | 载体 | 原文 |
|:--|:--|:--|:--|:--|
| E22 | 六桶词表 | 收口前全库 70 种写法，同一件事最多五个名字，边无法统计 | 脚本 | [[知识图谱词表]] |
| E23 | `并列` 与 `相关`：能否放进同一抽屉 | 旧定义要求共享上位，把「并列可以没有共同上位」排除了。判不出就落 `相关`，`相关` 于是占到 52% | 无 | [[知识图谱词表]] |
| E24 | `comparison` 的被比较对象不进桶 | 被比较对象是这篇的材料，已写在首段；再进 `相关` 只是复述，比对族反而连不起来 | 模板 | [[知识图谱词表]] |
| E25 | 不设 `## 关联` 节 | 实测 114/119 篇写了这一节，82% 第一条链接就是 `up` 副本，89% 是不带关系标签的裸链接。丢一个 `up` 就能交差 | 脚本 | [[atomic 设计]] |
| E26 | `up` 管容器，上位管抽象 | `up` 回答「只能放一个地方放哪」，上位回答「它是哪一类的一个实例」。两者不一致是常态，实测 21 篇被误判成缺陷 | 无 | [[元数据规范]] |
| E27 | 外来格言不建链接 | 写 `[[外来格言]]` 等于生产一张永远不打算清偿的欠条，每次扫断链都要重判一次 | 无 | [[文件名与别名规范]] |
| E28 | 链接用文件名，不用别名 | 文件名的存在性由文件系统保证，别名的存在性靠人记。实测 169 处别名引用 + 15 处假前缀 | 脚本 | [[文件名与别名规范]] |
| E29 | 前缀放 `aliases`，不进文件名 | 正文链接若依赖别名，改一次别名要全库改链接，漏一处就是断链 | 脚本 | [[文件名与别名规范]] |
| E30 | 格言位 ≤ 14 字（参考口径） | 标题中位数 22 字，超过 14 字塞不进句子中间，硬塞会失去断言感。它是复查时的排序依据，不是合格线 | 无 | [[文件名与别名规范]] |

### 第 5 层：字段

字段层的判据几乎都来自同一个病灶：同一语义存两处，且要手工同步。

| 编号 | 判据 | 为什么 | 载体 | 原文 |
|:--|:--|:--|:--|:--|

| E32 | `up` 每个链接都要双引号 | 裸写 `[[x]]` 在 YAML 里是列表套列表，没有语法报错，只在读取时表现为空。实测 27 处 | 脚本 | [[元数据规范]] |
| E33 | 派生值不落 `frontmatter` | `quadrant`、`status`、`category` 三次都是同一个病灶：能算出来的值手工填，必然与源头不一致 | 脚本 | [[元数据规范]] |

## 三、读数

**第一，比例是 16 : 39。** 预设判据不到三成，工程判据占七成。这本身就是结论：理论只提供方向，可执行性全部来自实践。一个库如果只有预设判据，它能被说出来，但不能被照着做。

**第二，预设判据只有三条有载体（P4 模板、P7 Truth 纪律、P8 脚本），其余 13 条是口径。** 这不是它们写得虚，而是性质决定的——它们回答「为什么」，而「为什么」不能被脚本查。P6 没有载体，但它是否决式的：不靠脚本，靠它能否决一个方案。

**第三，载体分布是 25 : 31。** 56 条里 25 条有载体（脚本 14、模板 10、纪律 1），31 条没有。按类拆：P 类 16 条中 13 条无载体，E 类 40 条中 18 条无。所以「这条判据有没有脚本」对 P 类基本无效，会逼出一个假脚本；对 E 类也不是自动成立——近一半 E 判据只能靠评审。载体为「无」是合法状态，前提是它知道自己在靠人判。

**第四，理论偏移不是全库性的，它集中在形态层。** 卡片盒只回答「该不该拆小」，从不回答「拆小后正文写几段」。所以形态层的判据全是工程判据——这不是偏移，是分工。真正的偏移只有一种：拿卡片盒当理由去删工程判据，或者把工程判据追认成卡片盒的要求。本文件旧版（J3、J4）正是这么干的。

### 已识别的后起解释（不要再犯）

分类判据时最容易犯的错，是给工程判据补一条预设出身。下面四条是已经抓到的：

| 曾经的写法 | 错在哪 |
|:--|:--|
| 把 2026-10-20 自建的 atomic 命题标成「预设判据、理论演绎」 | 给一条工程判据发了理论出身证明 |
| 先划好「卡片盒只回答该不该拆小」的边界，再给形态族下结论 | 顺序是反的：先有结论，再为结论划边界 |
| 把 `up` 与上位的分工追认成「防误判判据」 | 它本是 2026-10 一次误判事故（21 篇）的教训，属 E |
| 把「抗不整理」写成 Less is More 的因 | 时序反了：10-24 先有读法，11-07 才回溯归结 |

判据只有一条：**这条理由能不能在它要解释的那条规则之前找到出处。** 找不到就是后起，写进档案时标日期，不倒写成初衷。

## 五、怎么用这张表

新增一条判据时问三句：

1. 它落在哪一层？落在 L0 到第 6 层之外，说明它不是判据，是偏好。
2. 去掉它，目的还达成吗？达不成是 P，更贵更易错是 E。这个判断决定它将来怎么被废除。
3. 它的失效对象是什么，载体会是什么？两者都说不出，它无法被证伪，也就不该进 Truth。

要废除一条判据时看哪边：

- P 类：看目的变没变。目的没变就不能用「没人执行」当理由——那是执行问题，不是判据问题。
- E 类：看证据过没过期。读者消失、成本消失、反例消失，它就该退场，而且应当进一次墓碑。
