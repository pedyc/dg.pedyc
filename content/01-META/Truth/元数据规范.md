## uid 的生成规则

格式 `YYYYMMDDHHmmss`，由模板里的 `<% tp.file.creation_date("YYYYMMDDHHmmss") %>` 在创建瞬间生成。存量 12 位（`YYYYMMDDHHmm`）不批量改写，遇到再改。

为什么是秒级而不是分钟级：12 位精度下，同一分钟批量建卡会撞号，实测出过 45 组重复，最大一组 `202603121028` 被 12 篇共用（含 3 个领域主页与本库指南）。uid 的用途是唯一标识，撞号等于没有。

为什么必须由 Templater 生成：`<% %>` 只有 Templater 渲染，Daily Notes 与核心 Templates 插件都不认。把模板交给它们套用，占位符会被原样写进文件，且不会报错——2026-10-25 那篇日记的 uid 就是这么变成字面量的。创建链路见 [[笔记类型规范]] 的「日记的创建链路」。

## up 的写法

`up` 是**链接字段**，必须让 YAML 解析出字符串或字符串列表，再由 Obsidian 解析成链接。三种写法的实际语义完全不同：

| 写法 | YAML 解析结果 | 后果 |
|:---|:---|:---|
| `up: "[[概念]]"` | 字符串 `"[[概念]]"` | ✅ 解析为一个链接 |
| `up: ["[[概念]]", "[[机制]]"]` | 字符串列表 | ✅ 解析为两个链接 |
| `up: [[概念]]` | **嵌套列表** `[["概念"]]` | ❌ dataview 拿不到链接，反查失效 |
| `up: 概念` | 字符串 `"概念"` | ❌ 不是链接，只能当纯文本显示 |

**规则：每个 `[[...]]` 都必须被双引号包裹。**

```yaml
up: "[[概念]]"                          # 单一父级（默认情形）
up: ["[[Agent]]", "[[LLM]]"]            # 多父级：跨两个概念时才用数组
up:                                    # 无父级：留空，不要写 null 或 ""
```

三条约定：

1. **单父级用标量，多父级才用数组**。实测全库多父级仅 10 处（跨概念的笔记），其余都是单父级——不要为了「统一」把所有值都包成数组，那是多余噪音。
2. **没有父级就留空**。`""`、`null`、`[]`、`{ 父级 }` 占位符残骸一律视为未填。**不猜**：不知道挂哪个概念就不写，留空是待办信号，填错是污染知识网络。
3. **链接目标用文件名，不用别名**，与正文链接同一条规则（见 [[文件名与别名规范]]）。显示文本需要更通顺时用 `|`：`up: "[[Signal(Angular)|Angular Signals]]"`。

> **为什么写死双引号**：裸写 `[[x]]` 在 Markdown 正文里是链接，在 YAML 里却是「列表套列表」。这个差异没有语法报错，只在读取时表现为「字段是空的」，极难反查——2026-10-23 全库实测 27 处踩了这个坑。同日统一 240 处写法（裸链接 27、裸值 87、单元素数组降级 105、null 与空串 19、占位符残骸 2）。

### up 与正文「上位」的分工（2026-10-27 定）

`up` 表示**归档位置**——这篇笔记挂在知识树上哪一篇下面。它**不表示认知层级**：某个概念比本笔记更一般，写在正文「知识图谱」的 `上位` 桶里。

两者不一致不算缺陷。实测 144 篇可比对里 21 篇不同（15%），例如 `Reflect` 的 `up` 是 `ES2015`（包含它的规范版本），正文上位写「元编程」（它所属的类别）——容器关系与抽象关系本来就是两回事。**不要为了让两处一致去改其中一处。**

判据一句话：`up` 问「如果只能放一个地方放哪」，上位问「它是什么东西的一个实例」。六个桶的判据与对照表见 [[知识图谱词表]]。

> 这里的「归档位置」指知识树上的挂载点，与后面「归档只有一层：移入目录」讲的 40-ARCHIVE 退役归档无关。


## 各类型专属字段

> 本表是**各 content-type 特有 frontmatter 字段的唯一定义**。`笔记类型规范` 只声明「某类型有专属字段」，具体字段定义以本表为准。

### project（项目笔记）

| 字段 | 用途 | 可选值 |
|------|------|--------|
| `consequence` | 重要程度 | 1~10 |
| `urgency` | 紧急程度 | 1~10 |
| `energy-type` | 精力类型 | 💡 创意 / ⚡ 能量 / 🔄 常规 / 🏃 运动 |
| `expire` | 截止日期 | 日期 |

> [!important] `quadrant` 不是存储字段
> 四象限位置由 `consequence` 与 `urgency` 派生（重要 ≥7 且紧急 ≥7 为 Q1，重要 ≥7 但紧急 <7 为 Q2，以此类推），**不由人工填写**。原 `quadrant:` 字段已于 2026-10-23 从模板与本文移除：它是前两个字段的函数，三处手工维护必然产生不一致。实测依据：`10-PROJECTS` 内 `consequence` / `urgency` 各填 2 篇，`quadrant` 为 0 篇。
>
> 需要看象限分布时，在 `.base` 里用 formula 计算，不要在笔记里落库。

### article（博客文章）

| 字段 | 用途 | 可选值 |
|------|------|--------|
| `published` | 发布状态 | true / false |
| `category` | 横向分类 | 固定 `blog` |

### record（记录）

`record` 覆盖事件与素材两种形态，字段按形态取用：

| 字段 | 用途 | 可选值 | 适用形态 |
|------|------|--------|----------|
| `url` | 原文链接（定义见通用字段） | - | 素材必填，事件可空 |
| `date` | 这件事发生的日期——事件的发生日、素材的发布日 | 日期 | 均可 |
| `location` | 地点 | - | 仅事件 |
| `participants` | 参与者 | - | 仅事件 |

信源与产出的挂载**不是字段，是正文的 `## 来源` / `## 产出` 两段**。三条理由：base 无法跨笔记取值，字段填了也统计不出来；正文段能被脚本按段正则读到，且不受「相关阅读」类链接干扰；写在正文里阅读时看得见，字段看不见。三种形态的判据见 [[笔记类型规范#record 的三种形态]]。

## 为什么没有 status 字段（2026-10-24 废除）

本库**不设** `status`。曾经的 `fleeting / active / archived` 三值已废除：17 个模板不再生成该字段，存量笔记里残留的该字段视为历史遗留——**不读取、不维护、不批量删除**（符合「先不管遗留，遇到再改」）。

废除依据全部来自实测，不是判断：

| 证据 | 数据 |
|:--|:--|
| 它记录的是「用了哪个模板」，不是成熟度 | 17 个模板里 10 个写 `fleeting`、7 个写 `active`，新建笔记的 status 由模板决定，与内容进度无关 |
| 它不追踪生长 | `fleeting` 的最后修改中位年龄 88 天，`active` 是 70 天，两组几乎重合；170 篇 fleeting 里 33 篇创建超 180 天，最老 606 天 |
| 终态被目录抢了职能，且不同步 | `40-ARCHIVE/` 88 篇里只有 13 篇 `status: archived`，42 篇缺字段，2 篇是 `active` |
| 维护成本真实、收益为零 | 17 个模板各一行 / 曾为收窄值域改写 344 篇 / 清 28 处脏值 / 1 个专属 base（全库零嵌入）/ 1 个校验函数 / 2 个巡检视图 |

**根本原因：同一个语义存两处，且需要手工同步，必然漂移。** 「这篇归档了吗」由「在不在 `40-ARCHIVE/`」表达一次就够，再声明一次只会得到两个互相矛盾的答案。

### 用什么替代

状态是「位置 × 时间」的派生值，按本库「派生值不落 frontmatter」的原则本就不该手填：

- **位置表达阶段**：`00-INBOX`（捕获）→ `30-RESOURCES`（加工）→ `50-ZETTELCASTEN`（原子化）→ `40-ARCHIVE/`（退役）。物理移动不会忘记改，也不可能忘。
- **时间表达新旧**：`date-created` / `date-modified` 写在 frontmatter 里，`file.ctime` / `file.mtime` 由文件系统给（后者更根本，不依赖任何工具跑过）。
- **要看「哪些笔记卡住了」**：打开 `99-ASSETS/Bases/笔记滞留与陈旧.base`，它按 `file.mtime`（最后写入时间）排序——这个时间不可能漏记，因为它不是字段。

### 不要加回来

「状态」这个词天然让人觉得该有——上一代正是因为这点被设计出来、又因为这点被放弃的（同样的故事已在 `quadrant`、`energy-type` 上发生过，两者全库 0 篇）。若将来确实要判断成熟度，判定顺序固定为三层：**先看目录（事实）→ 再看 `date-modified`（工具记的）→ 最后才轮到人来判断（主观的，且必然被放弃）**。凡是需要人定期回看内容才能填的字段，在本库一律不设。

## 为什么不设 related（2026-10-24 废除）

`related` 曾是「平级相关笔记」的字段，111 篇写过。废除理由只有一条：**关联写在正文里才有信息量**。

`related: ["[[动画原理]]", "[[CSS Animation]]"]` 只说明「这几篇有点关系」，没说是什么关系。写进正文则必须交代：

```markdown
## 关联

- [[动画原理]] — 帧序列如何决定视觉连续性
- [[CSS Animation]] — 同样做补间，但它跑在合成线程
```

两句话的成本，换来的是「为什么相关」而不只是「相关」。而 `up` 已经承担纵向父级；横向关系如果只剩一个裸链接列表，它不承载任何判断。

另有两个技术原因：

- **三种写法混用**：`related: "[[x]]"`（单值）、`related: ["[[x]]"]`（行内数组）、`related:` 块列表（多行），还有 `related: [["ES2026"]]`（嵌套数组，YAML 解析后链接丢失——和当年 `up` 踩的是同一个坑）。
- **零消费者**：没有 base、没有脚本、没有 dataview 读它。它只被写，从没被读。

存量 111 篇不批量清理（先不管遗留，遇到再改）。新建笔记时关联一律写正文，不写字段。

## 字段墓碑

字段被废除在本库是常态，因为**加字段几乎零成本，维护字段几乎一定失败**。想加回来的人先看这张表：

| 字段 | 原意 | 废除理由 | 替代 |
|:--|:--|:--|:--|
| `status` | 笔记生命周期 | 记录的是「用了哪个模板」，与成熟度无关 | 目录表达阶段 + `file.mtime` 表达新旧 |
| `related` | 平级相关笔记 | 只有链接没有关系，写正文更有信息量 | 正文 `## 关联` 节 |
| `quadrant` | 四象限分类 | 全库 0 篇填写；应由 `consequence × urgency` 派生 | formula |
| `energy-type` | 日程能量类型 | 全库 0 篇填写；属日程层，不属 project 字段 | — |

> 共同规律：**需要人回头看内容才能填的字段，一律长不出来**。能活下来的字段都满足「创建那一刻顺手就能写」。

## 按 content-type 的归档语义

| content-type | 成熟后的标志 | 归档触发条件 |
|:---|:---|:---|
| `atomic` | 洞察完成 | ⚠️ 几乎不归档——洞察是资产，永不过期 |
| `concept` | 概念理解完成 | 版本过时但笔记未更新 |
| `term` | 定义完成 | 定义被证伪或被新版本替代 |
| `roadmap` | 版本覆盖完成 | 新版本已发布但笔记未更新 |
| `sop` | 流程验证完成 | 技术栈变更导致流程失效 |
| `area` | 领域探索完成 | 放弃该领域的学习/关注 |
| `moc` | 索引整理完成 | 主题已放弃，无导航价值 |

## 归档只有一层：移入目录

| 判断 | 操作 |
|:---|:---|
| 明确过时 / 错误 / 长期孤立且无保留价值 | 物理移动到 `40-ARCHIVE/` |
| 内容仍有效、只是暂时不想维护 | **不动**。留在原目录，用 `date-modified` 说明它多久没碰过 |

> [!warning]
> **Zettelkasten 不删除原则**：atomic 笔记永不被删除；其他类型笔记过时/孤立时归档而非删除。
>
> 「软归档」（原地不动、只改字段）这条路已随 `status` 一起废除。它在实践中使用率为 0（`40-ARCHIVE/` 88 篇里仅 13 篇字段同步），却让「归档」这个判断出现两个可能互相矛盾的答案。

## 归档判断决策树

```bash
笔记不更新了？
├── 内容完善 + 仍被引用 + 版本未过时
│   └── → 不动（原目录留着，不必标记）
├── 版本已更新但笔记未更新
│   └── → 移入 40-ARCHIVE/
├── 入链=0 + 从未被引用 + 无孤立价值
│   └── → 移入 40-ARCHIVE/
└── atomic 类型
    └── → 永不归档（洞察是资产）
```
