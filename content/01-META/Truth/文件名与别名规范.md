> [!important]
> 本文件是**本库「文件名 + aliases」命名规则的唯一真值**（Single Source of Truth）。
> 前缀**取值**只在本表定义；其他文件可保留速查副本（如 [[笔记类型规范]] 的映射列、技能内的速查表），但取值必须与本表一致，冲突时以本表为准。

## 适用范围

命名涉及三个对象，本文件只管其中两个：

| 命名对象 | 唯一真值 | 本文件是否定义 |
|---------|---------|--------------|
| 顶层目录名（`00-INBOX` / `_templates`） | [[本库目录结构]]「前缀语义」 | ❌ 不管，见该处 |
| 文件名（纯标题） | **本文件** | ✅ |
| `aliases`（前缀宿主） | **本文件** | ✅ |

附带管一个相邻问题：**文件名出现在正文里的写法**（内联引用、外来格言该不该给链接），见本文「引用写法」一节。它放在这里，是因为「该不该链接」是 aliases 与显示文本两节的共同前置判断——链接不存在时，后面两个问题都不成立。

**不管**的两类，避免误引：

- **目录名**：编号语义、`_` 前缀约定 → [[本库目录结构]]
- **`atomic` 标题须为陈述句**：这是 atomic 的形态特征，不是通用命名规则 → [[笔记类型规范]]

## 核心原则

**前缀仅用于 aliases 检索，WikiLink 引用使用纯标题。**

```markdown
<!-- 正确：纯标题引用 -->
[[闭包]] 而不是 [[C-闭包]]

<!-- aliases 字段放前缀 -->
aliases: [C-闭包]
```

理由有两条，第二条是 2026-10-23 才被数据证实的：

1. **别名会被改**。aliases 是检索标签，发现更贴切的词就该换；一旦正文链接依赖它，
   每次改别名都要全库改链接，漏一处就是一个断链。
2. **别名不一定存在**。实测 `[[A-宗教与神秘学]]` 被 5 篇笔记引用 9 次，而目标文件
   `宗教与神秘学.md` 的 aliases 里从来没有这一项——写的人以为有，实际直接断链。
   **文件名的存在性由文件系统保证，别名的存在性靠人记**，这两者的可靠性不在一个量级。

**2026-10-23 已全库执行**：169 处别名引用 + 15 处假前缀引用改为文件名引用。
常驻检查 `python _scripts/validate_meta.py --links`，规范一旦回退会立刻报出来。

## 显示文本（`[[标题|显示文本]]`）

**允许，且推荐用于文件名不够通顺的场合。** 这类写法的链接目标仍然是文件名，前半段符合上面的核心原则，后半段只是渲染时的替换文本。

```markdown
[[Signal(Angular)|Angular Signals]]     文件名带括号，可读性差
[[SSR|服务端渲染]]                      英文缩写，中文读者需要
[[Hooks(React)|React Hooks]]           同上
```

**注意别把两个「别名」搞混**——它们同名不同物，作用完全不同：

| 概念 | 位置 | 作用 | 能否用于链接 |
|:---|:---|:---|:---|
| `aliases` 字段 | frontmatter | 让搜索、自动补全能匹配到同义词 | ❌ 不用于链接（见核心原则） |
| 显示文本 | `[[标题\|显示文本]]` 的竖线后 | 只改这一处渲染出来的文字 | — 它就是链接的显示部分 |

区别的实质：`aliases` 是**文件的属性**（改一次影响全库引用），显示文本是**某一次引用的局部写法**（只影响那一行）。前者会被改、可能不存在，后者永远跟着这行文字走，所以两者风险量级不同。

三条使用约定：

1. **文件名已通顺就不要加 `|`**。`[[博弈论]]` 不要写成 `[[博弈论|博弈论]]`，那是纯噪音。
2. **表格内必须转义**：`[[标题\|显示文本]]`，否则竖线会被 Markdown 当作列分隔符，把表格结构撑坏。
3. **别用它掩盖坏命名**。如果一篇笔记在十几处都被加了同一个显示文本，说明**文件名本身该改**——把文件重命名成那个通顺的名字，然后让显示文本退化成同义词或直接删掉。显示文本是补丁，不是解药。

## 引用写法：正文里怎么提到一句话

上一节解决「链接怎么显示」，这一节解决「什么时候该链接、什么时候不该」——它是显示文本一节的前置判断，因为「该不该加 `|`」在「该不该链接」没定之前无从谈起。

**分界线只有一条：被引用的那句话，在本库有没有自己的文件。**

| 被引对象 | 有没有文件 | 写法 |
|:---|:---|:---|
| 本库的格言（`atomic` 的标题） | 有 | 内联 `[[全句]]`，不加引号、不加显示文本 |
| 外来格言（Less is More、奥卡姆剃刀原话…） | 没有，且**不应有** | 直写 + 引号，**不建链接** |

### 本库格言：链接即引文

`atomic` 的标题必须是陈述句，这条规则不只是写作约束——它顺带把「引用」解决了：`[[格言句]]` 渲染出来就是那句话本身，**链接已经完成了引用**，不必再套引号或单独写一遍引文。

三个引用位，长度要求完全不同：

| 引用位 | 写法 | 长度容忍 |
|:---|:---|:---|
| `## 关联` 区 | `- [[全句]]：一句解释`（解释=关系类型） | 不限，独占一行 |
| `concept` 的「核心命题」段 | 段中内联，紧跟一句展开 | 中，需与行文咬合 |
| 笔记正文里当论据（**格言位**） | 用破折号把链接推到句末 | **≤ 14 字** |

为什么单独给格言位设长度线：`50-ZETTELCASTEN` 229 篇标题的**中位数是 22 字**。也就是说库里多数标题是「判断」而不是「格言」——判断需要语境才有信息量，天然不适合塞进句子中间。真要当格言用，超过 14 字就别硬内联，改挂 `## 关联`，或者**改文件名**。

两条红线：

1. **不造短别名当链接**（`[[痛点驱动]]`）。2026-10-23 全库清理过 169 处别名引用，这是同一个错误的另一个变体。
2. **不为缩短而加显示文本**。`[[长标题|痛点]]` 之后读者看到的是「痛点」两个字，格言的断言感就没了——格言的力量来自整句判断，不是关键词。

```markdown
✅ 他换了四款笔记软件，每款都没坚持过三个月——[[痛点是知识管理的唯一动力源]]。

⛔ 他换了四款笔记软件，每款都没坚持过三个月（见 [[痛点是知识管理的唯一动力源|痛点]]）。
   显示文本把一句判断缩成了标签

⛔ 正如「痛点是知识管理的唯一动力源」所言（[[痛点是知识管理的唯一动力源]]），换工具……
   先复述再给链接，同一句话写了两遍
```

### 外来格言：直写，不给链接

外来格言写「引号 + 原文」，**不建链接**。理由不是排版习惯，而是库自己的断链语义：

> `[[断链]]` 的定义是「我认可了这个洞见、但还没把它提炼成独立的 `atomic`」。

所以写 `[[Less is More]]` 等于生产一张**永远不打算清偿的欠条**——每次扫断链医院它都会跳出来问「这句要不要提炼成 atomic」，而正确答案是「不要」：提炼它就是把别人的话写成你的洞见。

```markdown
✅ 本库的设计美学是「Less is More」，落到规则上就是「即用即改」。读法见 [[本库设计原则]]。

⛔ 本库的设计美学是 [[Less is More]]。
   这会产生一条假的待提炼断链
```

外来格言要「有用」，靠的不是链接，是**把它的读法写下来**。同一句格言在不同语境能推出相反结论（「Less is More」既可以读成「内容要少」也可以读成「动作要少」），不写清读法，它就只是漂亮话，而且下一轮讨论会从同一句话推出另一套规则。本库对这句话的读法落在 [[本库设计原则]]，那里也是「即用即改」的出处。

### 引用前的自检

引用一句格言或判断之前问一句：**它在这一处约束了哪个具体决定？** 说不出，说明这里是修辞装饰而不是论据——格言最容易退化成万能论据，正因为它短、读起来对、贴哪儿都行。

另一个信号：**同一句被内联引用十几次**，说明它是那个领域的**公理**，应该住进对应 `concept` 的「核心命题」段（一处完整展开），`atomic` 只保留一次论证。判据是它在多处扮演同一个角色（总前提）吗。

## aliases 前缀速查

| 前缀 | content-type | aliases 示例 |
|------|-------------|--------------|
| `P-` | project | `P-求职` |
| `A-` | area | `A-人工智能` |
| `Q-` | question | `Q-如何学习编程` |
| `MOC-` | moc | `MOC-前端知识地图` |
| `SOP-` | sop | `SOP-周回顾` |
| `T-` | term | `T-TCP` |
| `C-` | concept | `C-闭包` |
| `VS-` | comparison | `VS-React vs Vue` |
| `R-` | record / roadmap / person | `R-俄乌冲突` / `R-Angular-版本演进` / `R-爱因斯坦` |
| （无） | atomic / article / diary | — |

> 注：`R-` 前缀由 record、roadmap、person 三种类型共享，语义不冲突。

## 子主题命名规则

当一个笔记是另一个笔记的子主题时，在 aliases 中添加父级前缀，避免命名混淆。

**命名格式**：`{类型前缀}-{父概念}-{子概念}`

| 场景 | aliases 示例 |
|:---|:---|
| Fiber 是 React 的子概念 | `["C-React-Fiber", "Fiber"]` |
| Fiber 是 React 的子术语 | `["T-React-Fiber", "Fiber"]` |
| 场景图结构 是 ThreeJS 的子概念 | `["C-ThreeJS-场景图结构", "场景图结构"]` |
| 虚拟头节点 是 链表 的子术语 | `["T-链表-虚拟头节点", "虚拟头节点"]` |

**判断标准**：
- 子概念名称通用/易混淆（如 Fiber）→ 必须加父级前缀
- 子概念名称独特/仅限某领域 → 建议加父级前缀
- 子概念是 atomic（陈述句）→ 不需要加前缀

## 目录前缀

数字前缀（`00-` … `99-`）与 `_` 下划线前缀的语义、档位划分、编号约规，全部定义在 [[本库目录结构]] 的「前缀语义」一节，本文件不重复。

## 命名原则

- 采用中文 + 内容描述
- 避免拼音、缩写和无意义编号
- 禁止特殊字符（`? * < > | \ / : "`）
- 文件名只写纯标题，不带类型前缀（前缀进 `aliases`）
- `atomic` 的标题须为陈述句 → 该约束属形态特征，见 [[笔记类型规范]]
