## 目录结构

```bash
content/
├── 00-INBOX/        # 捕获篮（未消化的原始素材，ingest 的唯一入口）
├── 01-META/         # 系统元数据（含 Truth/ 真值、设计指南、规范、索引）
├── 10-PROJECTS/     # project（面向 PARA 项目，有明确目标/截止日期）
├── 20-AREAS/        # area（面向 PARA 领域，需持续关注）
├── 30-RESOURCES/    # 缺省落点（形态已判、无容器归属）
├── 40-ARCHIVE/      # 归档（已完成/过时/孤立节点）
├── 50-ZETTELCASTEN/ # atomic（单形态）
├── 60-BLOGS/        # article（博客文章）
├── 80-PRIVATE/      # 私有内容（敏感信息、API keys 等）
├── 90-DIARY/        # diary（日记，时间序列）
└── 99-ASSETS/       # 额外资源（插件配置、附件等）
```

## 编号约定

> [!important] 数字只定排序，不定语义
> 语义由**目录名里的单词**承载（`PROJECTS`、`AREAS`、`ZETTELCASTEN`……），数字只保证排序稳定、同组相邻。所有顶层目录统一使用 **2 位数字**，位数不承载信息。
> 这不是新规矩：[[本库子系统概述]] 一直写的是「数字前缀排序 + 语义由目录决定」，本节此前却写成「数字前缀承载语义」，两份真值相反。现按前者统一。

**分组只用于归类与取号，不表示生命周期先后。** 证据在本表内：`4x` 是退役，逻辑上排在最后，编号却在 `5x`（`atomic`）之前。原因是 4 是 PARA 的 `Archive` 留下的槽位，不是按流水线分配的；若数字真承载阶段，它应该是 `99`。

### 分组表

| 分组 | 包含什么 | 现有目录 |
|------|---------|---------|
| `0x` | 系统与入口 | `00-INBOX`、`01-META` |
| `1x` | 项目工作区 | `10-PROJECTS` |
| `2x` | 责任领域容器 | `20-AREAS` |
| `3x` | 无容器归属的知识（缺省兜底） | `30-RESOURCES` |
| `4x` | 退役 | `40-ARCHIVE` |
| `5x` | `atomic` | `50-ZETTELCASTEN` |
| `6x` | `article` | `60-BLOGS` |
| `8x` | 不可公开内容 | `80-PRIVATE` |
| `9x` | 时间序列与支撑物 | `90-DIARY`、`99-ASSETS` |

`7x` 空着，留作扩展槽。

> [!note] 「包含什么」是描述，不是准入判据
> 本表只说明某组大致装什么，用来判断新目录该进哪组。**某一篇笔记该不该进某个目录，只看后文「目录侧约定」表的形态约束**，不看本表措辞。例如 5x 写 `atomic` 而不写「原创洞见」：落到 50 的唯一依据是形态为 `atomic`，不考察它由谁写出。

### 编号约规

1. **宽度统一 2 位**（`0x`–`9x`）。不使用 `000-` / `010-` 这类 3 位写法——宽度不携带信息，混用只会制造「`00` 与 `000` 抢同一槽位」的歧义。
2. **十位分组，个位排序**。新增目录先判断属哪一组，再取该组内最小空闲个位号（`0x` 已用 00/01，下一个是 `02`）。
3. **个位号即视觉优先级**。数字小的排在文件树上方，应代表「打开库时最该看见的东西」——故 `00-INBOX`（每日入口）在 `01-META`（低频规范）之上。
4. **留空即预留**。`7x` 空着就空着，作为扩展槽，不为「填满整齐」而占号。
5. **`_` 前缀 = 非知识工件**。`_templates/`、`_scripts/`、`_resources/` 存模板、脚本、附件等支撑物，不参与内容体系；`_` 的码位大于数字，天然排在所有编号目录之后。
6. **禁止无前缀顶层目录**。既无数字又无 `_` 的新顶层目录不得创建；确有需要时，先在本表登记它属哪一组再建目录。

## 归属与形态：两个正交维度

> [!important]
> **一个维度只能有一个权威来源。** 目录回答「这条信息归属于哪一站」，`content-type` 回答「这篇笔记怎么写」。两者**互不推导、互不校验一致性**。

| 维度 | 回答的问题 | 唯一权威 | 取值 |
|------|-----------|---------|------|
| **归属** | 这条信息在生命周期的哪一站？ | **目录路径** | 见「目录结构」 |
| **形态** | 这篇笔记用什么方式写？ | **`content-type` 字段** | 见 [[笔记类型规范]]（14 种） |

### 为什么不再做一一映射

旧模型规定「目录 ↔ content-type 一一对应」（如 `10-PROJECTS/` 只装 `project`）。该规则在实践中已被证伪：

- `10-PROJECTS/` 现有 59 篇笔记中仅 2 篇为 `project`，其余是 `question`（19）、`concept`（18）、`record`（7）等——**项目目录是工作区，不是类型容器**。项目推进过程产生的知识笔记，本就该留在项目里，而不是为了迎合类型被迫搬到 `30-RESOURCES/`。
- `01-META/` 内含 23 篇 `article`、7 篇 `moc`、2 篇 `concept`，同样无法用单一类型概括。
- 一一映射的隐性代价是：**每新增一个目录就要重新定义一次类型归属**，且两处描述必然逐渐漂移——这正是维护负担的来源。

### 目录侧约定（取代旧「决定方式」列）

| 目录 | 归属语义 | 形态约束 |
|------|---------|---------|
| `00-INBOX/` | 未加工原料，全库唯一入口 | 不判形态（待 ingest） |
| `01-META/` | 系统元数据（真值、规范、索引、日志） | 不限（实际以 `article`/`moc`/`sop` 为主） |
| `10-PROJECTS/` | **项目工作区**（`P-XXX/`），装项目全过程笔记 | 不限；`project` 仅标记该工作区的主页 |
| `20-AREAS/` | **领域容器**（`A-XXX/`） | 以 `area` 为主，边界见「20-AREAS 边界」一节 |
| `30-RESOURCES/` | **缺省落点**（形态已判、无容器归属） | 不限；出口三条见「30-RESOURCES 的边界」一节 |
| `40-ARCHIVE/` | 退役，免维护 | 不校验 |
| `50-ZETTELCASTEN/` | `atomic` 的家 | **单形态**：`atomic` |
| `60-BLOGS/` | 对外发布的成文 | **单形态**：`article` |
| `80-PRIVATE/` | 不可公开内容 | 不限 |
| `90-DIARY/` | 时间序列 | **单形态**：`diary` |
| `99-ASSETS/` | 附件与插件配置 | 不判 |

> **「单形态」是目录侧约束**（该目录只接受一个取值），性质上不是「类型→目录」的映射。其余目录的形态取值不参与位置判断，也不做一致性校验。

### 归属判定顺序

新建笔记时按以下顺序落地，**不按类型反推目录**。这七步不是一条排序，而是两套判据分管：1–2 步判容器归属，3–5 步判形态所在的单形态目录，6 是缺省，7 是未判。两套互不竞争——形态不影响归属，归属不影响形态，因此不需要统一优先级。

1. 属于某个已有项目的工作过程？→ 该项目目录 `10-PROJECTS/P-XXX/`
2. 是某个领域的主页或其周边资料？→ `20-AREAS/A-XXX/`（判定见「20-AREAS 边界」）
3. 形态是 `atomic`（标题即陈述句观点，正文三段见 [[atomic 设计]]）？→ `50-ZETTELCASTEN/`
4. 是对外发布的长文？→ `60-BLOGS/`
5. 是当天的时间记录？→ `90-DIARY/`
6. 其余独立知识 → `30-RESOURCES/`
7. 尚未判断 → `00-INBOX/`

归属定完，再单独填 `content-type`。**不存在「选了 concept 所以必须放 30-RESOURCES」这类反向约束**——concept 最常见的归属是 `30-RESOURCES/`，但项目里提炼的概念也可以留在项目目录，形态照填 `concept`。

## 30-RESOURCES 的边界（缺省目录）

`30-RESOURCES` 没有入口判据，位置由排除法得出：上文「归属判定顺序」1–5 步都不成立时落在这里。这是缺省目录的正常形态——它不需要正面定义「装什么」。

但排除法只能保证「不属于别处」，保证不了「该不该留」。缺省目录的真实风险从来不是进错，而是**出不去**：一篇三年前的二手概念，七步排除全部通过，落进 30，此后不再有任何动作会碰到它。它不违反任何边界，却违反了「用得上」。

所以 30 的判据在出口，只有三条：

| 出口 | 触发条件 | 去向 |
|:--|:--|:--|
| 形态已够 `atomic` | 标题是陈述句观点，正文齐备「观点 + 边界 + 论据」（见 [[atomic 设计]]）；不看由谁写出 | `50-ZETTELCASTEN/` |
| 不再服务任何当前的东西 | 内容过时，且没有笔记再引用它 | `40-ARCHIVE/` |
| 是某项目的过程产物 | 它能回答「P-XXX 进行中遇到的问题」 | 该项目目录 |

三条都不成立 → 留在 `30-RESOURCES`，合法，不需要为它的存在找理由。

> [!note] 与 `00-INBOX` 的区别
> 两者都「不知道放哪」，区别在**处理到哪一步**：`00-INBOX` 是形态未判（还没读、没整合），`30-RESOURCES` 是形态已判、无容器（读过、写过）。可操作判据：**能填出 `content-type` 的，就不该留在 00**。这也是前者不计入知识资产、后者计入的原因（见「其他约定」）。

## 其他约定

- **判据决定**：`40-ARCHIVE/` 由**单篇是否还有用**决定，不由「所属项目是否结束」决定。项目结束只触发一次逐篇判定，判定表见 [[元数据规范]] 的「项目结束：触发逐篇判断」。非新建目录
- **临时中转**：`00-INBOX/` 是唯一的「未分类捕获区」，不承担 content-type 归属；任何内容进入后都必须在 ingest 时判定类型并迁出，不常驻
- **不计入资产**：`00-INBOX/` 的内容属于**未加工原料**，不参与「知识资产」统计（日记的今日沉淀面板、wiki-index、领域索引均排除该目录）。只有迁出并完成 ingest 的内容才算沉淀

## 20-AREAS 边界（领域容器规则）

> [!note] 一个领域 = 一个目录 = 一份 area 笔记
> `20-AREAS/` 的**目录是「责任领域」的容器，不是「同类文件的堆」**。判断某文件该不该进 20-AREAS，只看一个问题：

**「这是我要长期负责的领域，还是我要弄懂的知识？」**

| 判断 | 归属 | 位置 |
|------|------|------|
| 需长期负责、有长期目标的**责任领域** | `area` | `20-AREAS/`，一份 `XX.md` = 一个子目录 |
| 需弄懂的**概念 / 术语 / 问题 / 索引** | `concept` / `term` / `question` / `moc` 等 | `30-RESOURCES/`，用 `up: "[[领域]]"` 挂回 area |

- **目录结构**：一个领域目录里通常只有 1 份 `XX.md`（area 本身）+ `_resources/`（图片等附件）。`A-知识管理/` 下只有一份 `知识管理.md` 是**正常的**，不是缺失。
- **领域层级**：子领域也是 `area`，挂在更宏观的 area 下（如 `A-前端/前端开发.md` ← `A-前端/JavaScript.md`，`up: "[[前端开发]]"`）。
- **知识挂载**：围绕领域沉淀出的概念/术语/问题，**不放在领域目录里**，而是放 `30-RESOURCES/`，通过 `up` 字段指回领域（如 `类型收窄`（term）`up: "[[TypeScript]]"`）。物理位置分离、逻辑关系靠 up 维持。
- **易踩错位**：把「围绕领域的知识」（concept/term/question）跟「领域本身」（area）混放在一个目录里，导致 20-AREAS 膨胀。这是最常见的方向性错误——判断口诀「**领域问『我负责什么』，知识问『我懂什么』**」。

## 40-ARCHIVE 免维护约定

> [!note] 归档目录是「免维护区」
> 40-ARCHIVE 只用于**丢弃**过期、废弃、不再活跃的笔记，**不关心其 content-type 或 frontmatter 是否规范**。
> - 笔记丢进 40-ARCHIVE 即代表「我不再维护它」，无需再花精力规整其元数据、类型标注、链接。
> - 治理规则（content-type 对齐、挖空、断链修复等）**只作用于活跃目录**（30-RESOURCES、50-ZETTELCASTEN 等），不作用于 40-ARCHIVE。
> - **免维护不等于免判断**：进来之前判一次，且只判这一篇还有没有用。整目录搬进来会把仍有效的资产一并免掉调用——这正是这个区能免维护的前提被反过来用。

## 维护归属

> [!note] 下表是「物理上的精力分配」，**不是「谁写内容」的边界**。人机分工的唯一真值见 [[人机分工规范]]——人类负责内容、AI 负责包装，按职责而非目录划分。

| 目录 | 维护方 |
|------|--------|
| 00-INBOX | 人类捕获 + AI 消化（临时区，不长期留存） |
| 01-META、10-PROJECTS、50-ZETTELCASTEN、90-DIARY | 人类维护 |
| 30-RESOURCES、40-ARCHIVE、60-BLOGS、99-ASSETS | AI 维护包装（内容可能来自人或 AI） |
