> [!important]
> 本文件是「知识图谱」一节**桶名的唯一真值**。新写或批量改写时只从下表取词，不再造同义词。
> 2026-10-27 收口前，全库出现过 70 种写法（`父级概念`、`母 MOC`、`技术栈关联`、`延伸阅读`……），同一件事最多有五个名字。
> 2026-10-28：**`并列` 的判据去掉了「共享同一个上位」这一条**，`相关` 相应交出「对比」。两者新的边界见 [[知识图谱词表#`并列` 与 `相关` 的边界（2026-10-28 放宽）]]。

## 六个桶

| 桶 | 回答的问题 | 判据 | 适用范围 |
|:---|:---|:---|:---|
| `上位` | 什么比它更一般 | 本笔记是目标的实例、特例或子类 | 全部类型 |
| `下位` | 什么比它更具体 | 目标从属于本笔记：本笔记的结论在它身上成立，且它多了额外限定 | 全部类型 |
| `并列` | 谁和它同层 | 抽象层级相同，可以并排放进同一个抽屉：同类的一个实例、可互替的方案、同一问题的另一种解法。**不要求有共同上位** | 全部类型 |
| `相关` | 还有什么跟它有关 | 有单向联系，但既说不清一般/特殊，也说不清同层：演进、依赖、工具链、人物、出处 | 全部类型 |
| `外部资料` | 库外有什么 | 目标不是本库笔记：文献、文章、官网、仓库 | 全部类型 |
| `问题来源` | 这条流程从哪个问题收敛来 | `question` → `sop` 的血缘，不是概念关系 | 仅 `sop` |

判定顺序（防止二义）：先问「目标是不是库外链接」→ `外部资料`；再问「是不是 Q→SOP 血缘」→ `问题来源`；剩下按「更一般 / 更具体 / 同层」判，判不出来就落 `相关`。**`相关` 是默认桶，不是次选。**

桶里装什么由关系决定，与目标类型无关：`下位` 里可以是 `term`、`atomic`，也可以是 `concept`，只要它比本笔记具体。

### `并列` 与 `相关` 的边界（2026-10-28 放宽）

放宽前的定义是「与本体共享同一个上位，互不从属」。它排除掉了奥苏贝尔明确属于并列结合的一类情形：**并列恰恰可以没有共同上位**——正因为没有，才只能靠一般性内容固定，才最难。定义一窄就判不出，判不出就落 `相关`，于是 `相关` 成了最大的桶（2026-10-28 实测 793 条，占 52%；`并列` 只有 217 条，14%）。

判据换成一句话：**能不能并排放进同一个抽屉。**

| 问 | 是 → | 否 → |
|:--|:--|:--|
| 两者各自独立成立吗（谁都不需要谁才成立） | `并列` | `相关` |
| 抽象层级相同吗（都是框架、都是协议、都是一类攻击） | `并列` | 回到「更一般 / 更具体」判 |
| 关系能写成「A 用到了 B」「B 是 A 的老版本」「B 是 A 的一部分」吗 | `相关` | `并列` |

三个例子：`Vue` 与 `React` 是并列（同类框架、可互替、各自成立）；`Vue` 与 `Vue版本演进` 是相关（后者是前者的时间线，单向）；`CORS` 与 `HTTP` 是相关（前者建立在后者之上，单向依赖）。

**反判据（防吞并）**：一放宽，最省事的写法会变成「把两个都认识的词放一起」。所以补一条：并列的两项必须能被一句共同的话概括——「它们都是 ___」。这个空填不出来，就不是并列。

**`comparison` 的被比较对象不进关系桶。** `Angular vs React` 里的两个框架是这篇笔记的**材料**，不是它的关系；它们已经写在首段的对比对象里，再进 `相关` 只是复述。comparison 的 `并列` 应当是**其他同类对比笔记**（`Vue vs React`、`Vue2 vs Vue3`），对比族才连得起来。同理 `React.memo vs useMemo` 指向 `React.memo`、`useMemo` 不算并列——那篇讲的是两者的差别，不是它们与别的东西同级。

## 与 `up` 的分工：归档位置 vs 认知层级（2026-10-27 定）

`up` 和 `上位` 不是同一件事，**不一致不算缺陷**——本条要消掉的就是这个误判。

| | `up`（frontmatter） | `上位`（正文知识图谱） |
|:---|:---|:---|
| 回答 | 这篇笔记挂在树上哪一篇下面 | 哪个概念比它更一般 |
| 关系 | 整体—部分（容器） | 一般—特殊（抽象层级） |
| 判据 | 「如果只能放一个地方，放哪」 | 「它是哪一类东西的一个实例」 |
| 缺省 | 应填；空着是待办信号 | 可以没有：834 个节点里 557 篇一个桶都没有（67%），见「现状」 |

两者常常重合——实测 144 篇可比对里 123 篇相同（85%）。不重合时**两边都对**：

| 笔记 | `up` | `上位` | 差在哪 |
|:--|:--|:--|:--|
| `Reflect` | ES2015 | 元编程 | ES2015 是包含它的规范版本（容器），元编程是它所属的类别（抽象） |
| `Angular版本演进` | Angular | 前端框架 | 前者是同一条版本线，后者是它所在的那一层 |
| `CSRF` | Web安全问题 | 浏览器安全机制 | 前者是问题清单里的位置，后者是机制归属 |

所以：**不要为了让两处一致去改其中一处。** 10-27 之前的核查把 21 篇（15%）判成「`up` 与父级不一致」，是因为当时把 `up` 当成「父级概念」的同义词；分工定下后，这 21 篇不需要动。

> 这里的「归档位置」指知识树上的挂载点，与 40-ARCHIVE 的退役归档无关（后者见 [[元数据规范]] 的归档语义）。

## 六个词的来源

| 词 | 出自 |
|:--|:--|
| `上位` / `下位` | 2026-10-27 新定名。收口前写作 `父级概念`/`父级领域`/`父级 Hook`/`母领域`/`母 MOC`/`上级`/`上游` 与 `子级概念`/`子集概念`/`下位概念`/`基础组件`/`深入主题`。词借自术语学的上位词 / 下位词（hypernym / hyponym）。**不用「父级」正是为了跟 `up` 的父级语义分开**——见上一节 |
| `并列` | 沿用 `_templates/template_concept.md` 原有的 `并列概念` 桶，去掉「概念」二字：桶里常常装的是 `term` 或 `atomic` |
| `相关` | 沿用原有的 `相关概念` 桶，同样去掉「概念」二字；并接收 `关联概念`/`演进关系`/`相关对比`/`技术栈关联`/`相关工具`/`生态库`/`相关人物` |
| `外部资料` | 沿用原有的 `参考文章` 桶，接收 `参考来源`/`参考资源`/`延伸阅读`——这四者本来是同一件事 |
| `问题来源` | 沿用 `_templates/template_sop.md` 原有写法，未改名。它是唯一的非概念关系桶，收口时整体保留 |

## 只借了三个：六桶的构成（2026-10-28 补）

前三个桶借自奥苏贝尔的三型同化，后三个不是。把它们并列说成「六桶来自有意义学习」，会让人以为按理论补全就能得到完整词表——事实相反，补全的代价是丢掉近一半的边。

| 组 | 桶 | 身份 | 为什么是它 |
|:--|:--|:--|:--|
| 借来的 | `上位` `下位` `并列` | 奥苏贝尔三型同化 | 借了名，只借到「分类」这一层；「同化」那一层要自己补（见下） |
| 工程补 | `相关` `外部资料` | 本库自造 | 奥苏贝尔框架里没有对应位置，而知识库里这两类联系大量存在 |
| 血缘 | `问题来源` | 本库自造 | 它是 `question → sop` 的谱系，不是认知关系 |

三条不借全的理由：

1. **三型同化描述的是「意义如何产生」，不是「关系如何记录」。** 它的单位是「新知识被哪个旧观念接住」，只回答纵向。横向两个同级项之间，奥苏贝尔只说「并列结合」，并且明确它最难、最不稳——这不是适合当存储结构的基础。
2. **`外部资料` 在他的框架里不存在。** 书、文章、仓库不是知识单元，没有「被接住」这回事。它是书目字段。
3. **`相关` 在他的框架里等于「没发生有意义学习」。** 本库保留它，是工程决定：先把边建起来，之后再判断有没有意义。这不是理论缺陷，但必须写明——否则会有人拿「奥苏贝尔没有这个桶」去删掉 793 条真实存在的联系——那是全部 wiki 边（1527 条）的 **52%**。`外部资料` 同理：它装的是书与网址，不是知识单元，所以它是唯一一个不计入「边」的桶。

**借来的那一半其实也是缺的。** 三型同化给的是桶名，没给判据里最要紧的那一问：这个上位**真的**起过固着作用吗。奥苏贝尔的下位同化，前提是旧观念真的接住了新知识；而本库 `下位` 的判据只是逻辑包含（本笔记的结论在它身上成立 + 它多了限定），不检查目标是否真从本笔记获得过意义。所以能写出「逻辑上从属、认知上从不互相引用」的假下位。补判据只需一问：**我写那篇的时候，真的回头读过这一篇吗？** 答不上来，它是分类，不是同化。

**`相关` 同时是仪表。** 它长期是最大的桶（现 793 条 / 52%），不是笔记写得差，而是判据在实践中不够用的信号。占比上升，说明某条判据太窄（2026-10-28 放宽 `并列` 正是照这条信号做的）；占比下降，说明分类在收敛。所以不要以「消灭 `相关`」为目标——那会逼出大量假边。

> [!warning] 统计这个数必须先想清口径，两次都错过
> **2026-10-27 的旧快照（752 处）**只统计 `concept` 与少数几类，且用的是多行正则——它会把后面几个桶的条目一并算进第一个桶，所以那个数字既偏窄又偏串。
