## content-type 总览

> [!important]
> `content-type` 只描述**形态**（这篇笔记怎么写），**不描述位置**。它不映射到目录，也不与目录做一致性校验——归属由目录决定，见 [[本库目录结构]]。
> 本表因此不含「目录」列：同一种形态可以落在不同归属里（例如 `concept` 多数在 `30-RESOURCES/`，也可以是某个项目工作区里的概念笔记）。

| 类型 | content-type | aliases 前缀 | 文件名示例 | 定义 |
|------|-------------|-------------|-----------|------|
| 原子笔记 | `atomic` | 无 | `闭包的本质是…md` | 一句话命题，标题即结论（主观洞见或已成命题形式的客观机制） |
| 概念笔记 | `concept` | `C-` | `闭包.md` | 概念整合与系统理解 |
| 术语笔记 | `term` | `T-` | `TCP.md` | 术语客观定义 |
| 标准流程 | `sop` | `SOP-` | `周回顾.md` | 标准化操作流程 |
| 问题笔记 | `question` | `Q-` | `如何学习编程.md` | 开放性问题探索 |
| 比较笔记 | `comparison` | `VS-` | `React vs Vue.md` | 对比分析 |
| 记录 | `record` | `R-` | `俄乌冲突.md` | 外部事实落地页：事件、素材、信源 |
| 演进路线 | `roadmap` | `R-` | `Angular版本演进.md` | 版本演进时间线 |
| 人物笔记 | `person` | `R-` | `爱因斯坦.md` | 人物生平与思想记录 |
| 索引地图 | `moc` | `MOC-` | `前端知识地图.md` | 领域入口与索引 |
| 领域笔记 | `area` | `A-` | `人工智能.md` | 责任范围与长期目标 |
| 项目笔记 | `project` | `P-` | `求职.md` | 有明确截止日期的任务 |
| 博客文章 | `article` | 无 | `如何学习React.md` | 长篇主题文章 |
| 日记 | `diary` | 无 | `2026-07-17.md` | 时间序列记录 |

> 「aliases 前缀」列是**类型属性视图**，前缀的取值规则、子主题写法、与文件名的分工以 [[文件名与别名规范]] 为准。
> `atomic` 的标题须为陈述句——这是形态特征而非命名规则，故在此定义，不进 [[文件名与别名规范]]。

### atomic 与 concept 的分界：看形式，不看主客观

曾误以为 atomic 必须是「主观洞见」、客观机制一律归 concept。**这个判据不成立。**

客观机制一旦以命题形式陈述，它就是 atomic。强行改写成主观话语只是换个说法，不增加信息，还会丢掉精确性。

| 判据 | atomic | concept |
|:--|:--|:--|
| 标题 | 一个**可判断真假**的命题 | 一个**主题名或机制名** |
| 读完以后 | 你多了一条判断依据 | 你多了一套理解 |
| 结构 | 一句话 + 边界（+ 可选一个论据） | 定义 + 机制 + 演进 + 示例，可分多节 |

三个例子：

- ✅ **atomic**（客观但已成命题）：`CORS简单请求不发送预检而复杂请求会发送预检请求`
- ✅ **atomic**（主观洞见）：`痛点是知识管理的唯一动力源`
- ⛔ **该是 concept**：`CORS是浏览器允许服务端控制跨域访问的机制`——标题是「X 是 Y 机制」的定义式，正文展开工作原理、关键响应头、为什么需要，那是理解而非断言。定义本身归 [[CORS]]；若想留下一条 atomic，就得改写成命题，如 [[CORS的约束只在浏览器侧生效，服务端无法单方面实施]]

一句话判据：**读完这一篇，你是「知道了一条可以拿去判断的依据」，还是「理解了一套运作方式」？** 前者 atomic，后者 concept。

### atomic 标题的第一关：主语可指认

`atomic` 标题会在**离开本文的任何地方单独出现**——被 concept 引用成 `[[...]]`、出现在文件列表与图谱、出现在搜索结果里。所以它得先过一关，比「可判断真假」更前置：

> 把标题抄到一张白纸上，问：**这句话说的是哪个对象上的事？** 若要翻回 `up` 字段、目录路径或正文才能回答，这句话就没有主语。

主语悬空时无所谓真假——读者连它在说什么都不确定，谈不上检验。所以顺序是**先主语，后真假**，反过来的检查会漏掉整整一类残句。

下表两个例子取自 2026-10-28 全库体检里真实犯过的病例（左列是当时的标题，右列是补法）。这是病征演示，不是当前的待修清单——库里现存的篇目以 `.claude/agents/atomic-title-reviewer.md` 的判定为准。

| 病征 | 悬空 | 指认得出 |
|:--|:--|:--|
| 砍掉定语的简称 | `两阶段模型只管单次进入` | `执行上下文的两阶段模型只管单次进入` |
| 行业泛称当专名 | `优先级调度只决定谁先跑` | `React 的优先级调度只决定谁先跑` |
| 引用式主语不交代出处 | `「一句话说清」是观点成形的结果` | `「一句话说清」这个拆分判据是观点成形的结果，不是判据本身` |
| 靠 up 才补全的主体 | `Tool 的执行权在 Runtime 手中` | `Agent 的工具执行权在 Runtime 手中，不在 LLM` |

**反向护栏：不自足 ≠ 必须写全称。** `Fiber`、`IndexedDB`、`WebSocket`、`CORS`、`localStorage` 这类全库唯一且业内公认的专名可以直接裸用，补成全称只会让标题变笨。要限定的是两种：**本身是泛称**（调度 / 依赖图 / 多路复用 / 框架 / 宏），以及**库里存在同名兄弟**（`Context` 同时指 React Context 与 Context Engineering，两边都得带限定）。

一句话判据：**标题里那个东西，能不能被指着说「就是这个」？**

### atomic 的正文结构：观点 + 边界 + 至多一个论据

atomic 只该有三种成分，其中「边界」是最常被写错、也最常被整格漏掉的一格：

| 成分 | 写什么 | 常见错误 |
|:--|:--|:--|
| 观点 | 标题那一句本身，正文不必复述 | 先复述标题再展开 |
| **边界** | 什么时候不成立、适用条件、代价，**它给观点划范围** | 把限定当论据写，于是越写越长 |
| 论据 | 至多一个能支撑观点的具体事实、反例或机制 | 一口气列出 3-5 条并列论据 |

判据只有一句：**这句话是在支撑观点，还是在给观点划范围？** 支撑 → 论据；划范围 → 边界。放错格子的后果不是写错，而是「论据格越写越长，边界格永远空着」——读者最终拿到的是一条不知道何时失效的断言。

由此得到一个固定病灶与它的唯一改法：

- **`## 论据/示例` 下再套 `### 论据 / ### 示例 / ### 推论`**。父标题本身就是多余的层，但机械把 `###` 降成 `##` 治不了——病根是里面有 3-5 条论据。只能整篇重写成「观点 + 边界 + 一段论据」。**出现 `### 论据` 基本等于宣告这篇该瘦身。**
- 反过来的信号：一篇 atomic 的自定义章节名，只有两种合法成分——**机制展开**（工作原理 / 实现方式 / 条件清单）属 concept，**限定**（注意事项 / 为什么需要 / 适用场景）属本节说的「边界」。各归各位之后，剩下的通常不够一个 `## 论据` 节，所以这类篇的动作是**补边界**，不是删内容。

瘦身顺序：**先读它的 `up` 概念，再删 atomic**。超过 500 字的 atomic，超出的部分几乎都能在父概念里找到，删掉的是重复，不是知识。

## 各类型定位

| content-type | 定位（一句话） |
|-------------|--------------|
| `atomic` | source of truth，单一洞察/观点，永不归档、永不删除 |
| `concept` | 概念总览与整合，解释「为什么」或「如何运作」（有「核心命题」段，是 atomic 的原料库） |
| `term` | 术语客观定义（来自文献），被 concept 引用 |
| `sop` | 可重复且步骤确定的标准流程，Question 的收敛态之一（另一种是 atomic）；可信度不由结构齐保证，由模板的「验证记录」与「依赖／失效条件」两段支撑 |
| `question` | 开放性问题探索，SOP 的「发散前身」 |
| `comparison` | 对比分析，跨越多个概念 |
| `record` | 外部事实的落地页，事件/素材附我的评价，注记只留事实（四种形态见下） |
| `roadmap` | 线性演进路线图，版本迭代/技术发展时间线 |
| `person` | 客观记录人物生平，附带思想观点提炼 |
| `moc` | 领域入口与索引，只做索引不做消化（「消化禁令」见下：一旦写原理就下沉为 concept） |
| `area` | 责任范围，需持续关注，必须有长期目标 |
| `project` | 有明确目标和截止日期的任务／工作区主页 |
| `article` | 长篇主题文章 |
| `diary` | 时间序列记录 |

### record 的四种形态

record 不是「事件类型」，是**外部事实的落地页**：凡不是我原创、有客观基础、有明确边界的东西，都归它。四形态共用 `template_record.md`（信源除外）：

| 形态 | 中段写什么 | 最低要求 | 例 |
|:---|:---|:---|:---|
| 事件 | 时间线、背景、影响 | 时间 + 出处 | 俄乌冲突、项目里程碑 |
| 素材 | 核心命题、关键论点、摘录 | 原文出处 | 一篇论文、一期播客、一本书 |
| 注记 | 一句事实，不写评价 | 一句话 + 一个出处 | 某个版本的行为差异、一条命令、一个参数 |
| 信源 | 不套本模板，走 `template_source.md` | 五维评分 | 一个 RSS、一个频道、一个人 |

**与 atomic 的分界不是题材，是归属**：同一篇论文，记「它说了什么」是 record，记「因此我认为 X」是 atomic。剪藏默认落 record，不落 atomic——后者是判断，只能由人下。

两个挂载位决定它是否只是孤立存档：

- `## 来源` 向上挂信源卡，一篇素材 = 该源的一条消费。
- `## 产出` 向下挂知识资产（atomic / concept / term / sop / comparison，**不含其他 record**），一条 = 该源的一条 ingest。

`up` 不指向信源——它表示知识归属，信源走 `## 来源`。两者的区分与用途见 [[元数据规范#up 的写法]]，产出率的计数口径见 [[信源质量审计标准]]。

#### 注记：一句话的那一档（2026-10-28 增）

注记是 record 里成本最低的一档，为「不常用、注释性质、一句话就够」的事实而设。它**不要求「我的评价」**——那一格留空是它的定义，不是缺陷；一旦写下评价，它自动升格为素材。

仓库里没有为它另立 `content-type`，原因是「简单」是长度不是形态：本库已经两次否决按程度划分类型（atomic 的主客观、sop 的能不能写死步骤），两次的理由相同——判据会随人和时间漂移。今天一句话、明天补两行，类型若跟着改，模板、枚举、视图都要跟着动。

两条判据：

- **能被反驳的是判断，归 `atomic`；只能被核实的是事实，归注记。** 「某版本在 fixed 定位下 `backdrop-filter` 失效」只能被核实，是注记；「讲不清一个概念说明没懂」能被反驳，是 atomic。判断混进注记，它就会以「已经记过了」的姿态躲掉该有的边界。
- **`up` 指向被注释的那一篇。** 注记按定义是对某个东西的补充说明，对象必然存在；`up` 因此不是额外成本，而是它日后被找到的理由。确实没有对象的（一条命令、一个参数），`up` 可空，但必须留一个可检索的落点：`url` 或 `tags`。

**最低要求只有两条：一句事实 + 一个出处**（`url` 字段，或 `## 来源` 一行）。只有标题、正文为空的卡片不算注记，是空壳。这条线守的不是格式，是它「事实」的身份：没有出处的一句话是传闻，传闻不进知识库。它也只需要「来源」这一个挂载位，不要求「产出」——一篇注记多半催生不出知识资产，那不算缺陷。

**升级触发**：注记被第二次引用（backlink ≥ 2）时，补成 atomic 或 concept。这一条不靠灵感靠查询——「以后有需求自然会写」已被证伪：库里存在一批一年以上、正文不足 200 字符、始终没有长大的笔记。需求来自使用，而使用的前提是被找到。

## 形态与归属的边界

三条约定划清两个维度的职责：

1. **`project` / `area` 是「主页角色」，不是位置标签**。它们标记的是「同一工作区里哪一篇是入口」，用于从几十篇笔记中定位主页（例：`P-Agent求职/` 56 篇中仅 `Agent求职.md` 为 `project`）。工作区里其余笔记照常填真实形态（`question`/`concept`/`record`…）。
2. **形态不决定去哪个目录**。不要因为「这是 concept」就把项目里提炼的概念搬去 `30-RESOURCES/`；归属看内容属于哪个工作区，形态看怎么写，两件事分开判断。
3. **反向仍有一条硬约束**：三个单形态目录只接受唯一取值——`50-ZETTELCASTEN/` 必 `atomic`、`60-BLOGS/` 必 `article`、`90-DIARY/` 必 `diary`。这是目录对形态的**单向限制**，不是类型到目录的映射。

> 校验口径随之调整：核查时不再比对「目录与类型是否一致」，只校验 ① 取值属本表 14 种合法枚举；② 上述三个单形态目录的取值是否合规。`10-PROJECTS/`、`20-AREAS/`、`01-META/` 内的形态取值为「不限」，不构成缺陷。


## atomic 与 Anki：新笔记不挖空（2026-10-24 起）

> **存量 222 篇的 `~~挖空~~` 保留不动**——不清理、不批量删除。新建 atomic 不再写挖空。

这是一个明确取舍，不是纠正错误：

| | Cloze（挖空） | Basic（不挖空） |
|:--|:--|:--|
| 卡片正面 | 句子 + 空格 | 完整观点句 |
| 复习动作 | 强制回忆那个词 | 读到观点，自评能否展开 |
| 复习强度 | 高 | 中——少了强制回忆环节 |
| 制作成本 | 每次都要判断「哪个词是关键机制词」 | 零成本 |

选 Basic 的理由是**成本不对称**：挖空要求每次写笔记多做一次判断，而这个判断经常做不准（实测有 `~~同步写法，~~` 把逗号一起挖进去的写法，说明「只挖 1~2 个机制词」这条规则实际没被执行）。

省下的成本可以直接换成更多篇 atomic。**卡面本身就有复习价值——看到观点、自问能不能展开，这个过程已经发生；少了问答环节只是强度下降，不是归零。**

因此：

- **新笔记**：正文不写 `~~挖空~~`，同步到 Anki 是 Basic 卡（整篇一卡正面）
- **存量**：保留 `~~`，同步过去仍是 Cloze 卡，形态不变。两种卡并存，可接受
- `noteId` 不要手动删除——已同步的卡片有复习记录挂在上面

其余与切卡相关的约定仍然有效：

- 正文不要出现孤立的 `---`（避免被任何切卡逻辑误判为分隔符）
- `tags` 若仍同步，会被当作 Anki 标签
- `## 论据/示例` 与 `## 关联` 属于论证与连接，从来就不参与挖空

## 断链与 atomic 提炼

> [!note] 断链 = 尚未掌握完全的知识
> 知识库中的 `[[断链]]`（被引用但对应文件不存在的标题）**不是错误**，而是一个「待办标记」——它代表「我认可了这个洞见、并在别处引用了它，但还没把它提炼成独立的 atomic 掌握」。
>
> - **断链是知识治理的信号**：看到断链，意味着这里有「悬而未决」的知识，值得提炼成 atomic 来消化。
> - **提炼断链 = 补全知识**：从断链标题创建 atomic，本质是「消化一个已被认可的洞见」，批量创建 atomic 只是副产品。
> - **优先级**：断链标题（已被 concept 认可）> 误放的 atomic（已写好但位置错）> 裸陈述句（尚未成文的洞见）。

### 断链的三类判断

| 现象 | 含义 | 处理 |
|------|------|------|
| 标题在全库搜不到同名文件，只在 concept 的 `[[...]]` 里被引用 | **断链**（洞见被认可但未成文） | 提炼成 atomic |
| 标题在 30-RESOURCES 有同名文件，但 content-type 是 atomic | **误放**（atomic 写好了但位置错） | 移到 50-ZETTELCASTEN |
| 标题在 30-RESOURCES 有同名文件，content-type 也正确 | 正常引用（非 atomic） | 无需处理 |

> [!important] 日记的创建链路（2026-10-25 定）
> 职责拆成两段：**Daily Notes 只负责在 `90-DIARY/` 建空文件**（`.obsidian/daily-notes.json` 的 `template` 已清空），**模板填充交给 Templater 的文件夹触发器**（`folder_templates`: `90-DIARY` → `template_diary.md`）。
>
> 根因：Daily Notes 是核心插件，只会替换 `{{date}}` / `{{title}}` 这类语法，**完全不认 `<% %>`**。此前 daily-notes 的 `template` 直指 `template_diary.md`，于是每次新建日记都原样铺上 `<% tp.file.creation_date(...) %>` 占位符，而 uid 是唯一不会被 Linter 兜底覆盖的字段，于是被肉眼发现。title 与 date-created 之所以看着正常，是 Linter 的 `yaml-title` / `yaml-timestamp` 事后补的。
>
> 由此定下一条硬约束：**全库模板只有一套占位符语法 `<% %>`**。Daily Notes、核心 Templates 插件都不渲染它，只有 Templater 渲染；任何模板不该交给它们套用。

## 类型辨析（判断标准）

- **atomic vs concept vs term**：想表达「洞察/观点」→ atomic；想表达「术语/定义」→ term；想做「概念整合和索引」→ concept
- **atomic vs record 注记**：这句话能被反驳吗？能（有真假、需要划边界）→ atomic；只能被核实（有对错但不需要边界，有出处就够）→ record 注记。一句话不等于简单笔记，它是判断还是事实，决定它去哪
- **area vs concept vs moc**：需要「深入学习并应用到项目」→ area（有长期目标）；只是「了解某技术」→ concept 或 moc（无目标）
- **sop vs question**：判据是**有没有值得留下的岔路**——有分岔且分岔本身有价值 → question；只剩一条路且这条路以后要照做 → sop。**不是**「能不能写死步骤」（那随说话人的水平漂移，同一件事三个月前写不出、现在随手就写），也**不是**「跑没跑通过」——没跑过的流程也可以写成 sop，只是「验证记录」留空，那是有效数据，不是待办

### sop 与 question：同一条轴，允许同主题并存（2026-10-27 定）

其余 12 种类型描述的是**知识形态**（这坨东西长什么样），彼此互斥；只有 `question` 与 `sop` 多带一层**阶段**属性，回答的是「我在这个主题上做到哪一步」。同一条知识因此可以先后经过两者。

| 组合 | 是否允许 | 说明 |
|:--|:--|:--|
| 同主题 `question` + `sop` | ✅ | Q 是发散期的探索记录，SOP 是收敛后的动作序列，并存是设计意图 |
| 同主题 `question` + `atomic` | ✅ | 答案是一句断言而非一套动作时，收敛产物是 atomic；不过 atomic 仍是独立命题，不是 Q 的摘要 |
| 同主题其余任意两种 | ❌ | `concept` / `term` / `atomic` 之间是互斥形态，重复即重复建设 |

**收敛目标的形状判据**：答案是**一套可以照做的动作** → SOP；答案是**一句可判断真假的断言** → atomic。一条 Q 可以同时收敛出两者，实测已有此例（`HTTP2在丢包环境下为什么会性能倒退` 同时挂一条 SOP 与一条 atomic）。

「如何实现 Promise」与「手写Promise」不是两个主题、也不是两种类型，而是同一主题的两个刻度。**标题句式（问句 / 名词）不参与类型判断**——把「手写Promise」改成「如何手写 Promise？」不该让它变成 Q。

并存时的分工由三条硬约束固定：

1. **收敛动作是另建目标笔记（SOP 或 atomic），不是改造 Q**。在 Q 的 `## 收敛` 打勾留链接。把 Q 就地改写成目标笔记会让被否掉的方案一起消失，而那些方案恰是 Q 存在的理由。
2. **收敛后的 Q 冻结正文**，只在收敛行追加日期。否则两篇互相漂移，读者不知道该信哪个。
3. **验证记录归 SOP，不归 Q**。Q 的 `## 待验证` 只是未验证假设的清单，证据写进 SOP 的「验证记录」段——「我实现了」是 Q 的合法终点，「我证明它对了」才是 SOP 的起点。收敛到 atomic 时没有验证记录段，证据随那条 atomic 的论据一并写明。

现状（2026-10-27 核查）：全库 15 篇 Q 带 `## 收敛`，共 16 条收敛记录，其中 15 条指向 SOP、1 条指向 atomic；多数 SOP 仍是独立另起、与 Q 无链接。这是执行缺口，不是规范缺口。

### MOC vs concept 边界（消化禁令）

> 三层粒度模型：`area`（宏观，责任视角）→ `moc`（中观，导航视角）→ `concept`（微观，概念视角）→ `atomic`（最小洞见）。MOC 与 concept 是这条链上最易混淆的一环，边界规则如下：

| 判定维度 | `moc`（只索引不消化） | `concept`（解释与整合） |
|---------|----------------------|------------------------|
| 核心动作 | **分类**：把笔记按主题/维度归类 | **解释**：说明「为什么」「如何运作」 |
| 每条的形态 | `[[链接]] — 一句话说明`（说明只做分类标注，不展开原理） | `[[atomic]]` + `**原理**`（原理是论证，可展开） |
| 是否产出洞见 | ❌ 不产出，洞见下沉到 concept/atomic | ✅ 核心命题段产出 atomic |
| 有无「核心命题」段 | ❌ 无（若有，说明已越界为 concept） | ✅ 有（这是 atomic 的唯一合法原料段） |
| 典型章节 | 分类分组、知识网络、待探索 | 核心命题、运行机制、关键区别、适用范围、批判、问题与流程 |

**消化禁令**：MOC 一旦开始写「为什么/原理/机制」，就应下沉为 concept（或把该条目提炼成 atomic）。判断口诀——**「MOC 问『有哪些』，concept 答『为什么』」**。

**易踩的三种错位**（体检已实际发现）：
1. **concept 写得像 MOC**：只有子概念罗列、无「核心命题」段 → 本质是 MOC，应改 `content-type: moc` 或补核心命题段。
2. **MOC 膨胀成 concept**：开始逐条展开原理、写运行机制 → 应把消化内容下沉到 concept，MOC 只留索引。
3. **area 误标成 concept**：带「长期目标」「关键领域」等 area 专属字段，却标 `concept` → 应改回 `area`（React.md 曾是此例）。

### 规范名与聚合名：名字的外延先于正文（2026-10-28 增）

上面三种错在形态，这一条错在**取名字**。`Web Storage` 是 W3C 规范名，只定义 `localStorage` 与 `sessionStorage` 两个对象；原来那篇 144 行的聚合页顶着这个名字，讲四种存储如何分工。名字的外延由规范给定，正文写得越全，错得越远——而且不报错，只让每条入链都得先猜「它指规范，还是指领域」。

| 问 | 是 → | 否 → |
|:--|:--|:--|
| 这个名字是某份规范的正式名吗（`Web Storage`、`Fetch API`、`DOM`、`Service Worker`） | 外延由规范给定，正文不超出该规范定义的对象 | 问下一行 |
| 要讲的是跨规范的选择或分工吗（Cookie / Web Storage / IndexedDB 怎么选） | 那是 `concept`，另起一个领域名（`客户端存储`、`前端缓存`） | 名字是自造的领域名（`Web事件`、`Web通信`），可以聚合 |

**这条约束的是外延，不是 content-type。** 所以 `Web API` 作为 `moc` 合法（它索引的正是这一层外延），`DOM` 作为 `term` 也合法；被拦的只有一种：名字是规范名，正文却按领域铺开。

**三种错法要分开，动作不同**：

| 错法 | 判据 | 动作 | 本次实例 |
|:--|:--|:--|:--|
| 名字越界 | 正文的主体是另一份规范的对象 | 另起一个领域名，规范名留给 term | `Web Storage`：144 行的四方案聚合页 → 拆出 `客户端存储` |
| 正文越界 | 把相邻规范的对象展开成自己的章节 | 收成链接，退回自己的外延 | `Service Worker`：Push / Background Sync / Cache 被写成「核心功能」 |
| 形态错标 | 名字是规范名，正文是定义 + 用法，却标了 `concept` | 改 `content-type` | `TreeWalker API`：concept → term |

**「有核心命题段 / 有 SOP」不是越界的判据。** 第一轮我按「名字的性质 + 篇幅」列了 8 篇，逐篇读正文后只剩 2 篇成立：

- `Cookie` 的 Cookie vs Web Storage 对照表、`WebSocket` 的轮询 / SSE 对比、`Temporal API` 的 Temporal vs Date——都是**借相邻对象说明自己的边界**，不是把对方搬进来当主体
- `WebSocket` 与 `Web Animations API` 的 SOP / FAQ 段只挂链接、不展开；`Web Animations API` 的 SOP 段还是空的
- `DOM` 的节点类型表、继承关系、核心 API 全在 WHATWG DOM 之内；`Web API` 作为 `moc` 只索引不消化，本就合法

判据因此收成一句：**正文的主体是不是另一份规范的对象？** 是 → 越界；只在对照表或链接里出现 → 不算。用别人的存在划自己的界是边界，替别人写机制才是越界。

**名字错了贵，正文越界便宜。** `Web Storage` → `客户端存储` 那次是 9 处入链逐条判断指代、两处别名冲突排查、一次 uid 迁移；这八篇候选的入链合计 96 处（`Service Worker` 21、`Cookie` 20、`WebSocket` 20、`DOM` 14、`Web API` 10 等，含 `40-ARCHIVE`），而实际要动的只有 2 篇，**0 处入链改指**。

值得写进真值的理由：这类错位的症状是入链歧义，不报错、不显形；`Service Worker` 那 21 处、`Cookie` 那 20 处在此之前没人碰过。条文成本 10 行，收益是下一次「前端怎么发请求」的汇总不会又落进 `Fetch API`（62 行 `term`）变成第二个混合页。

## 与目录的关系

本文件**不定义**任何「类型 → 目录」的对应关系。归属（目录）与形态（content-type）是两个正交维度，各自有唯一权威来源：

- 归属由目录决定 → 见 [[本库目录结构]]
- 形态由本文件的 14 种枚举决定

唯一残留的方向性约束是三个**单形态目录**（`50-ZETTELCASTEN/` 必 `atomic`、`60-BLOGS/` 必 `article`、`90-DIARY/` 必 `diary`），性质是「目录限制可填的形态」，不是「形态决定去哪个目录」。基于此，旧的「特定型 / 通用型」二分已废止。
