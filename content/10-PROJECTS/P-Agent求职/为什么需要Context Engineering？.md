## 为什么需要 Context Engineering？

一个常见疑问是：

> 既然 LLM 很强，为什么不把所有信息一次性都喂给 LLM？

答案是：**理论上可以尽量多喂，但工程上不可行，也不高效。**
Context Engineering 要解决的，就是"在正确的时间，把正确的信息，以正确的形式，放进 LLM 的上下文窗口"。

---

### 1. LLM 本身并不清楚项目的真实状态

LLM 并不是天生就知道你的项目结构、代码、约束和历史操作。
它只能根据当前上下文进行推理。

例如在 Coding Agent 中，用户说：

> "修复登录页面的 Bug。"

如果没有 Context Engineering，LLM 并不知道：

- 项目是什么？
- 登录页面在哪里？
- 相关代码是什么？
- Bug 的具体表现是什么？
- 项目使用 React 还是 Vue？
- 有哪些技术约束？
- 之前尝试过什么？
- 测试结果是什么？

所以 Runtime / Agent 需要不断收集、更新和组装上下文：

```text
User Request
     ↓
Context
     ↓
LLM
     ↓
Tool Call
     ↓
Runtime 执行
     ↓
Tool Result
     ↓
更新 Context
     ↓
LLM
     ↓
…
```

也就是说，Agent 并不是"一次把全部信息喂给 LLM"，而是通过多轮循环，把相关信息逐步注入 Context。

---

### 2. LLM 的上下文窗口是有限的

LLM 对输入长度有窗口限制。
即使模型支持很长的上下文，也不能无脑塞入所有信息，因为：

- 输入长度有硬上限；
- 超长上下文成本更高；
- 无关信息会稀释真正重要的信息；
- 长上下文并不等于模型一定能有效利用。

因此需要 Context Engineering 来管理：

- 哪些信息应该保留？
- 哪些信息应该丢弃？
- 哪些信息应该压缩？
- 哪些信息应该摘要？
- 哪些信息应该按需检索？

---

### 3. LLM 的注意力是有限的

在多轮 Agent Loop 中，会产生大量内容：

- Tool Call
- Tool Result
- 中间推理
- 错误日志
- 文件内容
- 用户反馈

但 LLM 的注意力并不是无限可用的。
上下文越长，单个token消耗的注意力成本就越多，噪声也就越多，模型越可能：

- 忽略关键信息；
- 被无关内容干扰；
- 产生错误关联；
- 偏离原始目标；
- 降低推理和执行质量。

所以 Context Engineering 的目标不是"塞更多"，而是：

> **在有限窗口和有限注意力下，让 LLM 看到最相关、最关键、最及时的信息。**

---

### 4. 总结

需要 Context Engineering，是因为：

1. **LLM 不知道项目真实状态**，必须由 Runtime 动态提供信息；
2. **LLM 上下文窗口有限**，不能无限塞入所有内容；
3. **LLM 注意力有限**，信息越多不一定越好，噪声会干扰推理；
4. **Agent 是多轮循环系统**，Context 需要不断更新、筛选、压缩和重组。

一句话：

> 不是"把所有信息都喂给 LLM"，而是"把最该看的信息，在最适合的时候，以最合适的形式喂给 LLM"。
