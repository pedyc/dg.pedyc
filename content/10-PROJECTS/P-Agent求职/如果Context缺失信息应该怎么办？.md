## 问题

如果 Context 缺失信息应该怎么办？

## 回答

核心原则：

> **先确认缺什么，再决定去哪拿；拿不到就标注未知，绝不让模型默默脑补。**

处理工作流：

```text
判断关键信息是否缺失
→ 能否从环境获取
   ├── 能 → Retrieval / Tool Call
   └── 不能 → Ask User / 标注未知
→ 校验信息（相关/最新/冲突/可信/重复）
→ 加入 Context（结构化 + 来源 + 时效）
→ LLM 继续处理
→ 若仍缺失 → 标注未知，避免脑补
```

---

### 1. 判断关键信息是否缺失

不是所有缺失都要补。先问：

- 缺的是关键信息吗？
- 缺少它，模型会不会跑偏？
- 模型会不会自己脑补？

判断标准：

> 缺少它，任务是否会走向错误方向？

如果是，才需要处理。

---

### 2. 判断信息能否从环境获取

缺失信息分两类：

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 可从环境获取 | 文件位置、报错日志、接口定义 | 用工具/检索获取 |
| 无法从环境获取 | 用户真实意图、业务优先级 | 向用户确认 |

**原则：**

> 能查就查，不能查就问，不能问就标注未知。

---

### 3. 通过 Retrieval / Tool Call 获取

常见手段：

- **Retrieval**：从知识库、文档、历史记录中检索
- **Tool Call**：读文件、查数据库、跑测试、调 API
- **Ask User**：向用户确认意图、约束、优先级

你的流程可以细化为：

```text
判断缺失
   ↓
能否从环境获取？
   ├── 能 → Retrieval / Tool Call → 获取信息
   └── 不能 → Ask User / 标注未知
   ↓
校验信息
   ↓
加入 Context
   ↓
LLM 继续处理
```

---

### 4. 校验获取到的信息

拿到信息后，不能直接塞进 Context，要先检查：

1. **是否相关？** 与当前任务有关吗？
2. **是否最新？** 是否过期？
3. **是否冲突？** 与已有信息矛盾吗？
4. **是否可信？** 来源可靠吗？
5. **是否重复？** 已有类似信息吗？

**原则：**

> 先过滤，再进入。

---

### 5. 加入 Context

加入时注意：

- 结构化，不写大段散文
- 标注来源和时效
- 标注优先级
- 只放当前需要的信息
- 长内容先摘要，保留指针

---

### 6. 如果获取失败怎么办？

获取失败时：

- **标注未知**：明确告诉模型"此项未知"，避免脑补
- **降级处理**：用保守方案，不假设
- **向用户确认**：把问题抛回给用户
- **记录缺口**：在 Context 中保留"缺失项"，提醒后续补充

**原则：**

> 拿不到不可怕，可怕的是模型假装知道。

---

### 8. 总结

Context 缺失信息时，处理流程是：

1. 判断是否关键缺失
2. 判断能否从环境获取
3. 能查就查，不能查就问，不能问就标注未知
4. 校验信息
5. 结构化加入 Context
6. 获取失败时显式标注，避免脑补

一句话：

> **缺失要补，补不到要标，绝不能让它猜。**
