## 目标

不学会怎样：回滚只能重跑流水线，而流水线构建的是主干最新提交——于是「回滚」实际是又发了一版新代码；线上出事后只有压缩后的文件名与行列号，一条报错等于一个坐标；而流水线是绿的，于是所有人都以为上线成功了。

两条判据各一句话：**这一版能不能回去**（产物按版本存放，回滚 = 切指针）、**出事后能不能定位到源码行**（sourcemap 传到该传的地方）。

勾选在 [[前端工程学习专项#KR3：交付与观测]]，本页只管怎么学。

## 读什么

**依据**：GitHub Actions（workflow syntax / deployment environments / OIDC）、Vite Static Deploy、MDN Server-side。灰链即待写清单，不标「待写」。

### ⑤ 上线（15 条）

- [[触发事件的语义差异决定这次跑的是哪份代码、能拿到什么凭据]]——push、PR、pull_request_target 是三个权限世界；分支到环境的映射也在这里
- [[job 之间不共享文件系统，产物必须显式传]] → [[GitHub Actions]]（平台模型）
- [[cache 可丢，artifact 是本次交付物]]——混用这两个词，deploy 拿到的是上一次的 dist
- [[needs 决定单测挂了部署会不会照样跑]]——失败不向下传播，门就是画出来的
- [[托管 runner 是预置镜像，运行时通常要自己装]]——「本地能跑 CI 报 command not found」的第一成因
- [[依赖缓存的 key 语义：精确命中与前缀回退是两种结果]]——「这次是命中还是没命中」判不出来，后面全在猜
- [[部署凭据的作用域：secrets 可见性、environment 保护、OIDC 换取]]——取到空 token 时，分不清是权限、作用域还是时机
- [[流水线的三处平台语义：并发组、矩阵与 fail-fast、条件求值时机]]——连推两次线上最终是哪一次的结果，答案在这里
- [[部署原子性：资源与入口 HTML 谁先替换]]——顺序错了，用户拿到半新半旧的页面
- [[preview 命令不是生产服务器]]——「preview 通过了」不是上线判据
- [[灰度扩量按什么判据扩]]——[[灰度]] 只给了定义，没给扩量的门槛与回退线
- [[回滚不只是退代码，还会撞上已写入的数据与缓存]]——第二次故障往往发生在回滚之后

以下三条来自 2026-11-10 的外部覆盖核对（见 [[前端工程学习专项#覆盖核对]]），原先整簇漏掉：

- [[部署是不可变产物，回滚是指针切换不是重新构建]]——「每次部署一份不可改的产物」是所有部署模型的共同前提
- [[能不能单独验证一个改动，取决于部署有没有唯一地址]]——没有独立地址，验证和上线就是同一次动作
- [[preview 验证再 promote，是灰度之外的第二种分批手段]]——静态托管做不到按比例放量，但可以做到「先验证再提升」

### ⑥ 判定（6 条）

- [[「可用」是分层判据：进程活着、200、关键路径成功、错误率，四者不等价]]——流水线绿了不等于上线成功；口径见 [[前端监控指标采集]]，采集面见 [[前端监控]]
- [[客户端错误不进服务器日志]]——白屏与资源加载失败发生在浏览器侧，服务端日志干净是正常的
- [[回滚要落到一个可执行动作上]]——「回滚」不是名词，是某一条命令或某一次指针切换

以下三条同批补入，都是发布健康度的口径问题：

- [[release 是部署的对象，不是 commit 的别名]]——发布不主动上报，线上报错就归不到某一次部署
- [[crash-free users 与 crash-free sessions 是两个口径]]——同一个版本，两个数可以一个 99% 一个 97%
- [[发布采用率低时，崩溃率下降不说明变好]]——新版本只覆盖了 5% 的用户，它的健康度不具代表性

## 自测

答不出就是没学：

1. 回滚为什么不能重建？
2. 没传 sourcemap 时，一条报错你拿得到什么、拿不到什么？
3. 灰度扩到 10% 时，你用哪个数说「停」？这个数多久能看到？
4. 流水线全绿，能不能说这次上线成功？如果不能，缺的是哪一层信号？
5. 服务端日志干净，但用户说白屏——错在哪一侧，为什么日志里没有？

## 决定项

| 决定项 | 取值 | 为什么这个不能换 |
|:--|:--|:--|
| 部署目标 | 静态托管，**必须支持多个版本目录共存** | 只支持单目录覆盖的托管做不到「回滚 = 切指针」，这一档就没有判据 |
| 监控 | Sentry 免费额度，或任一支持 sourcemap 上传的方案 | 选哪家不重要，验收是堆栈能还原到源码行 |
| 灰度形态 | **待定**：静态托管本身不做按比例放量，只有版本目录 + 指针切换 | 要真灰度就得换到支持流量切分的平台，或接受「全量切换 + 退得快」 |

**三项都还是待确认状态，第三项是新提出的。** 前两项不定，「用得上」那一档连「做没做对」都判断不了。第三项要接受一个诚实的结论：**在纯静态托管上，⑤ 环的「影响面收得住」只能退化成「退得快」**——这不是配置问题，是部署形态的问题。若这个降级不可接受，就得在 12-12 前改部署目标。
