## 背景

「前端有哪些缓存机制」这个问题我查过很多次，每次拿到的都是一张更长的清单：强缓存、协商缓存、Memory Cache、Disk Cache、Service Worker、Cache API、IndexedDB、localStorage、Cookie、CDN……清单越来越长，理解没有变深反而更加困惑。

问题出在**清单没有结构**：Web Storage 存的是应用数据，HTTP 缓存存的是网络资源，把两者放进同一张按容量和介质排列的表，只能逐项记忆，不能推理。而真正会出事的地方恰恰在推理上——「发了版，用户还是旧页面」「清了缓存，CDN 还是旧的」「加了 `immutable` 还是回源了」，这些都不是记不住 API 造成的。

所以这个专项的目标不是「补齐缓存相关的笔记」，是将**判断依据的建立**和**名词表**分开做：先有一套能对新机制提问的框架，再往里填。

---

## 核心目标

**Outcome**：对任意一个缓存机制（包括没见过的），能用同一组问题判断它属于哪一层、能省什么、失效后谁负责、代价落在哪里；并且在「发版后旧副本」这类真实故障里，能按层定位而不是靠猜。

**成功标准**：

- 能不看笔记答出四层==失效控制权==分别归谁，并各举一个「你以为清了其实没清」的例子。
- 能解释强缓存与协商缓存为什么不是两种缓存，且说清中文教材这个分法从哪里来、多了什么、少了什么。
- 面对一个新机制（例如 `Speculation Rules API`、HTTP/3 的 `QUIC` 连接缓存），十分钟内能填出「存什么 / 谁判失效 / 省的是哪一段 / 代码能不能读写」四格。
- 库里所有缓存相关的红链降为 0，或明确标为「不打算写」。

## 战略地图

### 判定框架（先于名词表）

任何缓存机制只回答四个问题，答不出第三问就是没学：

| 问 | 为什么必须先问它 |
|:--|:--|
| **存什么**（键是什么） | 决定「同名不同内容」会不会对冲：URL 做键会被 `?v=1` 绕过，文件名做键要求构建期就有哈希 |
| **谁判失效** | 决定你手上有没有开关。协议判的只能改响应头，代码判的才能上线即修 |
| **失效后付什么** | 决定它是否值得配。强缓存失效付一个请求，协商缓存付一个 RTT，SW 失效付一段 JS 执行 |
| **代码能否读写** | 决定调试手段。黑盒层出问题只能看 DevTools 的 Size 列，白盒层能 `console` 出来 |

第二问是主轴，因为它同时决定「谁能作废这份副本」和「出事时你能做什么」。第四问是副轴，因为它决定排查路径。

## 学习路径

顺序按「谁能真的省掉请求」排，不按 API 熟悉度排。理由：只有前两层能让请求根本发不出去，后两层省的是计算与后端查询——先把收益最大的那部分弄对，再去处理存储。

| 阶段 | 读什么 | 自测（答不出就是没学） |
|:--|:--|:--|
| 1. 协议层 | [[HTTP缓存机制]] → [[HTTP强缓存]] → [[HTTP协商缓存]] → [[新鲜度]] | 为什么 `max-age=31536000` 配了还是不命中？`immutable` 省掉的是哪一步？ |
| 2. 代码层 | [[Service Worker]] → [[Cache API]] | SW 的 `fetch` 拦截与 Disk Cache 谁先？离线时 `no-store` 的响应还能不能拿到？ |
| 3. 存储层 | [[Web Storage]] → [[Cookie]] → [[IndexedDB]] | 为什么 `localStorage` 不该存大对象？Cookie 为什么会拖慢所有同源请求？ |
| 4. 一致性 | [[Content-Hash]] → [[CDN]] → [[RTT]] | 发版瞬间，四层里哪几份副本会旧？谁负责让它们变新？ |

第 4 阶段才是这个专项真正的验收：前三阶段都是「知道有哪些」，第 4 阶段是「知道它们同时存在时会怎么打架」。
