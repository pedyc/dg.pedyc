## 背景

「前端有哪些缓存机制」这个问题我查过很多次，每次拿到的都是一张更长的清单：强缓存、协商缓存、Memory Cache、Disk Cache、Service Worker、Cache API、IndexedDB、localStorage、Cookie、CDN……清单越来越长，理解没有变深，反而更困惑。

问题不在名词数量，在清单没有结构。Web Storage 存的是应用数据，HTTP 缓存存的是网络资源，把两者放进同一张按容量和介质排列的表，只能逐项记忆，不能推理。而真正会出事的地方恰恰在推理上——「发了版，用户还是旧页面」「清了缓存，CDN 还是旧的」「加了 `immutable` 还是回源了」，这些都不是记不住 API 造成的。

立项十天后，框架这一半做完了：按「失效由谁判」分四层、按「省掉哪一段」分两条轴，落成一篇文章和四条 atomic，体系页的请求路径也画出来了。所以本页现在要管的不是「怎么分」，是另一件事——**这套分法只在这堆笔记里成立过，一次都没在真实故障上用**。配置规范写了该配什么，没验过配下去是否生效；四条 atomic 全是读书所得，没有一条来自事故。

这也是重写本页的理由：结构不用换，缺的是把结构推到能出错的地方去。

## 核心目标

**Outcome**：对任意一个缓存机制（包括没见过的），能用同一组问题判断它属于哪一层、能省什么、失效后谁负责、代价落在哪里；并且在「发版后旧副本」这类真实故障里，能按层定位而不是靠猜。验收时打开 DevTools 指给我看：哪一条请求是 `from disk cache`，哪个响应头没生效，哪一层没被清掉。

**与上位的关系**：本页自定，不映射 [[前端性能优化]] 的条目。那个 MOC 按 P0–P3 优先级排，通篇没有缓存这一档，与它最近的只有 P1「资源加载与网络优化」里一句 CDN 容灾。缓存是性能优化里最便宜的一档（省掉的工作根本不会发生），却在上位页没有位置。这个空缺值得补，但补它要动 MOC 的条目结构，不属于本页，先记在这里。

**不做什么**：

- 不另立 Memory Cache / Disk Cache。它们是 HTTP 缓存的两个存放位置，不是两种机制；单独立篇会让「它们的 `max-age` 在哪配」这种问题无处可答。内容并进 [[HTTP缓存机制]]。
- 不按厂商写 CDN。边缘节点的行为差异是运维知识，写进本库会一年即过期。本页只用到它一件事实：边缘有一份副本，且作废它需要主动 purge。
- 不碰后端与推理侧缓存。[[分布式集群ETag缓存失效]] 讲的是集群里 ETag 因物理差异大面积失效，[[大模型缓存命中率]] 讲的是 LLM 的 KV Cache——两者与浏览器侧四层同名不同域，不并入，也不在本专项的路径上。
- 不把 `preload` / `prefetch` / `preconnect` 当缓存机制。它们只负责提前发起，不决定过期。文章已澄清，这里不重复第三遍。
- 不收代码片段合集。[[内容缓存示例]]（201 字）与 [[多级缓存示例]] 是示例记录，不是知识节点；读它们不会多出一条判据，本页的 KR 也不产出这类。

## 战略地图

### 判定框架（先于名词表）

任何缓存机制只回答四个问题，答不出第三问就是没学：

| 问 | 为什么必须先问它 |
|:--|:--|
| 存什么（键是什么） | 决定「同名不同内容」会不会对冲：URL 做键会被 `?v=1` 绕过，文件名做键要求构建期就有哈希 |
| 谁判失效 | 决定你手上有没有开关。协议判的只能改响应头，代码判的才能上线即修 |
| 失效后付什么 | 决定它是否值得配。强缓存失效付一个请求，协商缓存付一个 RTT，SW 失效付一段 JS 执行 |
| 代码能否读写 | 决定调试手段。黑盒层出问题只能看 Size 列，白盒层能 `console` 出来 |

第二问是主轴，因为它同时决定「谁能作废这份副本」和「出事时你能做什么」。第四问是副轴，因为它决定排查路径。

## 学习路径

顺序按「谁能真的省掉请求」排，不按 API 熟悉度排。只有前两层能让请求根本发不出去，后两层省的是计算与后端查询——先把收益最大的那部分弄对，再去处理存储。

| 阶段 | 读什么 | 自测（答不出就是没学） |
|:--|:--|:--|
| 1. 协议层 | [[HTTP缓存机制]] → [[HTTP强缓存]] → [[HTTP协商缓存]] → [[新鲜度]] | 为什么 `max-age=31536000` 配了还是不命中？`immutable` 省掉的是哪一步？ |
| 2. 代码层 | [[只有ServiceWorker同时握有请求拦截与存储写入，离线策略因此只能写在它里面]] → [[Service Worker]] → [[Cache API]] | SW 的 `fetch` 拦截与 Disk Cache 谁先？离线时 `no-store` 的响应还能不能拿到？ |
| 3. 存储层 | [[Web Storage]] → [[Cookie]] → [[IndexedDB]] → [[StorageManager API]]（待写） | 为什么 `localStorage` 不该存大对象？Cookie 为什么会拖慢所有同源请求？配额满了浏览器先淘汰谁，`persist()` 为什么可能失败？ |
| 4. 一致性 | [[Content-Hash]] → [[CDN]] → [[RTT]] | 发版瞬间，四层里哪几份副本会旧？谁负责让它们变新？ |

第 2 阶段开头那篇是前提：它定的是「为什么离线策略只能写在 SW 里」，没有它，阶段 2 的两篇只是 API 说明。第 4 阶段才是这个专项真正的验收——前三阶段都是「知道有哪些」，第 4 阶段是「知道它们同时存在时会怎么打架」。

**不在路径里的**（写清是「推后」还是「本来就不该在这里」）：

- [[分布式集群ETag缓存失效]]、[[大模型缓存命中率]] — 本来就不该在这里。前者是服务端集群问题，后者是 LLM 推理缓存，与浏览器侧四层只是同名
- [[多级缓存示例]]、[[内容缓存示例]] — 推后，实际是不打算读。代码片段不产判据，需要时直接抄进 `cache-lab`
- [[前端缓存方案]] — 它是索引，不是知识；治理它在 KR1，不在学习路径上
