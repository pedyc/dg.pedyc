## 这份笔记做什么用

现在是求职期，目标只有一个：面试被问到缓存时能讲清楚、能接住追问。不搭环境、不写代码、不做演示，也不需要能现场复现线上故障。

用法是三步：先读「一套框架」，把十几个名词放回各自的位置；再打开 [[缓存机制相关问题]] 按主题过题，答不出的顺着关联笔记点进去细读；最后合上笔记，用「自测清单」过一遍。框架在这页，能直接说出口的回答要点在题单里，机制细节在链接指向的笔记里。

## 面试里缓存到底在考什么

面试官很少让你背清单。真正被追问的是三件事：一次请求会经过谁、每份副本谁能作废、发了版为什么用户还是旧页面。

清单式答案（强缓存、协商缓存、Memory Cache、Disk Cache、Service Worker、Cache API、IndexedDB、localStorage、Cookie、CDN……）一定会卡住，因为这些词不在同一层：有的存 HTTP 响应，有的存应用数据，有的其实只是一种结果。按容量或介质排成一张表，只能逐项记忆，没法推理。

还有一个必须先拆掉的坑：中文教材常把缓存分成「强缓存 / 协商缓存 / 不缓存」三档。RFC 9111 里没有这三个词条，只有能不能存（§3）、能不能复用（§4）、复用前要不要验证（§4.3）。面试里能说出「强缓存是复用判定通过后的结果，不是一套机制」，比背十几个响应头更能拉开差距。

## 一套框架

### 任给一个机制，先问四句

| 问 | 答得出来才能往下推 |
|:--|:--|
| 存什么，键是什么 | 决定「同名不同内容」会不会对冲：URL 做键会被 `?v=1` 绕过，文件名做键要求构建期就有哈希 |
| 谁判它失效 | 决定你手上有没有开关：协议判的只能改响应头，代码判的才能上线即修 |
| 失效后要付什么 | 决定值不值得配：强缓存失效付一个请求，协商缓存付一次 [[RTT]]，代码层付一段 JS 执行 |
| 代码能不能读写 | 决定排查路径：黑盒层只能看响应头，白盒层能自己打出来 |

第三问答不出，通常说明只是记住了名字。这四句对没见过的新机制同样管用，被临时问到一个陌生名词也能当场归类，不用硬猜它属于哪一档。

### 失效由谁判，分四层

| 层 | 代表机制 | 谁能让它失效 | 出事时你有没有开关 |
|:--|:--|:--|:--|
| 协议 | `max-age`、`s-maxage`、`Expires` | 改响应头，或者等过期 | 几乎没有 |
| 服务端 | `ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since` | 改内容，由源站裁决 | 有，但要付一次往返 |
| 你的代码 | [[Cache API]]、[[Web Storage]]、[[IndexedDB]]、运行时 `Map` | 改版本号、`delete()`、覆写 | 有，且立即生效 |
| 浏览器 | 磁盘配额与 LRU 淘汰 | 只能申请持久化 | 几乎没有 |

「清了缓存还是旧的」这句话，答案就在这张表里：清掉的往往只是其中一两层，CDN 边缘和 Service Worker 里各自还有一份副本没动。

两条能直接说出口的结论，值得记牢：[[缓存分层分的是失效判定权，不是存储介质]]、[[强缓存省掉整个请求，协商缓存省掉响应体]]。

### 省掉的是哪一段

同样叫缓存，省掉的东西完全不同：

- 省掉整个请求：HTTP 缓存、CDN、Service Worker 拦截。只有这一档能让请求根本发不出去，优化首屏先看它。
- 省掉响应体：304。往返照付，服务端还要算一次验证器。
- 省掉计算或后端查询：运行时缓存、`IndexedDB` 存接口数据。请求数一个不少，省的是请求到达之后的工作量。

把组件加个 `memo` 当成「做了缓存优化」却去解释首屏为什么慢，就是选错了层。

## 学习顺序（只读和口述）

顺序按「谁能真的省掉请求」排，不按 API 熟悉度排。每行的自测合上笔记口述一遍即可，不需要打开 DevTools，也不需要起服务。

| 阶段 | 读什么 | 自测 |
|:--|:--|:--|
| 1. 协议层 | [[HTTP缓存机制]] → [[HTTP强缓存]] → [[HTTP协商缓存]] → [[新鲜度]] → [[Cache-Control]] / [[ETag]] / [[Last-Modified]] | 为什么 `max-age` 配了一年还是发请求？`immutable` 省掉的是哪一步？ |
| 2. 存放位置与代码层 | [[Memory Cache 与 Disk Cache]] → [[Service Worker]] → [[Cache API]] | SW 的 `fetch` 拦截和 Disk Cache 谁先？离线时 `no-store` 的响应还能不能拿到？ |
| 3. 存储层 | [[Web Storage]] → [[Cookie]] → [[IndexedDB]] | 为什么 Cookie 拖慢所有同源请求？`localStorage` 为什么不该存大对象？ |
| 4. 发版一致性 | [[Content-Hash]] → [[CDN]] → [[前端静态资源多级缓存配置规范]] → [[RTT]] | 发版瞬间哪几份副本会旧？谁负责让它们变新？ |

想看一版连贯的口语叙述，直接读 [[前端缓存怎么分类]]，那是本专项写好的对外文章，八节把两根轴和四层讲全。面试侧上下文可对照 [[前端面试知识清单]]、[[前端面试常见问题]] 与 [[面试提问的三层递进]]。

## 不用准备的部分

- 不搭 nginx、不起两层服务、不建演练仓库，不做故障复现或截图取证。求职期不考这个，用不上。
- 不按厂商背 CDN 配置，也不收 Nginx 配置片段。只需知道「边缘有一份副本，作废它要主动 purge」。
- 不碰后端 Redis、集群 ETag 调优、LLM 的 KV Cache。它们与浏览器侧四层只是同名，属于另一个域；集群 ETag 那一题只需答到「各节点生成口径不一致」这句话，不追调优方案。
- 不收集代码片段合集。示例不产生判断依据，面试也考不到。
- 不深究配额 API 的实现细节；知道失效由浏览器按 LRU 判就够。
- `preload` / `prefetch` / `preconnect` 不列进缓存机制，理由见题单第 4 组。

## 自测清单

能不看笔记讲出来就打勾。卡住的那一处，回头补对应笔记即可，不必另建新笔记。

- [ ] 一次请求按什么顺序被拦截，命中即返回
- [ ] 强缓存、协商缓存、304 各自省掉了什么
- [ ] 四层失效判定权分别归谁，各举一个「以为清了其实没清」的例子
- [ ] `no-cache` / `no-store` / `max-age=0` / `immutable` 各自关掉哪一档
- [ ] `ETag` 与 `Last-Modified` 的差别，以及同时在场时听谁的
- [ ] 为什么 Memory Cache 和 Disk Cache 不是两种缓存
- [ ] 入口 HTML 与哈希资产为什么配两套完全不同的策略
- [ ] 发版后旧副本的四类成因分别落在哪一层
- [ ] 任给一个新机制，十分钟填出四问

按 [[间隔重复]] 的 3 → 7 → 14 天节点，不看笔记再讲一遍。讲给不懂缓存的人听，比默背答案更能暴露漏洞。
