## MOC：缓存相关问题

> 前端面试缓存方向的过题清单，从 [[缓存机制学习专项]] 拆出。按面试官会先问哪一头分七组：请求流程 → 指令 → 验证器 → 存放位置 → 存储 → 发版一致性 → 易错说法。每题只给一句能直接说出口的回答要点，机制细节交给「关联笔记」列；合上笔记能复述要点，这题就算过。

### 核心原则

- 分组按「被问到的顺序」，不按 API 熟悉度：越靠前越可能被要求从头讲一遍，第 6 组最能拉开差距。
- 回答要点只写结论与边界，不展开机制。要展开时点关联笔记，避免同一份答案在本库存两处。
- 题目是口述题，不对应库里的 `question` 笔记；答案散在 [[HTTP缓存机制]] 及它的下位笔记里。

### 1. 从一次请求讲起

被要求「从头讲一遍浏览器缓存」时，按拦截顺序说，命中即返回，不再往下：Service Worker 的 `fetch` → 内存副本 → 磁盘上的 HTTP 缓存 → CDN 边缘节点 → 源站。「多级缓存」不是让你全配一遍，而是判断这次请求最可能被谁先拿走。

| 示例题目 | 回答要点（一句话） | 关联笔记 |
|:--|:--|:--|
| 强缓存和协商缓存有什么区别？ | 不是两种缓存，是同一次查找的两个分支：新鲜就直出不发请求，不新鲜就带验证器问源站、回 304 复用旧副本；前者省整个请求，后者只省响应体 | [[HTTP强缓存]]、[[HTTP协商缓存]] |
| 304 里有什么？ | 无响应体但有一组响应头，新的 `Date` 让副本重新变新鲜——一次 304 顺带给强缓存续了命 | [[HTTP协商缓存]] |
| 304 是不是等于没花钱？ | 一次往返照付，服务端还要算 ETag；小文件或弱网下可能比直接 200 还慢 | [[RTT]]、[[ETag]] |
| F5 和 Ctrl+F5 有什么不同？ | F5 发请求侧 `max-age=0`，跳过强缓存仍走协商；Ctrl+F5 发 `no-cache` 且丢掉验证器，连协商一起跳过，直接 200 全量 | [[HTTP强缓存]] |
| 为什么配了 `max-age=31536000` 还是发请求？ | 复用判定是五道门同时成立，前四道与时间无关；且 `max-age` 只是上限，配额、LRU、用户清理都会让副本中途消失 | [[HTTP强缓存]]、[[新鲜度]] |

### 2. Cache-Control 的指令

| 示例题目 | 回答要点（一句话） | 关联笔记 |
|:--|:--|:--|
| 常用指令怎么分组？ | 按它关掉哪一档：能不能存、能不能直接复用、过期后能否用旧副本、要不要验证 | [[Cache-Control]] |
| `no-cache` 和 `no-store` 区别？ | `no-cache` 允许存但每次必须验证；`no-store` 根本不存，副本从未存在过 | [[Cache-Control]]、[[HTTP强缓存]] |
| `max-age=0` 和 `no-cache` 一样吗？ | 行为几乎一致，前者让新鲜度立刻失效、后者跳过新鲜度判定；工程上写 `no-cache` | [[Cache-Control]] |
| `Expires` 和 `max-age` 谁优先？ | `max-age` 优先；`Expires` 是绝对时间，多一层对客户端时钟的依赖 | [[HTTP强缓存]]、[[新鲜度]] |
| `immutable` 做了什么？ | 不延长有效期，只取消有效期内刷新时那批条件请求；过期照常验证，必须配合内容哈希 | [[HTTP强缓存]]、[[Content-Hash]] |
| `private` / `public` / `s-maxage` 给谁看？ | 给共享缓存：`s-maxage` 覆盖共享缓存上的 `max-age`，`private` 禁止存私有响应，漏写会把 A 的响应发给 B | [[Cache-Control]]、[[CDN]] |
| `must-revalidate` 什么时候生效？ | 只在副本已不新鲜之后禁止用旧副本，不影响新鲜判定本身 | [[Cache-Control]] |

### 3. 两个验证器

| 示例题目 | 回答要点（一句话） | 关联笔记 |
|:--|:--|:--|
| `ETag` 和 `Last-Modified` 有什么区别？ | 内容指纹（可精确到字节）与秒级时间戳；时间戳看漏 1 秒内多次写、会因重新部署伪变更、依赖时钟对齐，ETag 更准但花 CPU | [[ETag]]、[[Last-Modified]] |
| 两个都带了听谁的？ | `If-None-Match` 优先，规范的含义是忽略 `If-Modified-Since`，不是两个都验一遍 | [[ETag]]、[[HTTP协商缓存]] |
| 既然 ETag 更准，为什么还留着 Last-Modified？ | 兜底：不少框架只发一个、静态服务器默认给时间戳，而且它几乎零成本 | [[Last-Modified]] |
| 强 ETag 和弱 ETag？ | `W/` 前缀表示语义等价即可，不带前缀要求字节一致；动态压缩与 CDN 常把强降弱 | [[ETag]] |
| 集群里 ETag 为什么会出问题？ | 默认生成常含 inode 或 mtime，各节点算出的值天然不同，本该 304 的请求全变 200，命中率缓慢下降且不报错 | [[分布式集群ETag缓存失效]] |
| ETag 除了缓存还用在哪？ | 条件请求的另一半：`If-Match` 做并发写的乐观锁，`If-Range` 支持断点续传 | [[ETag]] |

### 4. 缓存放在哪：内存、磁盘、Service Worker

| 示例题目 | 回答要点（一句话） | 关联笔记 |
|:--|:--|:--|
| 浏览器缓存分几级？ | 「SW → 内存 → 磁盘 → Push Cache → 网络」不是规范，是浏览器实现细节；协议只规定能不能存与复用，不规定副本放哪 | [[Memory Cache 与 Disk Cache]]、[[浏览器缓存与客户端存储体系]] |
| Memory Cache 和 Disk Cache 是两种缓存吗？ | 不是，是同一套 `Cache-Control` 下的两个存放位置，差别在生命周期、容量与读取成本；`no-store` 两层都不写 | [[Memory Cache 与 Disk Cache]] |
| 为什么刷新一次 `from memory cache` 变 `from disk cache`？ | 内存副本随文档／标签页，导航后不再复用；磁盘副本跨会话还在——`max-age` 只有一份 | [[Memory Cache 与 Disk Cache]] |
| Service Worker / Cache API 和 HTTP 缓存怎么区分？ | SW 是唯一能在请求发出前拦截的层；Cache API 白盒、由代码管淘汰，HTTP 缓存黑盒、由协议管；SW 接管后 HTTP 缓存可能根本不被问到 | [[Service Worker]]、[[Cache API]] |
| `preload` / `prefetch` / `preconnect` 算缓存吗？ | 不算，它们只提前发起连接或请求，不决定过期 | [[前端缓存怎么分类]] |

### 5. 别把存储当成 HTTP 缓存

| 示例题目 | 回答要点（一句话） | 关联笔记 |
|:--|:--|:--|
| localStorage、Cookie、IndexedDB 和 HTTP 缓存有什么不同？ | 前三者存应用数据、由代码读写与作废；HTTP 缓存存网络响应、由响应头判失效，代码碰不到 | [[浏览器缓存与客户端存储体系]] |
| Cookie 为什么拖慢请求？ | 它是唯一会自动随每个同源请求发送的本地存储，体积直接变带宽；Web Storage 是纯本地容器，服务端永远看不到 | [[Cookie]]、[[Web Storage]] |
| localStorage 为什么不适合存大对象？ | 同步 API 阻塞主线程、只存字符串、没有精细的配额管理 | [[Web Storage]] |
| 这几个怎么选？ | 小配置同步读 → localStorage；结构化大对象 → IndexedDB；要服务端读到 → Cookie；跨组件复用结果 → 运行时 `Map`，最便宜 | [[IndexedDB]]、[[Web Storage]]、[[Cookie]] |
| 配额满了浏览器先淘汰谁？ | 按 LRU 淘汰，`persist()` 可申请但常失败；这一层判定权在浏览器，几乎没有开关 | [[浏览器缓存与客户端存储体系]] |

### 6. 发版与 CDN：为什么用户还是旧页面

这一组考的是「同一个资源身上同时存在好几份副本，哪一份没被作废」。

| 示例题目 | 回答要点（一句话） | 关联笔记 |
|:--|:--|:--|
| 标准配置是什么？ | 入口 HTML 用协商缓存（`no-cache` + `ETag`），带内容哈希的 JS/CSS 用一年强缓存加 `immutable`；HTML 是把用户引到新哈希的唯一入口 | [[前端静态资源多级缓存配置规范]]、[[Content-Hash]] |
| 为什么不用 `app.js?v=2`？ | 查询参数不是可靠的失效手段，部分中间层与 CDN 不按查询串区分副本甚至忽略参数；哈希写进文件名才稳 | [[Content-Hash]]、[[CDN]] |
| 强缓存发出去之后还能撤回吗？ | 不能，协议层没有主动撤销客户端副本的通道，只能等过期或换 URL——这正是必须做内容哈希的原因 | [[HTTP强缓存]]、[[Content-Hash]] |
| 清了浏览器缓存为什么还是旧的？ | 只清了浏览器本地那一份；CDN 要主动 purge 或等 `s-maxage`，SW 的 Cache Storage 要代码自己删，源站与代理各有副本 | [[CDN]]、[[Service Worker]] |
| 旧副本大致有哪几类成因？ | 四类：HTML 被误配成强缓存、CDN 未 purge、SW 用了缓存优先策略、查询参数没穿透中间层；按「哪份副本没被作废」定位比背现象清楚 | [[前端静态资源多级缓存配置规范]] |
| 什么时候不该缓存？ | 会变又没版本号的文件、带用户身份的接口响应、需要强一致的余额与库存；缓存换性能付的是一致性与调试成本 | [[浏览器缓存与客户端存储体系]] |

### 7. 容易被追问「你确定吗」的说法

| 常见错话 | 纠正 | 关联笔记 |
|:--|:--|:--|
| 强缓存就是零成本 | 省的是网络往返，磁盘读取与 `Vary` 比对仍花时间；冷启动时磁盘命中未必比近端 CDN 快 | [[HTTP强缓存]]、[[Memory Cache 与 Disk Cache]] |
| 协商缓存省时间 | 省的是带宽，不是往返 | [[HTTP协商缓存]]、[[RTT]] |
| 304 是缓存命中的一种 | 它是「验证通过」这个结论，副本本来就在本地 | [[HTTP协商缓存]] |
| 清缓存等于全清掉 | 只清浏览器本地那几层 | [[浏览器缓存与客户端存储体系]] |
| 强缓存／协商缓存／不缓存是三档 | 第三档不在判定链上，`no-store` 在存储期就出局了 | [[HTTP强缓存]] |
| 零延迟和实时感知只能二选一 | 还有 `stale-while-revalidate` 这类先给旧副本、后台验证的中间态，只是把往返挪出关键路径 | [[新鲜度]]、[[HTTP强缓存]] |
