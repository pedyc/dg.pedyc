## 术语：Content-Hash

> **主题**：#前端工程化/构建产物

### 定义

Content-Hash 指把文件**内容的摘要**（通常是内容 MD5/SHA 的前若干位）嵌入文件名或查询串的做法：`main.a1b2c3d4.js`。

它解决的不是「怎么缓存」，而是**「缓存怎么失效」里最难的一档**：磁盘上的强缓存没有撤销接口，一旦写进去，在 `max-age` 内服务端说了不算。Content-Hash 把这个控制权从**时间**换成了**名字**——内容变，名字就变，浏览器按 URL 找副本，找不到自然会请求新的。

**它成立的前提只有一条**：URL 必须唯一标识内容。这条前提一旦破，整个机制失效且不可救——沿用了旧文件名的新内容，会让那份长期缓存变成无法召回的旧副本。

### 它换掉的是什么

| | 按时间失效 | 按名字失效（Content-Hash） |
|:--|:--|:--|
| 依据 | `max-age` 到期 | URL 变化 |
| 有效期 | 必须短到能接受旧内容 | 可以配一年，甚至 `immutable` |
| 回源次数 | 每个周期每用户至少一次 | 只有内容变化时一次 |
| 撤销能力 | 无（只能等或改头） | 有，但要重新构建 |

所以「带哈希的静态资源配一年强缓存」并不是激进配置，而是这套机制下的**正确配置**：既然名字已经保证不会拿到旧内容，限制有效期就只剩下浪费。反过来，给不带哈希的文件配长期强缓存，是把唯一的安全阀关掉了。

### 三种粒度，别混用

构建工具里的 `hash` / `chunkhash` / `contenthash` 是三个不同范围：

| 名字 | 计算范围 | 后果 |
|:--|:--|:--|
| `hash` | 整个构建 | 改任何一个文件，全部文件名都变，缓存全灭 |
| `chunkhash` | 一个 chunk | 同一 chunk 内的 CSS 变化也会让 JS 改名 |
| `contenthash` | 单个文件内容 | 只有自己变了才改名，命中率最高 |

生产环境该用 `contenthash`。用 `hash` 的典型症状是「只改了一行文案，用户要重新下载全部资源」。

### 边界

- **HTML 不能带哈希，也不该带。** 它是入口，名字必须稳定，用户和搜索引擎指向的是同一个 URL。所以 HTML 走协商缓存（`no-cache` + `ETag`），由它去引用带哈希的资源——**整条缓存链的失效，实际上是从 HTML 那一次验证开始的**。
- **它管不了 API 响应和用户数据。** 那些没有「文件名」可改，只能靠代码失效或短 `max-age`。
- **它管不了 CDN 上已经存在的旧副本。** 新文件的 URL 是新键，边缘节点没见过，会回源；但旧 URL 的副本仍在，只是不再被引用。所以「发版后仍看到旧页面」通常是 HTML 被强缓存或 SW 缓存优先，而不是哈希本身失效。
- **内容不变但语义变了的情况它看不出来。** 哈希只对字节负责。如果改动全在运行时约定里（接口字段含义、鉴权规则），产物字节没变，哈希给的就还是旧名字——这一类只能靠接口层的版本化或 `no-cache` 处理。
