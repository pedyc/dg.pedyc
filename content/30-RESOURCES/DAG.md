## 概念：DAG（有向无环图）

有向无环图（Directed Acyclic Graph，简称 DAG）是图论中的一种核心抽象数据结构。它由一组节点（Vertices）和一组具有方向的边（Directed Edges）组成，且满足一个严格的拓扑不变量：**从任意一个节点出发，沿着有向边的方向前行，永远无法回到该节点本身（即无环路 / 无循环回路）**。

**解决的核心痛点**：解决了复杂多任务并行调度、工程依赖解析、数据因果追溯以及分布式流水线编排中**依赖顺序混乱、死锁与循环引用（Circular Dependency）**的问题，为具有先后约束的依赖网络提供了唯一确定的执行序保障（拓扑排序）与最大化的并行切分能力。

---

### 核心命题

* [[DAG 的本质是将偏序因果约束投影为确定性的无死锁拓扑序]]
		* **原理**：DAG 内蕴偏序关系（Partial Order）；通过拓扑排序算法（Kahn / 基于 DFS 的逆后序），能将有向依赖坍缩为一条或多条线性的执行序列，且数学上保证无死锁。
* [[DAG 是实现依赖驱动并发调度与局部增量计算的最佳拓扑]]
		* **原理**：DAG 中入度为 0 的节点互不依赖可立即并行；一旦某个上游节点发生变更，其下游受波及范围严格受限于该节点的可达子图（Reachable Subgraph），从而使最小化增量重算（如构建缓存、响应式状态派生）成为可能。

#### 核心要素与运作机制

1. **拓扑排序（Topological Sort）**：

	* **Kahn 算法（入度表法）**：统计各节点入度 $\text{in-degree}$，将入度为 0 的节点推入就绪队列；出队执行并将后继节点的入度减 1，循环往复。若队列清空后仍有节点未被访问，则判定**存在环路（Cycle）**。
	* **DFS 深度优先遍历**：通过三色标记法（White-未访问 / Gray-正在访问当前路径 / Black-完全回溯）检测反向边（Back Edge），反向边的出现即标志着环路的存在。

2. **入度为 0 的并发池（Concurrency Pool）**：

	* 引擎调度器维护就绪池，所有入度归零的节点均可分发至不同 Worker/线程并发执行，无需阻塞在单一串行链条上。

3. **关键路径法（CPM，Critical Path Method）**：

	* 在加权 DAG（边权为耗时）中，从源节点到汇节点的最长路径决定了整个图调度的最短总工期，指导工程系统优化瓶颈。

### 关键区别

|**维度**|**DAG (有向无环图)**|**Tree (树)**|**DCG (有向有环图 / 通用有向图)**|
|---|---|---|---|
|**入度限制**|节点可有**多个父级节点**（入度 $\ge 0$）|除根节点外，每个节点**必须严格只有一个父节点**（入度 $= 1$）|任意节点入度自由|
|**环路存在性**|**严格无环**|严格无环|**允许存在回路**|
|**依赖表达能力**|支持"多对多依赖"与"汇聚节点"（钻石依赖）|仅支持单一分叉与自顶向下的层级展开|支持反馈调节、递归与双向强耦合环路|
|**调度与求解**|可拓扑排序，必能单向终结，无死锁|天然具备自顶向下/自底向上的递归序|需处理死锁、无限递归与环路检测算法（如 Tarjan SCC）|

### 适用范围

* ✅ **适用场景**
	* **现代前端构建与包管理**：Webpack/Vite 模块依赖图谱分析、Turborepo/Nx 的 Monorepo 构建流水线编排、pnpm 依赖拓扑安装。
	* **响应式框架派生计算**：Vue 3 `computed` 依赖链路、SolidJS / MobX 细粒度更新，避免"钻石依赖"引发的多次重复计算与撕裂。
	* **大数据与工作流编排引擎**：Apache Spark（RDD 转换算子 DAG）、Airflow 调度管道、Git 提交历史（Commit DAG）。
* ⛔ **误用与反模式**
	* **强行用 DAG 建模双向交互反馈网络**：业务流程若天然具备"审核退回修改"、"无限状态轮转"等反馈闭环，硬塞入 DAG 会导致频繁报出循环引用错误，此类场景应选用有限状态机（FSM）或 Petri 网。
	* **缺乏入库环检测导致引擎死锁**：在用户自定义连线或动态导入场景下未在编排前置执行环检测，直接进入入度消费队列会导致调度器挂起等待。
* **失效边界**
	* **循环依赖动态解析**：当系统必须允许模块相互循环引用（如 ESM 中 `a.js` 与 `b.js` 互相 import 并依赖运行时懒加载求值）时，单纯依赖静态 DAG 会失效，必须退回图强连通分量（SCC）缩点或引入动态运行时代理。

### 批判

* **外部批判**
	* **静态建模与动态条件分支的阻抗**：DAG 擅长表达静态依赖拓扑，但面对"运行时根据上游输出条件动态决定是否执行下游某子图"时，需要引入复杂的动态剪枝节点（如 Skip/Condition 节点），使图结构变得臃肿复杂。
* **内在张力**
	* **高度解耦与上下文追踪的矛盾**：DAG 倾向于将节点视为纯函数无状态管道，但在大型分布式任务流中，节点执行往往依赖前序复杂全局上下文或共享中间态，导致纯拓扑声明与隐式副作用之间存在摩擦。
