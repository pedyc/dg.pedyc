> HTTP/1.1 的管道化虽然允许并行发送请求，但服务端必须按序回传，导致了应用层的队头阻塞；HTTP/2 通过二进制分帧实现真正的并发传输。

## 论据/示例

### 1. 队头阻塞（Head-of-Line Blocking, HOLB）的跨版本演进

为了彻底理清管道化在应用层失效的原因，我们可以对比 HTTP/1.1、HTTP/2 和 HTTP/3 在队头阻塞表现上的核心演进：

- **HTTP/1.1 中的应用层队头阻塞**：
	- **机制**：持久连接（Keep-Alive）允许复用单条 TCP 连接。在此基础上，管道化（Pipelining）允许客户端在未收到前一个请求响应时，连续发送多个请求。
	- **问题**：由于**服务端必须按照接收请求的顺序返回响应**，如果排在最前面的请求处理极慢，即使后续请求已处理完毕，其响应也必须排队等待，引发严重的**应用层队头阻塞**。正因这一高危缺陷，实际生产环境中浏览器默认均未启用管道化。
- **HTTP/2 中的多路复用与传输层队头阻塞**：
	- **机制**：引入**二进制分帧机制 (Binary Framing)**，将应用层信息拆分为 Frame（帧）和 Stream（流），改用二进制编码传输。同一个 TCP 连接上支持并发交错传输多个具有独立 ID 的 Stream，客户端与服务端通过 Stream ID 重组消息，实现**多路复用**，彻底消除了应用层队头阻塞。
	- **问题**：但因底层仍基于 TCP 协议，若网络中发生单个数据包丢失，TCP 的滑动窗口和确认重传机制会阻塞后续所有流的数据交付，导致**传输层队头阻塞 (TCP HOL Blocking)**。
- **HTTP/3 中的无阻塞传输（基于 QUIC）**：
	- **机制**：HTTP/3 放弃 TCP，改用基于 UDP 的 **QUIC 协议**。
	- **解决**：QUIC 底层各 Stream 之间完全独立、互不干扰。一旦发生丢包，仅会阻塞发生丢包的对应 Stream，其他 Stream 的数据传输不受任何影响，从根本上消除了传输层队头阻塞。

### 2. 前端工程化策略的变迁

队头阻塞的解决和网络并发性能的提升，直接改变了前端工程化的打包与部署模式：

- **资源打包（Bundle）与雪碧图（Image Sprites）**：
	- _HTTP/1.1 时代_：受限于单域名 6 个 TCP 并发连接数的限制，前端通常会把多个 JS/CSS 打包成大 Bundle，或将零碎图片合并为雪碧图，以此减少 TCP 握手和 HTTP 头开销。
	- _HTTP/2 时代_：多路复用让并发不再受限。过度打包大 Bundle 会使得局部代码修改引发整体强缓存失效。现代工程化更推荐**细粒度 Code Splitting 与按需加载**。
- **域名分片（Domain Sharding）**：
	- _HTTP/1.1 时代_：通过配置多个静态资源子域名（如 `static1.example.com`）来规避单域名 6 个并发连接的硬性限制。
	- _HTTP/2 时代_：多域名会导致额外的 DNS 解析以及多次 TCP/TLS 握手，破坏了单连接多路复用的集中优化优势，域名分片在 HTTP/2 下成为了**反模式 (Anti-Pattern)**。
