## 概念：TCP拥塞控制

> **TCP拥塞控制**是发送端基于网络反馈（丢包或延迟）动态调整拥塞窗口（cwnd），以防止过量数据注入网络导致链路瓶颈节点缓冲区溢出、丢包加剧和吞吐量断崖式下跌（拥塞崩溃）的端到端分布式控制机制。

**解决的核心痛点**：解决分布式网络中各端节点缺乏全局拓扑感知的问题，防止因多主机突发盲目并发发包耗尽网络交换机/路由器的队列缓存，引发**拥塞崩溃（Congestion Collapse）**。

### 核心命题

> 核心命题引用 atomic 笔记（陈述句观点），每个命题是一句话洞见

- [[TCP拥塞控制是端到端的黑盒试探而非中心化精确调度]]
	- **原理**：TCP通信双方无法直接读取网络沿途路由器的即时带宽与队列深度，只能通过 ACK 确认、丢包超时（RTO）或 RTT 抖动等外部信号，间接试探网络瓶颈容量。
- [[拥塞控制与流量控制共同决定TCP最终发送速率]]
	- **原理**：发送端实际生效的发送窗口大小取决于 `W = min(cwnd, rwnd)`，其中 `cwnd`（拥塞窗口）受网络整体健康度约束，`rwnd`（接收窗口）受对端缓冲区处理能力约束。
- [[传统丢包型拥塞控制算法天生存在高丢包高延迟环境下的吞吐衰减缺陷]]
	- **原理**：Reno/Cubic 等基于丢包的算法将"丢包"等同于"网络拥塞"，在弱网随机丢包或长肥网络（BDP 巨大）中会产生误判而激进缩窗，导致带宽利用率极低。

### 运行机制

经典 TCP 拥塞控制状态机（以 Tahoe / Reno 为代表的 AIMD 机制）主要包含四个经典阶段：**慢启动（Slow Start）**、**拥塞避免（Congestion Avoidance）**、**快重传（Fast Retransmit）** 和 **快恢复（Fast Recovery）**。

```mermaid
stateDiagram-v2
    [*] --> 慢启动: 建立连接 (cwnd = 1 IW)
    慢启动 --> 拥塞避免: cwnd >= ssthresh (指数增长转线性增长)
    
    慢启动 --> 慢启动: 超时 (RTO) / ssthresh=cwnd/2, cwnd=1
    拥塞避免 --> 慢启动: 超时 (RTO) / ssthresh=cwnd/2, cwnd=1
    
    慢启动 --> 快恢复: 收到 3 个重复 ACK (3 Dup ACKs)
    拥塞避免 --> 快恢复: 收到 3 个重复 ACK (3 Dup ACKs)
    
    state 快恢复 {
        [*] --> 快速重传丢失分段
        快速重传丢失分段 --> 线性调整cwnd
    }
    
    快恢复 --> 拥塞避免: 收到新数据的 ACK (恢复正常传输)
    快恢复 --> 慢启动: 发生超时 (RTO)
````

1. **慢启动（Slow Start）**：连接初始阶段指数级增长（每经过一个 RTT，`cwnd` 翻倍），快速试探链路基础容量。
2. **拥塞避免（Congestion Avoidance）**：当 `cwnd >= ssthresh`（慢启动阈值），转为加性增（每个 RTT 增加 1 个 MSS），逼近链路极限。
3. **快重传（Fast Retransmit）**：发送端连续收到 3 个重复确认（Dup ACKs）时，不等超时立即重传丢失报文。
4. **快恢复（Fast Recovery）**：3 个 Dup ACK 判定为非恶性拥塞，将 `ssthresh = cwnd / 2`，`cwnd` 设为 `ssthresh + 3` 维持管道饱和，避免直接退化回 `cwnd = 1`。

### 关键区别

|**维度**|**[[TCP拥塞控制]]**|**[[TCP流量控制]]**|
|---|---|---|
|**核心逻辑**|**保护全局网络**：防止过多数据涌入中间链路和路由器|**保护通信对端**：防止发送方发包过快塞满接收端缓存|
|**控制主体**|发送方自主推测网络状态并维护的 `cwnd` (Congestion Window)|接收方通过 TCP 首部显式告知的 `rwnd` (Receive Window)|
|**反馈信号**|丢包（超时/重复ACK）、RTT 延迟增大、ECN 显式标记|接收端在 ACK 报文中通告的剩余窗口大小（Window Size）|
|**作用范围**|全局、多跳路由链路构成的分布式环境|端到端单点对等连接（Sender 与 Receiver 之间）|

### 适用范围

- ✅ **适用场景**
	- **骨干网与高可靠有线网络传输**：在丢包极小、链路稳定的光纤/以太网环境中，Cubic/BBR 等算法能够极大化打满链路带宽。
	- **高吞吐数据搬运**：如大文件上传下载、媒体流推流分发。
- ⛔ **误用**
	- **在移动无线弱网中生搬基于丢包的算法（如 Reno）**：无线电磁干扰易引起随机丢包（非拥塞），Reno 会误判为拥塞并骤降 50% 发送速率，导致严重性能劣化。
	- **超低时延微秒级内部网络（如数据中心 RDMA 场景）**：传统内核级 TCP 拥塞反馈周期（毫秒级 RTT）过长，容易引起 Bufferbloat（缓冲区膨胀）并增加尾延迟。
- **失效边界**
	- **无连接传输层协议**：对 UDP 生态（原生 DNS、实时音频视频裸流）无强制约束，需在应用层自定义拥塞控制（如 WebRTC 的 GCC、QUIC 的 BBR）。
	- **单向单包交互**：对于单次 HTTP 短请求/响应，尚未脱离慢启动阶段即已结束连接。

### 批判

- **外部批判**
	- **丢包反馈滞后性（BBR 学派观点）**：基于丢包（Loss-based）的算法本质上是"把交换机缓冲区撑爆才感知到堵车"，这会导致严重的 **Bufferbloat（缓冲区膨胀）**，带来不必要的高延迟；BBR 提出应基于瓶颈带宽（BtlBw）和最小往返时间（RTprop）来控制发送。
	- **公平性悖论（Fairness vs. Efficiency）**：AIMD 规则追求 Reno-Friendly（与老算法公平竞争），导致新算法在面对老算法的激进挤占时要么妥协降低吞吐，要么过于激进破坏网络生态。
- **内在张力**
	- **深队列与低延迟的不可兼得**：为了跑满高 BDP（带宽时延积）链路，发送端倾向于将队列塞满以提高吞吐，但这必然导致排队延迟激增，与交互式实时通信（低延迟诉求）存在根本冲突。
