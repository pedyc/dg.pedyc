## SOP：实施主线程让渡与异步调度

> 标准化拆解 CPU 密集型任务与长耗时批处理操作，主动让渡主线程（Yield to Main Thread），避免长时间阻塞渲染与用户输入，提升页面响应度并优化 INP 指标。

目标：将所有超过 50ms 的长任务（Long Task）拆分为连续的小粒度任务，保证在执行密集计算时主线程能及时响应点击、输入及每一帧的绘制（保持 60/120 FPS）。
实现：按场景选用 `scheduler.yield()`、`scheduler.postTask()` 或 `MessageChannel` 宏任务切片，并建立降级兜底机制。

> **问题溯源**：本 SOP 是 [[Q-大计算量或批量数据处理导致主线程冻结与交互迟钝]] 的收敛成果——经过多方案对比和实践验证，固化为标准流程。

---

### 适用场景

- 场景 1：初始化或数据同步时需要批量处理海量数据（如批量解析 5000+ 条数据、生成大型 DOM 片段）。
- 场景 2：用户交互后伴随重度计算（如实时过滤、模糊匹配、前端报表汇总），导致 INP（Interaction to Next Paint）恶化。
- 场景 3：非关键脚本（日志上报、预加载计算）抢占关键渲染资源。

### 核心步骤

1. **识别与评估任务特征**
	- 通过 DevTools Performance 面板确认是否存在超过 50ms 的 Long Task。
	- **决策分流**：
		- 若为**纯计算且耗时巨大**（如图片编解码、加密解密、复杂几何运算），优先移至 **Web Worker**，不占用主线程。
		- 若为**与 DOM 操作交织或渐进式渲染**，采用**主线程分片让渡（Yielding）**。

2. **封装通用的让渡工具函数（Yield Utility）**
	- 优先使用现代浏览器标准的 `scheduler.yield()`。
	- 针对不支持的环境，使用 `MessageChannel` 封装宏任务切片降级方案（避免 `setTimeout(fn, 0)` 的 4ms 最小嵌套延迟）。

3. **在耗时循环中设置时间切片检查点**
	- 避免每个微小迭代都让渡（频繁让渡会因上下文切换和调度开销导致总体耗时拉长）。
	- **推荐策略**：设置一个时间阈值（如每执行 5~16ms 检查一次耗时），超时则让渡一次。

4. **对并发任务实施优先级调度（Prioritized Scheduling）**
	- 结合 `Prioritized Task Scheduling API`（`scheduler.postTask`），按重要性分配等级：
		- `user-blocking`：直接影响当前视图和交互的最高优先级任务。
		- `user-visible`：默认优先级，用户可见但非阻塞核心操作。
		- `background`：低优先级后台任务（日志、预热、缓存）。

### 实践/示例

#### 1. 现代化让渡封装与时间切片（Time-Slicing）

```ts
/**
* 主线程让渡封装：优先使用原生 scheduler.yield()，降级到 MessageChannel
*/
export async function yieldToMain(): Promise<void> {
// 1. Chrome 129+ 原生优先
if ('scheduler' in window && 'yield' in (window.scheduler as any)) {
	return await (window.scheduler as any).yield();
}

// 2. 降级方案：MessageChannel 宏任务
return new Promise((resolve) => {
	const channel = new MessageChannel();
	channel.port1.onmessage = () => resolve();
	channel.port2.postMessage(null);
	});
}

/**
* 示例：使用时间切片批量处理大数组，防止阻塞 UI
*/
export async function processLargeArrayInChunks<T, R>(
	items: T[],
	processor: (item: T, index: number) => R,
	deadlineBudgetMs: number = 10 // 每批次占用主线程上限（ms）
	): Promise<R[]> {
	const results: R[] = [];
	let lastYieldTime = performance.now();
	
	for (let i = 0; i < items.length; i++) {
		results.push(processor(items[i], i));
	
	// 检查当前任务占用时间是否已超过预算
	if (performance.now() - lastYieldTime > deadlineBudgetMs) {
		await yieldToMain();
		lastYieldTime = performance.now(); // 重置计时
	}
}

return results;
}
```

#### 2. 使用 `scheduler.postTask` 进行优先级控制

```ts
// 高优先级：立即反馈用户输入结果
scheduler.postTask(() => {
	updateInteractiveUI();
}, { priority: 'user-blocking' });

// 默认优先级：渲染次要列表项
scheduler.postTask(() => {
	renderSecondaryList();
}, { priority: 'user-visible' });

// 低优先级：发送埋点与统计数据
scheduler.postTask(() => {
	sendAnalyticsBatch();
}, { priority: 'background' });
```

### 常见坑点

- ⛔ **反模式：使用 `Promise.resolve().then(…)` 做让渡**
	- 原因：Promise 回调属于**微任务（Microtask）**。微任务会在当前宏任务结束前全部清空，主线程**根本不会让出控制权**给浏览器进行渲染和事件处理。
	- 规范：让渡必须通过宏任务或专门的调度 API（如 `scheduler.yield()` / `MessageChannel`）。
- ⛔ **反模式：每次循环无脑 `await yieldToMain()`**
	- 现象：原本总耗时 100ms 的任务，拆成 10,000 次让渡后总耗时变成数秒。
	- 规范：务必配合耗时阈值（如 5~16ms 预算）批量让渡，平衡总吞吐量与单次响应性。
- 🔧 **排查：`requestIdleCallback` 执行时机不可控**
	- 检查：`requestIdleCallback` 适用于低优先级后台任务，且在 Safari 上兼容性欠佳；对于影响关键链路的任务切片，不可依赖 `requestIdleCallback`，应使用 `scheduler.yield` 或切片方案。
