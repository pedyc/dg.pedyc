## 问题

> 在分布式服务器集群部署的场景下，若未对基础设施进行同步配置，默认的协商缓存响应头中哪一个最容易因为多台机器物理差异而导致缓存大面积失效？

---

## 背景

此问题源于分布式系统架构中的常见痛点。在集群环境下，为了提升性能和减少带宽，通常会利用 HTTP 的协商缓存机制（如 `ETag` 和 `Last-Modified`）。然而，当集群中各节点的操作系统、文件系统、时间或软件版本存在细微差异时，本应高效工作的缓存机制可能意外失效，导致回源请求激增，拖累整体性能。理解哪个响应头最敏感，是进行架构调优的第一步。

---

## 解决方案

### 答案 1：`ETag` 是主要元凶

**核心观点**：`ETag` 因其生成机制的多样性，对机器间的物理和配置差异最为敏感，是导致缓存失效的首要因素。

- **机制分析**：`ETag` 旨在作为资源的唯一强标识符。但它的生成方式依赖于服务器实现：
		- **基于文件元数据**：如文件修改时间（`mtime`）、文件大小（`size`）或 inode 编号。这些属性在集群的不同机器上（尤其是文件未通过共享存储同步时）极易不同。
		- **基于内容哈希**：如对文件内容计算 MD5。如果集群节点上的资源版本存在微小差异（例如，部署时间不一致导致的配置文件差异），计算结果也会不同。
- **失效场景**：客户端从服务器 A 获取资源及其 `ETag` 并缓存。下一次请求被负载均衡到服务器 B。服务器 B 对相同路径的资源计算出不同的 `ETag`。客户端携带的旧 `ETag` 与服务器 B 的新 `ETag` 不匹配，服务器 B 判定缓存无效，返回完整响应（200），导致缓存命中率急剧下降。

### 答案 2：`Last-Modified` 的差异相对可控

**核心观点**：`Last-Modified` 虽然也受时钟不同步影响，但问题更易于发现和解决。

- **机制分析**：`Last-Modified` 基于资源的最后修改时间。
- **失效场景**：若服务器 A 和 B 的系统时间不同步（比如相差几分钟），则同一资源的 `Last-Modified` 时间在 A 和 B 上显示不同，导致验证失败。
- **可控性**：这个问题有标准的解决方案——部署 NTP（网络时间协议）服务来同步所有集群节点的系统时钟。相比之下，`ETag` 的不一致源于更深层的配置和算法差异，排查和统一难度更高。

### 我的理解

**结论**：在缺乏专项配置的集群中，`ETag` 的确是导致缓存大面积失效的首恶。它就像一把精度极高的尺子，一旦不同机器使用不同的"刻度标准"（即生成算法或依赖的元数据），测量同一物体便会得出不同结果。

**关键洞察**：`ETag` 的"强校验"特性在这里变成了"双刃剑"。我们的目标不是放弃 `ETag`，而是让集群中的所有机器"使用同一把尺子"。这要求我们在架构设计时，将 `ETag` 的生成逻辑视为一种**全局配置**，而非节点本地行为。

## 探索路径

- [ ] **调研**：梳理当前集群中各节点使用的 Web 服务器（如 Nginx, Apache）的 `ETag` 默认生成策略。
- [ ] **测试**：在测试环境中，关闭 Nginx 的 `etag` 指令，或修改其计算方式（如使用 `file-etag` 指令），观察缓存命中率变化。
- [ ] **方案设计**：若使用共享存储（如 NFS），研究如何让所有节点基于共享存储上的同一份文件元数据生成 `ETag`。
- [ ] **路由策略**：评估引入一致性哈希负载均衡策略（如 Nginx 的 `hash $request_uri consistent;`），将同一资源的请求始终路由到同一节点，从根本上绕开 `ETag` 不一致问题。

---

## 待验证（扩展）

- [ ] **验证点 1**：在使用 Nginx 时，设置 `etag off;` 并完全依赖 `Last-Modified` 进行缓存验证，在时钟同步后，对比开启/关闭 `ETag` 下的缓存命中率数据。
- [ ] **验证点 2**：在 Java 应用（如 Spring Boot）中，验证 `ShallowEtagHeaderFilter` 的行为。该 Filter 默认基于响应内容计算 MD5，它能消除文件系统差异，但会引入计算开销，需评估其性能影响。
- [ ] **验证点 3**：对于静态资源，验证是否可以通过构建流程，将资源的哈希值写入文件名（如 `app.a1b2c3.js`），并设置强缓存（`Cache-Control: max-age=31536000`），从而完全避免协商缓存带来的复杂性。
