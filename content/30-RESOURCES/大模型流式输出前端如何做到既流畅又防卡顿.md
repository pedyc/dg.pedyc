## 问题

在大模型（LLM）对话与生成式应用中，服务端通常采用 Server-Sent Events (SSE) 或 WebSocket 以极高频率（每秒几十至上百次 chunk）持续向前端推送 Token。当输出超长文本、复杂 Markdown（含实时代码高亮、公式 LaTeX、Mermaid 图表、HTML 标签）时，前端频繁触发 DOM 树重排（Reflow）、重绘（Repaint）以及 JS 运算阻塞主线程，导致打字机动画掉帧、用户无法平滑滚动甚至页面假死。前端应如何从数据流调度、DOM 渲染、[[富文本解析]]与滚动视口等多维度实现丝滑流畅的防卡顿体验？

---

## 背景

1. **数据推送与渲染频率阻抗**：LLM 吐字频率与网络分块（chunk）是不均匀的，瞬时可能到达多个高频小包；而浏览器屏幕刷新率通常为 60Hz/120Hz（每帧约 16.6ms / 8.3ms）。若每个 chunk 到达都直接触发一次全量解析和 React/Vue 响应式更新，极易导致 JS 线程长期占满，掉帧卡顿。
2. **Markdown 与 AST 解析开销激增**：流式推送过程中，内容持续增长。如果每次收到 chunk 都对全部文本进行 `marked.parse` 或 `markdown-it` 全量 AST 重新解析，时间复杂度会随文本长度呈指数或二次方暴增。
3. **复杂富媒体与数学公式渲染损耗**：实时渲染 KaTeX/MathJax、Highlight.js/Prism.js 或 Mermaid 图表需要昂贵的 DOM 节点创建与样式计算；若在流式未闭合状态（如未闭合的代码块 ```` ```js ````）频繁触发高亮与重排，会导致严重布局抖动（CLS）。
4. **自动触底滚动的性能摩擦**：边流式输出边跟随滚动（Auto-scroll to bottom）时，频繁调用 `scrollIntoView` 或修改 `scrollTop` 会强制触发同步布局（Forced Synchronous Layout）。

---

## 解决方案

### 方案 1：数据层缓冲调度与帧同步打字机（Buffer Queue + RAF / Web Worker）

* **核心思路**：将"网络层数据接收"与"UI 视图层渲染"解耦。建立内存缓冲区（Buffer），使用 `requestAnimationFrame` (RAF) 按照屏幕刷新率匀速消费字符。
* **具体实现**：
	* **环形/双端缓冲队列**：SSE 接收到的 chunk 仅 push 进队列，不直接触发视图 setState。
	* **RAF 动态调速打字机**：在每帧 RAF 回调中，根据队列积压长度动态调整步长（积压多则一次取 3~5 字，积压少则 1 字），确保视觉上均匀平滑输出，避免忽快忽慢。
	* **Web Worker 卸载计算**：将繁重的大文本正则切片、清洗、基础解析移至 Worker 线程，主线程仅接收结构化增量。

---

### 方案 2：分块增量解析与静态节点固化（Incremental Markdown Parsing）

* **核心思路**：避免全量 Markdown 解析，将长文本划分为"已完成闭合块（Frozen Blocks）"与"正在生成的活动块（Active Block）"。
* **具体实现**：
	* **按段落（Block-level）解耦**：以双换行符 `\n\n` 为界，已完成的段落、表格、代码块编译为静态 AST 后进行缓存/虚拟 DOM 固化（`React.memo` / Vue 的 `v-once`），不再重复参与后续渲染。
	* **尾部未闭合字符保护（Incomplete Syntax Patching）**：针对行末可能处于中间态的语法（如未闭合的 `**加粗**`、`` `代码` `` 或 HTML 实体），在解析前自动补齐闭合标记，避免整个段落解析崩溃或闪烁。
	* **富媒体懒编译**：对复杂图表（Mermaid）或大型代码块，在流式传输阶段仅展示轻量纯文本/占位骨架，直至该代码块完全闭合（收到结束符）或流结束时再触发二次渲染。

---

### 方案 3：DOM 虚拟化与内容可见性优化（Virtual List + content-visibility）

* **核心思路**：减少主文档中活跃的真实 DOM 节点数量，降低浏览器的 Style 计算与 Layout 成本。
* **具体实现**：
	* **CSS `content-visibility: auto`**：为对话历史消息卡片设置 `content-visibility: auto` 与 `contain-intrinsic-size`，让视口外的历史消息脱离渲染树，显著降低长会话的重排消耗。
	* **对话级虚拟滚动**：针对包含数百条上下文的大型会话，采用基于动态高度的虚拟列表（如 `@tanstack/react-virtual` 或 `vue-virtual-scroller`），只渲染视口内可见的消息节点。

---

### 方案 4：防抖动智能滚动策略（Decoupled Smooth Scrolling）

* **核心思路**：解耦用户手动滚动与自动触底滚动，消除强制同步回流。
* **具体实现**：
	* **用户交互意图感知**：监听 `wheel`、`touchmove` 事件；一旦用户向上回滚查看历史，立刻解绑自动吸底，禁止抢夺滚动条焦点。
	* **RAF 批量滚动与 Passive 监听**：滚动事件使用 `{ passive: true }`，且滚动距离的累加与执行统一合并至 RAF 阶段，避免在 SSE 回调中直接同步读取并修改 `scrollTop`。

---

## 方案决策与权衡矩阵

| 优化维度 | 缓冲队列 + RAF 调速 | 增量/块级 AST 解析 | 虚拟化 + content-visibility | 复杂度 |
| :--- | :--- | :--- | :--- | :--- |
| **解决痛点** | 高频 chunk 导致掉帧、忽快忽慢 | 长文本二次方解析开销、UI 假死 | 对话轮次过多时的 DOM 膨胀 | — |
| **实现难度** | 中等（需处理动态步长与打断中断） | 较高（需处理流式未闭合 Markdown） | 中等（CSS 方案成本低，虚拟列表需处理动态高度） | — |
| **首字延迟 (TTFT)** | 无额外延迟（队列首字即刻消费） | 无额外延迟 | 无影响 | — |
| **推荐优先级** | ⭐⭐⭐⭐⭐ (基础必做) | ⭐⭐⭐⭐⭐ (长文本/富文本必做) | ⭐⭐⭐⭐ (多轮长对话必做) | — |
