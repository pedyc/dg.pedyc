异步请求的状态竞争（Race Condition）本质是：

> **多个异步操作同时进行，但它们完成的顺序与发起顺序不一致，导致旧请求覆盖了新请求的结果。**

这是前端状态管理里非常重要的一类问题。

---

## 问题拆解

### 最典型的例子：搜索框

用户快速输入：

```text
p
pe
ped
pedy
```

程序可能发起：

```text
请求 A：搜索 "p"
请求 B：搜索 "pe"
请求 C：搜索 "ped"
请求 D：搜索 "pedy"
```

假设实际返回顺序是：

```text
A ───────────────→ 返回
B ───────→ 返回
D ───────→ 返回
C ─────────────────→ 返回
```

最后返回的是：

```text
C = "ped"
```

如果代码简单地：

```ts
const result = await fetchUsers(keyword)
setUsers(result)
```

那么最终 UI 可能显示：

```text
"ped"
```

而用户实际上已经输入：

```text
"pedy"
```

这就是典型的：

> **旧请求的结果覆盖了新请求的结果。**

---

## 解决方案

### 第一种方案：请求 ID / 序列号

这是非常通用、容易理解的解决方式。

```ts
let requestId = 0

async function search(keyword: string) {
  const id = ++requestId

  const result = await fetchUsers(keyword)

  if (id !== requestId) {
    return
  }

  users.value = result
}
```

执行过程：

```text
第一次请求
requestId = 1

第二次请求
requestId = 2

第三次请求
requestId = 3
```

如果请求 1 最后才回来：

```text
请求 1
  ↓
id = 1
  ↓
当前 requestId = 3
  ↓
丢弃
```

而请求 3：

```text
id = 3
当前 requestId = 3
       ↓
接受结果
```

核心原则：

> **只有最后一次请求有资格提交结果。**

前端可以做[[防抖和节流|防抖]]，当用户快速输入时，只取最后一次发送请求

这个方案特别适合：

- 搜索
- 自动补全
- 实时筛选
- 快速切换 Tab
- 根据参数重新加载数据

---

### 第二种方案：取消旧请求

如果使用 `fetch`，可以通过 `AbortController`：

```ts
let controller: AbortController | null = null

async function search(keyword: string) {
  controller?.abort()

  controller = new AbortController()

  try {
    const response = await fetch(
      `/api/search?q=${keyword}`,
      {
        signal: controller.signal
      }
    )

    const data = await response.json()

    users.value = data
  } catch (error) {
    if (error instanceof DOMException && error.name === "AbortError") {
      return
    }

    throw error
  }
}
```

过程：

```text
请求 A
    │
    │
请求 B
    ├── abort A
    │
请求 C
    ├── abort B
    │
    ▼
只有 C 继续
```

优点是：

> **不仅避免旧结果提交，还可以尽早终止不再需要的请求。**

但是要注意：

**取消请求和保证状态正确是两个不同问题。**

实际系统中仍然可能需要请求 ID / 版本检查作为最终保护。

### 第三种方案：比较请求参数

例如：

```ts
const keyword = ref("")

async function search() {
  const currentKeyword = keyword.value

  const result = await fetchUsers(currentKeyword)

  if (currentKeyword !== keyword.value) {
    return
  }

  users.value = result
}
```

逻辑是：

```text
请求开始
  ↓
记录 keyword = "ped"
  ↓
等待
  ↓
请求返回
  ↓
当前 keyword 还是 "ped"？
   │
  ├── 是 → 使用结果
  └── 否 → 丢弃
```

这实际上和 request ID 是同一种思想：

> **结果提交之前验证它是否仍然对应当前状态。**

不过 request ID 通常更加通用，因为参数可能是多个变量。

---

### 第四种方案：使用状态管理库提供的 Query 机制

如果项目使用：

- TanStack Query
- SWR
- Apollo Client
- Vue Query

那么通常不需要自己管理所有请求竞争。

例如 TanStack Query：

```ts
const { data, isLoading } = useQuery({
  queryKey: ["users", keyword],
  queryFn: () => fetchUsers(keyword)
})
```

这里：

```text
keyword = "ped"
      ↓
queryKey = ["users", "ped"]

keyword = "pedy"
      ↓
queryKey = ["users", "pedy"]
```

不同请求属于不同的 Query。

框架会帮助处理：

- 请求生命周期
- 缓存
- 去重
- stale 状态
- 请求竞争
- refetch
- 错误状态
- loading 状态

因此对于复杂应用：

> **不要把 Server State 全部手写成 `useState` / `ref` + fetch。**

这也是你上一题"服务端状态与客户端状态生命周期不同"的一个具体体现。

### 其他情形：组件已经卸载

还有一种竞争：

```text
Component
   │
   ├── 发起请求
   │
   ├── 用户离开页面
   │
   └── Component unmount
             │
             ▼
          请求返回
```

如果请求回来之后仍然执行：

```ts
setData(result)
```

就可能产生不必要的更新或副作用。

现代 React / Vue 中，通常可以通过 cleanup + `AbortController` 处理。

React：

```tsx
useEffect(() => {
  const controller = new AbortController()

  fetch("/api/user", {
    signal: controller.signal
  })
    .then(…)
  
  return () => {
    controller.abort()
  }
}, [])
```

Vue：

```ts
const controller = new AbortController()

onUnmounted(() => {
  controller.abort()
})
```

核心思想都是：

> **异步任务的生命周期应该和它所服务的 UI 生命周期保持一致。**

---

## 不要只处理"旧数据"，还要处理 loading 和 error

状态竞争不只是：

```text
旧数据覆盖新数据
```

还可能发生：

```text
请求 A
请求 B

B 成功
A 失败
```

如果代码是：

```ts
loading.value = true

try {
  const data = await request()
  result.value = data
} catch {
  error.value = "请求失败"
} finally {
  loading.value = false
}
```

那么：

```text
A ───────────────────→ finally
B ───────→ success
```

B 明明已经完成：

```text
loading = false
```

但 A 最后执行：

```text
loading = false
```

可能不会造成明显问题。

更复杂的情况下，A 的 `error`、`loading`、`data` 都可能覆盖 B 的状态。

因此应该把：

```text
data
loading
error
```

看成**同一个请求版本下的状态集合**。

例如：

```ts
const id = ++requestId

loading.value = true

try {
  const data = await request()

  if (id !== requestId) return

  result.value = data
} catch (error) {
  if (id !== requestId) return

  error.value = error
} finally {
  if (id === requestId) {
    loading.value = false
  }
}
```

## 一个更本质的解决思路：给异步操作建立"版本"

这其实是最值得记住的抽象。

假设：

```text
状态版本：

v1 → 请求 A
v2 → 请求 B
v3 → 请求 C
```

请求返回：

```text
A 返回 → v1
B 返回 → v2
C 返回 → v3
```

当前状态：

```text
v3
```

于是：

```text
A → v1 ≠ v3 → 丢弃
B → v2 ≠ v3 → 丢弃
C → v3 = v3 → 提交
```

所以：

> **异步结果提交前，必须确认它仍然属于当前状态版本。**

这比单纯记住 `AbortController` 更重要。

---

## 实际项目怎么选择？

可以这样：

|场景|常见方案|
|---|---|
|简单一次性请求|直接 `await`|
|快速搜索|请求 ID / AbortController|
|自动补全|AbortController + 请求版本|
|页面切换|生命周期 cleanup + AbortController|
|多参数查询|Query Key / 请求版本|
|复杂 Server State|TanStack Query / Vue Query / SWR|
|必须保证结果顺序|请求序列号 / 版本|
|旧请求结果绝不能覆盖新状态|**版本检查是最终防线**|

---

### 最后总结

异步竞争问题可以归结成三个问题：

```text
                       异步请求
                          │
        ┌────────┼────────┐
        ▼                ▼                ▼
      谁最新？         谁有效？         谁还需要？
        │                │                │
     Request         ID 版本检查      AbortController
                                      生命周期 cleanup
```

其中最核心的原则是：

> **异步任务完成 ≠ 它的结果仍然有效。**

一个请求即使成功返回，也必须先判断：

```text
这个结果是不是当前状态所需要的结果？
```

如果不是，就应该丢弃。

这也是前端异步状态管理中非常重要的一个思维转变：**不要把"请求成功"直接等同于"应该更新 UI"。**
