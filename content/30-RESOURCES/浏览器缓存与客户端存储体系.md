## 概念：浏览器缓存与客户端存储体系

> 浏览器缓存与客户端存储体系 **是指浏览器在处理网络资产加载与应用运行时数据时，所构建的涵盖"网络级资源拦截流水线（Network-Level Cache Pipeline）"** 与 **"应用级数据持久化方案（Application-Level Storage APIs）"** 的多层级、异构式存储协同架构。

**解决的核心痛点**：解决单一体积网络传输带来的带宽浪费与高时延（RTT）白屏问题，同时为富客户端 Web 应用（SPA/PWA）提供跨页面会话、离线可用以及大容量结构化数据的持久化管理能力。

### 核心命题

> 核心命题引用 atomic 笔记（陈述句观点），每个命题是一句话洞见

- [[网络级资源缓存与应用级数据存储存在严格的调用控制边界]]
	- **原理**：Memory Cache 与 Disk Cache 是渲染引擎底层的黑盒行为，由 HTTP 协议头驱动且无法被 JavaScript 显式读写；而 Web Storage、IndexedDB 和 Cache API 属于应用层 API，受同源策略和 JavaScript 运行栈直接控制。
- [[Service-Worker是连接网络请求拦截层与应用级存储层的唯一运行时桥梁]]
	- **原理**：Service Worker 运行在独立后台线程中，通过监听全局 `fetch` 事件拦截所有网络请求，并可编程调用 `Cache API` 或 `IndexedDB` 决定是返回本地缓存副本还是透传网络。
- [[localStorage与sessionStorage的同步I-O特性会阻塞主线程渲染]]
	- **原理**：Web Storage 采用同步读写机制，底层涉及磁盘或 SQLite 的同步 I/O，在频繁读写大体积数据时会直接卡死 JavaScript 运行主线程并导致丢帧，大容量数据应全面迁移至异步非阻塞的 `IndexedDB`。
- HTML通过协商缓存感知更新，静态资源通过内容哈希解决缓存失效问题
	- **原理**：HTML是应用入口，必须通过协商缓存感知更新；静态资源长期不变，通过强缓存减少网络请求

### 运行机制

浏览器针对网络资源的查找拦截遵循严格的自上而下优先级流水线（注意：`Push Cache` 已被现代浏览器废弃）：

```mermaid
flowchart TD
    Start(["发起资源请求"]) --> CheckSW{"1. 注册了 Service Worker 且命中?"}
    
    CheckSW -- "是" --> SWHandle["执行 fetch 拦截逻辑<br/>从 Cache API 或自定义逻辑返回"]
    CheckSW -- "否 / 未命中" --> CheckMemory{"2. Memory Cache 是否存在有效副本?"}
    
    CheckMemory -- "命中 (Base64/字体/同页复用CSS)" --> ReadMem["从 RAM 内存快速读取 200 (Memory Cache)"]
    CheckMemory -- "未命中" --> CheckDisk{"3. Disk Cache 强缓存是否有效?<br/>(Cache-Control / Expires)"}
    
    CheckDisk -- "强缓存命中" --> ReadDisk["从磁盘读取 200 (Disk Cache)"]
    CheckDisk -- "强缓存失效 / no-cache" --> SendHTTP{"4. 发起网络请求 (协商缓存)"}
    
    SendHTTP -- "ETag / Last-Modified 校验未变" --> Resp304["304 Not Modified<br/>刷新缓存元数据并复用本地数据"]
    SendHTTP -- "资源更新 / 无缓存" --> Resp200["200 OK<br/>下载完整 Body 并写入 Disk/Memory Cache"]
````

### 关键区别

为了彻底消除概念割裂，需将"底层网络级资源缓存"**与**"应用级数据持久化存储"两套体系分维对照：

#### 1. 网络级资源请求缓存流水线（协议与引擎驱动）

|**缓存层级**|**存储介质**|**控制权限**|**命中特点**|**生命周期**|
|---|---|---|---|---|
|**Service Worker Cache**|磁盘 / CacheStorage|**JS 完全可控** (`caches`)|可编程拦截 `fetch`，离线优先|持久化，由代码逻辑更新与淘汰|
|**Memory Cache**|RAM 内存|**浏览器内部调度**（代码不可读写）|快速响应短周期/体积较小资源、预加载标签|关闭当前 Tab 页或刷新即被释放|
|**Disk Cache**|硬盘文件系统|**HTTP 标头控制** (`Cache-Control`)|绝大多数强缓存资源（带 Hash 的静态文件）|受 `max-age`、`immutable` 与磁盘配额管理|
|**协商缓存 (网络层)**|服务器 / CDN|**服务端/请求头协同** (`ETag`, `304`)|强缓存失效后的二次条件请求校验|取决于源服务器资源更新周期|

#### 2. 应用层数据持久化方案（JavaScript API 驱动）

|**存储方案**|**存储介质**|**容量限制**|**数据类型**|**读写机制**|**典型适用场景**|
|---|---|---|---|---|---|
|**Cookie**|硬盘 / 内存|~4 KB|ASCII 字符串|**同步**（每次 HTTP 请求自动随 `Cookie` 请求头携带）|用户鉴权 Token、会话 Session ID|
|**localStorage**|硬盘 (SQLite)|~5~10 MB|纯字符串键值对|**同步阻塞主线程**|用户偏好设置（主题/语言）、持久配置|
|**sessionStorage**|硬盘 / 内存|~5~10 MB|纯字符串键值对|**同步阻塞主线程**（仅限当前单个 Tab 页面生命周期）|多步骤表单草稿、单次会话临时状态|
|**IndexedDB**|硬盘|极大 (磁盘 20%~60% 以上)|对象、TypedArray、Blob、文件等结构化数据|**异步非阻塞**（支持事务机制与游标索引查询）|复杂离线数据、日志埋点本地缓冲、富文本编辑器暂存|
|**Cache API**|硬盘|很大（共享配额）|专门存储 `Request` / `Response` 键值对|**异步非阻塞** (Promise 体系)|PWA 离线资源打包、REST API 响应持久化|

### 适用范围

- ✅ **适用场景**
	- **极致首屏静态分发**：入口 `index.html` 配置协商缓存（`no-cache`），其余带 Content-Hash 的 JS/CSS/字体资产配置一年强缓存（`Cache-Control: max-age=31536000, immutable`）直冲 Disk Cache。
	- **弱网离线与秒开（PWA）**：利用 Service Worker 拦截骨架屏与关键 API 响应并缓存至 Cache API。
	- **大容量离线客户端**：在线文档编辑器、Canvas 绘图应用的大型草稿及历史版本持久化至 IndexedDB。
- ⛔ **误用**
	- **高频大体积数据滥用 localStorage**：在 `scroll`、`resize` 等高频事件或大对象序列化中读写 `localStorage`，造成明显的 JavaScript 运行时卡顿与主线程掉帧。
	- **对无 Hash 静态资产开启长期 Disk 强缓存**：由于无法主动撤销磁盘缓存，发版后用户无法及时获取新代码。
	- **在 Cookie 中存放非鉴权业务数据**：所有同源接口请求都会自动携带 Cookie，过大的 Cookie 体积会导致严重的请求头带宽开销。
- **失效边界**
	- **浏览器存储配额淘汰机制（Eviction Policy）**：当用户磁盘空间紧张时，浏览器会按照 LRU 策略自动清除 Cache API 与 IndexedDB 中未标记为 `persistent` 的数据。
	- **无痕模式（Incognito Mode）**：所有本地持久化存储（localStorage / IndexedDB / Cache API）均降级为内存会话级，窗口全部关闭后立即彻底销毁。

### 批判

- **外部批判**
	- **API 碎片化与维护心智负担**：Web 平台先后推出了 Cookie、Web Storage、WebSQL（已废弃）、IndexedDB、Cache API，各 API 间数据类型与同步/异步机制完全割裂，开发者必须依赖第三方封装库（如 `idb`、`localForage`）才能降低接入成本。
	- **强缓存黑盒不可撤销性**：一旦强缓存写入磁盘，在过期前完全脱离服务端控制，强制将"缓存一致性"问题推给前端打包工具链（强制要求文件名 Hash 化）。
- **内在张力**
	- **持久化容量与主线程性能的权衡**：同步 API（Web Storage）简单易用但伤害性能；异步 API（IndexedDB）性能极佳但代码复杂度极高。
