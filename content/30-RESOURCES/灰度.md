## 术语：灰度

> **主题**：#软件工程/交付

### 定义

灰度（gray release）指把新版本先暴露给一小部分用户或流量，观察其指标与旧版本一致后按批次扩大比例，异常时停止扩大并把已放量部分退回旧版本的发布方式。它不改变系统结构，只改变「哪些请求由哪个版本处理」的分配规则。

英文里没有与「灰度」一一对应的词，最接近的两个是 canary release（金丝雀发布，强调新旧两组对比、先小样本探路）与 staged / gradual rollout（强调按阶段放量）。国内语境把两者混称，严格说 canary 多了「与对照组比指标」这一层——名称出自煤矿用金丝雀试瓦斯。

三个要素决定一次灰度是否成立：

| 要素 | 具体含义 |
|:---|:---|
| 放量单位 | 按比例、按人群、按地域、按租户都行，但分桶必须稳定：同一用户在放量期内始终命中同一版本。漂移会让体验抖动，也会污染指标 |
| 判定线 | 错误率、延迟、业务指标的阈值要在放量前定下。没有判定线的放量不叫灰度，叫「先上一点看看」 |
| 退出方式 | 爆炸半径等于当前放量比例；回滚是停止扩大加已放量部分回流，因此小步扩大的真正收益是随时可以停在一个小数字上 |

### 与相邻手段的区别

| 对照 | 差在哪 |
|:---|:---|
| 蓝绿部署 | 蓝绿是两套完整环境、一次性全量切换，回滚靠切路由（秒级）但爆炸半径 100%；灰度在同一环境内按比例分配，爆炸半径就是那个比例 |
| 特性开关 | 开关决定「哪条代码路径执行」（发布层），灰度决定「哪个版本接请求」（部署 / 流量层）。开关是实施灰度的常见载体，但开关也用于 kill switch 与暗发布 |
| 暗发布 | 暗发布的新路径用户看不见、结果不外露；灰度的用户真实在用新版本并承担后果 |
| A/B 测试 | 目的相反：A/B 要测出哪个更好，长期分流；灰度要确认新版没坏，最终收到 100%。两者共用分流基建，但判定指标与终点不同 |
| [[双跑]] | 双跑的新结果不对任何人返回，验的是「算得一样」；灰度验的是「上线后稳不稳」 |

### 边界

- **前端灰度的放量单位是 HTML，不是 JS**。产物带 hash，HTML 与 JS/CSS 必须同批；新旧 HTML 掺在一起跑，会出现 HTML 引用了不存在的 chunk。只灰 JS 而不灰 HTML，等于把版本错配当作灰度的常态。
- **CDN 让回滚不彻底**。切回旧版本之后，边缘节点上仍缓存着新 HTML 与资源，回滚要连带刷新缓存或改变 URL，否则一部分用户继续命中新版本。
- **分组标记必须在首屏渲染前可得**。只靠客户端 JS 分流会先渲染旧版再跳到新版，出现闪屏；SSR 场景下 HTML 已按某个版本生成，事后改不动。所以分组通常落在 Cookie、请求头或边缘规则上，见 [[Cookie]]。
- **灰度标记本身是状态**，放 localStorage 服务端读不到，放 URL 参数则用户一分享就把分组传出去。
- **它不能替代验证**。灰度只能把故障的影响面缩小，不能证明新版正确；小比例流量跑一周也覆盖不到月末结算这类低频路径——那类等价性要靠 [[双跑]]。
