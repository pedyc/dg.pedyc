## SOP：优化静态资源加载与网络链路

> 标准化 Web 应用在网络传输与资源调度全链路上的优化流程，降低关键资源到达时间（TTFB/FCP/LCP），减少网络阻塞与冗余传输。

目标：首屏关键静态资源（HTML/CSS/核心 JS）网络传输延迟降至极致，实现二次访问 0 网络开销，高价值资源（如 LCP 媒体与核心字体）优先抢占带宽。
实现：配置 HTTP/2+ & Brotli + 构建 ContentHash 强缓存 + 精准实施 Resource Hints（Preload/DNS-Prefetch/Fetchpriority）。

> **问题溯源**：本 SOP 是 [[Q-弱网与首屏加载缓慢关键资源竞争带宽]] 的收敛成果——经过多方案对比和实践验证，固化为标准流程。

---

### 适用场景

- 场景 1：首屏关键资源加载慢（LCP/FCP 不达标），存在关键链路资源阻塞与队头拥塞。
- 场景 2：静态资源二次加载重复请求，CDN 与本地缓存命中率低，服务器带宽开销大。
- 场景 3：第三方资源（CDN 字体、分析脚本、外部图床）建立连接耗时过长，拖慢整体页面加载。

### 流程图解

```mermaid

    A[接入层与协议优化: HTTP/2+ / CDN / Brotli] --> B[制定缓存策略]

    E --> F

    F --> H[预加载首屏核心资源: preload / fetchpriority=high]
    F --> I[非关键脚本延迟执行: defer / async / 按需分包]
    G & H & I --> J[上线并在 DevTools Network / Web Vitals 验证]
````

### 核心步骤

1. **协议层与传输压缩基础建设**
	- **升级传输协议**：全站启用 **HTTP/2** 或 **HTTP/3 (QUIC)**，利用多路复用与头部压缩（HPACK/QPACK）消除 TCP 队头阻塞与并发连接限制。
	- **开启高级文本压缩**：在 Nginx / CDN 边缘节点启用 **Brotli 压缩**（对比 Gzip 体积通常能再缩减 15%~25%），设置 `br` 优先于 `gzip`。
	- **开启 TLS 1.3 与 0-RTT**：减少 HTTPS 握手往返（RTT），降低 TTFB。

2. **建立分层 HTTP 缓存模型**
	- **HTML 入口文件**（绝对禁止强缓存）：
		- 配置 `Cache-Control: no-cache`（每次向服务器校验有效性，配合 `ETag`）。
	- **带 ContentHash 的静态资源（JS / CSS / 字体 / 图片）**：
		- 配置永久强缓存：`Cache-Control: public, max-age=31536000, immutable`。
		- **更新机制**：发版时通过变更文件名 Hash 立即强制刷新客户端，其余时刻完全从内存或磁盘缓存（Memory / Disk Cache）瞬时读取。

3. **配置现代 Resource Hints（资源提示机制）**
	- **DNS 解析与提前建连**：
		- 对关键外部域名（如字体 CDN、图片 CDN）配置 `<link rel="preconnect" href="…">`。
		- 对次要外部域名配置 `<link rel="dns-prefetch" href="…">`。
	- **LCP 核心资源与关键字体预加载**：
		- 使用 `<link rel="preload" as="image" href="…" fetchpriority="high">` 提前加载首屏 Hero 图。
		- 使用 `<link rel="preload" as="font" type="font/woff2" crossorigin>` 预加载关键字体，防止 FOIT（文字闪烁）。
	- **低优先级资源预热**：
		- 使用 `<link rel="prefetch" href="…">` 预测并利用浏览器空闲带宽提前下载下一页路由产物。

4. **非核心资源延后与按需加载**
	- **脚本执行解耦**：所有非关键外部 JS 添加 `defer`（保证解析不阻塞且按序执行）或 `async`（独立无依赖脚本如埋点统计）。
	- **动态分包（Dynamic Import）**：结合打包工具对次要路由组件、重型图表库执行按需拆包（Chunking）。

### 实践/示例

#### 1. Nginx 缓存与压缩配置标准范式

```nginx
# 1. 开启 Brotli 与 Gzip
brotli on;
brotli_comp_level 6;
brotli_types text/plain text/css application/javascript application/json image/svg+xml;

gzip on;
gzip_min_length 1024;
gzip_types text/plain text/css application/javascript application/json image/svg+xml;

# 2. HTML 入口文件：强制协商缓存
location = /index.html {
    add_header Cache-Control "no-cache";
    etag on;
}

# 3. 带 Hash 的打包静态资源：永久强缓存
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
    access_log off;
}
```

#### 2. 页面 `<head>` 资源调度最佳实践

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8" />
  
  <!-- 1. 提前对第三方 CDN 建连 -->
  <link rel="preconnect" href="[https://fonts.example.com](https://fonts.example.com)" crossorigin />
  <link rel="dns-prefetch" href="[https://analytics.example.com](https://analytics.example.com)" />

  <!-- 2. 预加载关键字体并防止闪烁 -->
  <link rel="preload" href="/assets/fonts/inter.woff2" as="font" type="font/woff2" crossorigin />

  <!-- 3. 首屏 LCP 图片提升优先级 -->
  <link rel="preload" fetchpriority="high" as="image" href="/assets/images/hero-banner.webp" type="image/webp" />

  <!-- 4. 关键 CSS 阻塞加载，普通脚本全部 defer 异步化 -->
  <link rel="stylesheet" href="/assets/css/index.a8f9c1.css" />
  <script defer src="/assets/js/app.3d2e1b.js"></script>
</head>
<body>
  <div id="app"></div>
</body>
</html>
```

### 常见坑点

- ⛔ **反模式：HTML 文件被误配为永久强缓存（max-age > 0）**
	- 现象：前端部署上线后，用户必须按 Ctrl+F5 强刷才能看到新版本，产生难以恢复的线上版本分叉。
	- 规范：HTML 必须且只能是 `no-cache` 或 `max-age=0, must-revalidate`。
- ⛔ **反模式：滥用 `<link rel="preload">`**
	- 现象：将非首屏必需的 10+ 个脚本/CSS 全部 preload，导致主线程和网络带宽在加载初期被严重挤占，反倒拖慢了 LCP 资源。
	- 规范：Preload 只给**首屏关键渲染路径前 2~3 个最核心资源**（如首屏 LCP 图像、关键字体、首屏必要 CSS）。
- 🔧 **排查：Preload 字体时缺少 `crossorigin` 导致二次重复下载**
	- 检查：即使字体同域存放，规范中 `<link rel="preload" as="font">` 依然必须携带 `crossorigin` 属性，否则浏览器会以匿名模式下载两次。
