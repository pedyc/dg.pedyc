领域驱动设计（Domain-Driven Design，简称 DDD）是一种软件设计方法论，由 Eric Evans 在 2003 年的同名著作中提出。它的核心思想是：**软件系统的设计应该以业务领域为核心，而不是以技术实现为核心。**

下面从几个层面来介绍 DDD。

## 一、为什么需要 DDD

传统开发中常见的问题是：业务逻辑散落在各个 Service、Controller、DAO 中，代码与业务概念脱节，随着业务复杂化，系统变得难以理解和维护。

DDD 试图解决的核心问题是：**业务复杂度**。它通过让开发人员与领域专家使用同一套语言、建立同一套模型，来降低沟通成本和实现偏差。

> [[DDD通过限界上下文与统一语言降低复杂业务的理解与协作成本]]

需要注意：DDD 适合**业务复杂**的系统。如果只是简单的增删改查，用 DDD 反而会过度设计。

## 二、核心概念

### 1. 通用语言（Ubiquitous Language）

团队（开发、产品、领域专家）在同一个限界上下文内，使用统一、无歧义的业务术语。代码中的类名、方法名应直接反映这些术语。

例如电商场景中，"订单""库存""支付单"这些词在代码和业务讨论中含义完全一致。

### 2. 限界上下文（Bounded Context）

同一个词在不同业务场景下含义可能不同。限界上下文就是**一个模型适用的边界**。

例如"商品"在销售上下文里关注价格、描述；在仓储上下文里关注重量、体积、货位。两者是两个不同的限界上下文，各自有独立的模型。

### 3. 领域（Domain）与子领域（Subdomain）

- **核心域**：业务竞争力所在，最值得投入，如电商的推荐算法。
- **支撑域**：业务需要但不核心，如订单管理。
- **通用域**：行业通用能力，如权限、日志。

### 4. 上下文映射（Context Mapping）

描述多个限界上下文之间的关系与集成方式，常见模式有：

- 防腐层（ACL）：隔离外部模型，避免污染本地模型
- 开放主机服务（OHS）
- 共享内核（Shared Kernel）
- 客户-供应商（Customer-Supplier）

## 三、战术设计（代码层面的构建块）

| 构建块 | 说明 |
|--------|------|
| 实体（Entity） | 有唯一标识、生命周期内标识不变的对象，如订单 |
| 值对象（Value Object） | 无标识、不可变，用属性值判等，如金额、地址 |
| 聚合（Aggregate）与聚合根（Aggregate Root） | 一组相关对象的边界，外部只能通过聚合根访问，保证一致性 |
| 领域服务（Domain Service） | 不属于任何实体/值对象的重要业务逻辑 |
| 领域事件（Domain Event） | 领域中发生的、其他部分关心的事情，如"订单已支付" |
| 仓储（Repository） | 对聚合的持久化抽象，让领域层不依赖具体数据库 |
| 工厂（Factory） | 封装复杂对象的创建 |
| 应用服务（Application Service） | 编排用例流程，本身不含业务规则 |

## 四、战略设计 vs 战术设计

- **战略设计**：划分限界上下文、识别子领域、建立上下文映射。解决"系统怎么切分"的问题。
- **战术设计**：在单个限界上下文内，用实体、值对象、聚合等构建模型。解决"模型怎么落地"的问题。

战略设计优先级更高。边界划错了，战术设计再漂亮也难维护。

## 五、分层架构

典型的 DDD 分层：

1. **用户接口层**：Controller、DTO，处理请求响应
2. **应用层**：编排用例，协调领域对象，不含业务规则
3. **领域层**：实体、值对象、领域服务、领域事件——业务核心
4. **基础设施层**：数据库、消息、外部服务实现

依赖方向由外向内，领域层不依赖基础设施。

## 六、聚合设计的关键原则

- 聚合内强一致性，聚合间最终一致性
- 聚合尽量小，只把真正需要原子一致的放入同一聚合
- 外部只能持有聚合根的引用
- 一次事务只修改一个聚合

例如：订单和订单项在同一聚合；订单和库存不应在同一聚合，跨聚合用领域事件解耦。

## 七、DDD 的常见误区

1. **把 DDD 当成技术框架**：DDD 是方法论，不是 Spring 那样的工具。
2. **贫血模型**：只有 getter/setter，业务逻辑全在 Service，这不是 DDD。
3. **过度设计**：简单业务硬套 DDD，增加复杂度。
4. **忽视战略设计**：只关注代码结构，不划分上下文。

## 八、适用场景

**适合**：业务规则复杂、需求频繁变化、团队需要与领域专家紧密协作的系统，如金融、保险、供应链、ERP。

**不适合**：以数据展示或简单 CRUD 为主的系统。
