> 没有 CSP 时，浏览器对资源来源不做判定——页面引什么就加载什么。CSP 在加载与执行前插入一道判定，依据预先声明的策略决定放行还是拦截。

**边界**：它判定的是脚本的**来源与内联性**，不是脚本**做了什么**。一段代码通过来源检查之后，读 Cookie、发请求、改 DOM 一概不管。所以 CSP 拦的是「新注入进来的脚本」，拦不住「已被信任的脚本被利用」——供应链投毒里打进产物包的代码来源是 `'self'`，照样放行。

## 论据/示例

判定点落在资源生命周期的三个位置：取（`connect-src` / `img-src`）、解析（`script-src` / `style-src`）、执行（`unsafe-eval`、内联脚本的 nonce / hash 校验）。

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-abc123'
```

`nonce` 与 `hash` 的机制含义值得单说：CSP 允许内联脚本的唯一方式，是「你事先声明了这段脚本的指纹」，而不是「你声明了允许内联」。`'unsafe-inline'` 一旦出现，判定就退化成放行。

开哪些指令、怎么灰度、报告怎么收属于策略侧，归 [[Web安全]]；本笔记只回答判定发生在哪一步。
