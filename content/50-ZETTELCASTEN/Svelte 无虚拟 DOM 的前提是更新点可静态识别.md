> Svelte 在~~编译阶段~~分析组件模板，生成精准的原生 JavaScript DOM 操作指令，无需虚拟 DOM 运行时

**边界**：编译期确定更新路径的前提是更新点可静态识别。动态组件、运行时拼装的模板、跨组件传递的插槽仍需运行时调度，那时 Svelte 与带运行时的框架差距收窄。

第二条边界与版本有关：编译期只固定「哪个节点依附哪个表达式」，**不固定「谁依赖谁」**。后者在 Svelte 4 及以前靠编译器静态分析，5 起交给运行时信号图。所以这条命题在两代都成立，但「编译时响应式」这个更常被顺手带上的说法，只对 4 及以前成立。

## 论据/示例

**三条路线各自省在哪一步**（不写体积数字：它随版本、压缩方式与 tree-shaking 变化，写下来一年就过期）：

| 框架 | 运行时依赖 | DOM 更新方式 |
|:---|:---|:---|
| React | 运行时库（React + ReactDOM） | 虚拟 DOM + Fiber diff |
| Vue | 运行时库（响应式 + 渲染器） | 响应式追踪 + VNode diff |
| Svelte | 内部辅助代码，远小于前两者，但非 0 | 编译期定位节点，直接写入 |

**Svelte 5 的写法**：

```svelte
<script>
  let count = $state(0);
</script>

<button onclick={() => count++}>
  点击次数：{count}
</button>
```

编译期已经定死三件事：这个文本节点只受 `count` 这一个表达式影响、变更时写的是它的 `textContent`、以及**不需要为了更新而重新描述整棵 UI**。运行时还要做的是：读值时收集依赖（信号图）、写入时标脏并入队、微任务 flush 后执行那个节点的更新函数。

**关键洞察**：Svelte 省掉的不是「计算」，而是「比对」——它把「哪个节点要改」提前到构建期算完，运行时只剩执行。真正昂贵的 Diff 从未发生，因为不存在可供 Diff 的中间树。换来的约束是模板必须静态可分析：一旦结构要等到运行时才知道，这条路就走不通，只能退回运行时调度。
