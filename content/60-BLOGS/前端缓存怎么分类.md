## 前端缓存怎么分类

> 核心摘要：缓存的全部难度不在「存」，而在「失效」。所以分类的正确度量不是容量、介质或 API 形态，而是**失效由谁判定**——这个同时决定了出事时你能不能正确判别。

---

## 引言

「前端有哪些缓存机制」这个问题，我查过很多次，每次拿到的都是一张混杂的清单：强缓存、协商缓存、Memory Cache、Disk Cache、Service Worker、Cache API、IndexedDB、localStorage、sessionStorage、Cookie、CDN……

清单越来越长，混淆却越来越深。原因是清单里并排的东西根本不是同类：`Web Storage` 存的是应用数据，`HTTP 缓存` 存的是网络资源。把它们放进同一张按容量和介质排列的表，那就只能逐项记忆，没法推理。

而缓存真正有意义的地方，全在推理上：

- 发了版，用户还是旧页面；
- 清了浏览器缓存，拿到的还是旧的；
- 配了 `max-age=31536000, immutable`，网络面板里照样有请求。

这三件事没有一件是「记不住 API」造成的。它们共同的原因是：**同一个资源身上同时存在三四份副本，而你不知道哪一份还在生效、谁有权作废它。**

下面先看==一次请求实际上的缓存链路==，再给两根分类逻辑度量轴，然后才看那张表。

---

## 主体

### 一、一次请求会经过谁

缓存不是「五种可选方案」，而是请求路径上的一串拦截点，**命中即返回，不再往下**：

| 顺序 | 拦截者 | 谁能往这里放东西 | 命中时省掉什么 |
|:--|:--|:--|:--|
| 1 | Service Worker 的 `fetch` 处理器 | 你的代码（`Cache API`、`IndexedDB`） | 下面的全部 |
| 2 | 内存中的副本 | 浏览器自己 | 磁盘 I/O |
| 3 | 磁盘上的 HTTP 缓存 | 响应头 | 整个网络往返 |
| 4 | CDN 边缘节点 | 运维与响应头 | 回源的那一段 |
| 5 | 源服务器 | 业务逻辑 | 数据库查询与渲染 |

这个顺序解释了「多级缓存」这个词为什么容易误用：它不是让你把五层都配上，而是告诉你一次请求**最可能被谁先拿走**。配得对的系统，第 1 层和第 3 层之间通常只有一层在真正干活。

### 二、第一根轴：它省掉的是哪一段

同样是「缓存」，省掉的东西不一样，代价结构也就不一样：

| 省掉的是 | 机制 | 代价落在哪 |
|:--|:--|:--|
| **网络往返** | HTTP 缓存、CDN、`Cache API` | 一致性：内容更新后要主动作废旧副本 |
| **后端查询** | Redis、接口层缓存、`IndexedDB` 存接口响应 | 新鲜度：数据可能比数据库旧几秒 |
| **计算** | `Map`、`memo`、React Query、SWR | 内存：缓存不释放就是泄漏 |
| **序列化与解析** | 预先解析好的 `Response`、结构化克隆缓存 | 内存翻倍：原件和副本同时存在 |

第一行是唯一能让请求**根本发不出去**的，所以排在最前面。后三行并不减少请求数，它们减少的是请求到达之后的工作量——这个区别决定了优化该往哪个方向做：想降低首屏时间，去压第一行；想降低接口 QPS，去压第二行；想降低长列表滚动时的掉帧，去压第三行。

把「用了缓存」当成一个统一手段，最常见的后果是在第四行使劲（比如给组件加 `memo`），而真正的瓶颈在第一行（一个没配缓存的接口被每个业务调用多次）。

### 三、第二根轴：失效由谁判定

这才是分类的主轴。缓存的全部难度在于失效，而失效的判定权只有四个归属：

| 失效由谁判           | 具体机制                                                           | 你怎么让它失效                                 | 你有没有控制权         |
| :-------------- | :------------------------------------------------------------- | :-------------------------------------- | :-------------- |
| **协议**（响应头里的时间） | `max-age`、`s-maxage`、`Expires`                                 | 改响应头，等过期                                | 没有，只能等          |
| **服务端**（验证器比对）  | `ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since` | 改内容，或换文件名                               | 有，但要付出一次往返（RTT） |
| **你的代码**        | `Cache API`、`IndexedDB`、`Web Storage API`                      | 改版本号、`delete()`、覆写                      | 有，且立即生效         |
| **浏览器**（配额淘汰）   | 所有落在磁盘上的存储                                                     | 无法控制，只能申请 `navigator.storage.persist()` | 几乎没有            |

这张表能拆掉一个反复出现的误解。有人说「我清了缓存，怎么还是旧的」——他清掉的是第一行和第四行的东西，而 CDN 边缘、Service Worker 里各自的副本一份没动。反过来，有人抱怨「用户拿不到新版本」，往往是因为第一行的时间还没到，而他又没有任何第三行的开关。

「有没有控制权」这一列，比「怎么配置」更值得分辨。 排查线上问题时，它决定你第一步该看哪里：有控制权的层先去作废，没有的层只能等或在构建期规避。

### 四、强缓存和协商缓存不是两种缓存

这是中文资料里最容易造成误解的一处。它俩是同一次查找的两个分支：

```text
有这个资源的副本吗？
├─ 没有 → 发请求，拿到 200，存下来
└─ 有 → 它新鲜吗？（freshness_lifetime > current_age）
        ├─ 新鲜 → 直接用，不发请求        ← 这叫「强缓存命中」
        └─ 不新鲜 → 带验证器问一句
                    ├─ 没变 → 304，用旧副本，只更新元数据   ← 这叫「协商缓存命中」
                    └─ 变了 → 200，拿新的
```

两个分支用的是**同一份副本、同一套判定**。所以不存在「分别配置两套缓存」，也不存在「强缓存失效后切换到协商缓存」——后者听起来像切换机制，其实是同一次查找走进了下一个分支。

中文社区常把缓存分成三档：强缓存（`max-age`）、协商缓存（`no-cache`）、不缓存（`no-store`）。这个三分法的问题在第三档：**「不缓存」不在判定链上**。`no-store` 在存储期就已经出局，副本从来没存在过，谈不上「有没有过期」。把它当成第三档，会让人以为存在一条「每次都请求」的判定路径，从而问出「不缓存什么时候过期」这种无解的问题。

`RFC 9111` 里只有两段：§3 存储、§4 复用（`§4.3` 是验证）。所谓「强缓存」就是 §4 的复用判定全部通过；所谓「协商缓存」就是走到了 §4.3。

### 五、完整分类：按缓存的主体分三类

| 类别 | 具体机制 | 存在哪 | 失效由谁判 | 代码能读写吗 |
|:--|:--|:--|:--|:--|
| **资源缓存**<br>缓存 HTTP 响应本身 | `Cache API`（配 Service Worker） | 磁盘 | 你的代码 | 能，且能拦截请求 |
| | 内存副本 | 进程内存 | 浏览器（会话内，刷新即失） | 不能 |
| | HTTP 缓存（磁盘） | 磁盘 | 响应头 | 不能，只能改响应头 |
| | CDN 边缘 | 边缘节点 | 运维（`s-maxage`、主动 purge） | 不能 |
| **数据存储**<br>存 API 响应或用户数据 | Cookie | 磁盘或内存 | 你（`Max-Age`）+ 浏览器 | 能，且会**自动随请求发送** |
| | localStorage | 磁盘 | 你（手动覆盖） | 能，同步 |
| | sessionStorage | 内存或磁盘 | 标签页关闭 | 能，同步 |
| | `IndexedDB` | 磁盘 | 你（事务） | 能，异步 |
| | `Cache API` | 磁盘 | 你 | 能，异步 |
| **运行时缓存**<br>缓存计算结果 | `Map`、`memo`、React Query、SWR | JS 堆 | 你的代码 | 能，随页面销毁 |

第三类最容易被漏掉，但它最便宜：同一个接口在多个组件间复用，靠它比任何持久化都快，而且没有跨会话的一致性问题。它的失效规则最简单——页面没了就没了。

`Cache API` 在两处出现，因为它既是「能被拦截的响应仓库」，也是「能被代码读写的存储」。

### 六、最容易混淆的地方

| 混淆 | 区分点 |
|:--|:--|
| **Cookie vs Web Storage** | 只有 Cookie 会**自动随每个同源请求发送**。Web Storage 是纯本地容器，服务端永远看不到——这也是它不能存鉴权态的原因（要存就得靠 JS 手动塞进请求头） |
| **Cache API vs HTTP 缓存** | Cache API 是代码显式管理的 `Request`/`Response` 仓库，白盒、要自己写淘汰；HTTP 缓存由协议驱动，黑盒、配额与淘汰浏览器负责。**Service Worker 是唯一能把两者接起来的**，因为只有它能拦截 `fetch` |
| **内存副本 vs 磁盘缓存** | 不是两种机制，是 HTTP 缓存的两个存放位置。所以它们没有各自的过期配置——`max-age` 只有一份，写在同一组响应头里 |

再补一个常被当成缓存的东西：`preload`、`prefetch`、`preconnect` **不是缓存机制**，是「提前发起连接或请求」。它们的作用是把资源送进上面某一层，本身不决定过期。把它们当作一类缓存来列，就会说不清「它的过期时间在哪」。

### 七、选用顺序

要让**请求本身消失** → 先配响应头 + CDN。这是唯一能让请求发不出去的一层，投入产出比最高。
要**离线可用或自定义路由** → Service Worker + `Cache API`。
要存**结构化的大对象** → `IndexedDB`。注意它异步、有事务、要处理版本升级。
要存**小配置且同步读** → localStorage。注意它会阻塞主线程，且只存字符串。
要**让服务端也读到** → Cookie。**注意它会被每个同源请求携带，体积直接变成带宽**。
要**跨组件复用结果** → 运行时缓存。优先做这个，成本最低。

### 八、几条容易被当成规律的说法

- **`max-age` 是上限，不是保证。** 它说的是「在这段时间内可以不用再问」，不是「这份副本一定留这么久」。磁盘配额、LRU 淘汰、用户清理都会让它中途消失。把长期强缓存当成「一定命中」，是很多「首屏为什么还是慢」的来源。
- **`immutable` 不延长有效期。** 它省的只是有效期内的那次条件请求（用户刷新时）。过了 `max-age`，它照常要验证。
- **「清浏览器缓存」只清一层。** CDN 边缘、Service Worker、服务端缓存都不在其中。
- **缓存是负资产。** 它换取性能的代价是一致性成本和调试成本：一处配错，用户可能长期看到旧版本，而你在本地永远复现不出来。所以「什么时候不该缓存」和「怎么缓存」同等重要——内容会变又没有版本号的文件、带用户身份的接口响应、需要强一致的余额与库存，都属于不该缓存的那一类。

## 总结

回到开头那个问题：缓存怎么分类。

两根轴，四层：

- **省什么**：网络往返 / 后端查询 / 计算 / 序列化。只有第一档能让请求消失。
- **谁判失效**：协议 / 服务端验证器 / 你的代码 / 浏览器配额。这一档决定出事时你有没有开关。

判断一个新机制，问四句就够：**存什么（键是什么）？谁判它失效？失效后付什么？代码能不能读写？** 第三问答不出来，说明只是记住了名字。
